# FeatherAuth: Requirements

This file says what FeatherAuth must do, how safe it must be, how it is run, and how fast and small it must be. It does not say how any of it is built: that is [DESIGN.md](DESIGN.md), which also holds the acceptance table ("Acceptance criteria and test plan") and the tests.

How to read it:

- **Kinds.** `FR` are product requirements (what the service does for apps and users), `OPS` are operations requirements (deploy, upgrade, back up, scale, observe, release, supply chain), `SEC` are security requirements, and `NFR` are performance and size targets.
- **Ids are stable.** An id never changes meaning and is never reused. Ids of features that were dropped stay unused (see Unused ids).
- **MUST** means required. Every requirement is one testable statement with the reason it exists (who needs it, or which threat it stops).
- **How each kind is checked.** FR and SEC requirements are proved by automated tests: the "Covers" column of the acceptance table in DESIGN.md is the only map from a requirement to its tests, and `make trace` fails when an FR or SEC id has none. OPS and NFR requirements are checked at each release by the release check in [RELEASING.md](RELEASING.md).

Names in examples are neutral: realm `main`, clients `web` and `mobile`, host `auth.example.com`.

## Product goals

FeatherAuth is a small, self-hosted login service. Apps send users to it, it runs the sign-in with a social provider, and it returns standard OpenID Connect (OIDC) tokens that any API can verify with public keys.

It is an **authentication** service: it proves who a user is. It does not decide what a user may do; permissions, roles and ownership stay in each app or API.

1. **One login service for many apps**, on mobile (iOS, Android, cross-platform) and on the web, so that no provider secret ever lives in an app.
2. **Standard OIDC**, so that any OIDC or OAuth 2 client library works with it and any API verifies its tokens offline.
3. **Social login first**: Google, Apple, GitHub, Facebook and any OIDC provider, with FeatherAuth's own user records, so that one person can have several linked sign-in identities.
4. **Configuration as plain text files**, changeable while the service runs, never a rebuild.
5. **Small and cheap to run**: one small server and Docker are enough (see the NFR targets).
6. **No lock-in**: SQLite by default, Postgres as an option, its own user table, standard tokens.
7. **Easy to audit**: a developer new to Go can follow the code in an afternoon (NFR-14 is the checkable part).

**Expected load** that the targets are sized for: about 1,000 users signing in 5 times a day (about 5,000 sign-ins a day), with headroom for 1,000 simultaneous requests.

## Users and use cases

| ID | Who | What they do |
| --- | --- | --- |
| UC-1 | A native mobile app (iOS, Android, React Native, Flutter) | Signs the user in through the system browser or an in-app browser tab and keeps the user signed in for a long time. It cannot keep a secret (public client) |
| UC-2 | A single-page web app | Signs the user in from the browser and calls the token endpoint from JavaScript. It cannot keep a secret (public client) |
| UC-3 | A server-rendered web app or a backend for a frontend | Signs the user in from its server, which keeps a client secret (confidential client) |
| UC-4 | An API | Trusts FeatherAuth's access tokens by checking them offline with the realm's public keys; may also ask for the user's claims |
| UC-5 | Several products on one service | Each product or environment gets its own fully isolated realm |
| UC-6 | An operator or a script | Installs, configures, upgrades, backs up and monitors the service, and maintains users from the command line where the data is |
| UC-7 | A person signing in | Chooses a provider, signs in there, and later may sign out, sign out everywhere, or delete their account through the app |
| UC-8 | A developer trying FeatherAuth | Runs the shipped example single-page app against their FeatherAuth to see sign-in, claims, refresh and sign-out working, and copies its code |

## Scope

FeatherAuth provides:

- The OIDC endpoints: discovery, authorize, token, userinfo, keys (JWKS), logout (RP-Initiated Logout), token revocation, and the list of the signed-in user's sessions.
- Sign-in through Google, Apple, GitHub, Facebook and any single-issuer OIDC provider, each with its own branding on the chooser page.
- The providers' account notices: Apple's server-to-server notifications, Google's Cross-Account Protection security events, and Meta's data-deletion callback and instructions page.
- Its own user records with several linked identities, and safe automatic linking by verified email.
- Access tokens, ID tokens and rotating refresh tokens, optionally bound to a device key (DPoP).
- A single sign-on browser session with silent `prompt=none` sign-in, and back-channel logout notices to apps' servers.
- Public and confidential clients with exact redirect URI matching.
- Isolated realms, clients, providers and every setting in text files, reloaded while the service runs.
- A command line for configuration checks, keys, users, sessions, import, backup and health checks.
- SQLite or Postgres, a copy tool from SQLite to Postgres, and several instances on one Postgres database.
- A container image, compose files, reverse proxy examples (Caddy, nginx), optional built-in TLS, built-in backups, health endpoints, and signed release images.
- English and Indonesian page texts, and translation files for other languages.
- Options for client libraries that expect fixed URL layouts or token formats: configurable endpoint paths, provider-hint and logout-return parameter names, and refresh token format.

**Providers are reached by the web flow only.** Towards a provider, FeatherAuth is always a web client: the browser goes to the provider and comes back to FeatherAuth. Towards apps it speaks standard OIDC. This keeps one sign-in path to secure and test. The cost: on iOS the user sees Apple's web sign-in in the browser tab, not the system's Sign in with Apple sheet.

## Non-goals

FeatherAuth deliberately does not do these and does not plan to. A request for one gets a clear error and no option exists for it:

- Authorization: permissions, roles, groups, ownership rules, consent screens.
- Offline tokens and offline sessions, service accounts, client policies and profiles.
- The implicit, password (direct access) and device grants; token exchange.
- A native sign-in in which the app hands FeatherAuth a token from a provider's SDK.
- Mutual-TLS bound tokens, pushed authorization requests, request objects (`request`, `request_uri`), ACR or level-of-assurance mapping.
- Dynamic client registration, front-channel logout and token introspection.
- Scopes that select claims: `openid` is the only scope; every client of a realm gets the same small set of user claims.
- Email-based actions (verification, password reset).
- Administration over the network or in a browser: no admin port, no admin HTTP API, no admin user interface; administration is by command line and text files.
- Themes beyond the login page settings of FR-55.
- Multi-tenant OIDC providers whose ID tokens carry a different issuer per tenant.
- Telemetry of any kind (SEC-46).

## Roadmap

Not built yet, in no fixed order:

- **Scale beyond 1,000 concurrent users**: set capacity targets for several instances behind a load balancer, measure them, and decide what else is needed (more database capacity, a connection pooler, instances started automatically).
- **Metrics**: a Prometheus `/metrics` endpoint on a separate local address (requests and latency by endpoint, tokens issued, refresh failures, reload status, goroutines, memory).
- **Roles**: a `roles` claim and commands to manage it, only if several apps need to share roles.
- **More sign-in methods**: magic links, passkeys, multi-factor authentication, and the email sending they need.
- **Account linking by the user** (the operator's `user link` command exists).
- **A recheck at the provider for long sessions**, so that a user who removed the app at GitHub or Facebook is noticed before the refresh token expires.
- **Built-in ACME certificates** (today Caddy, or a proxy, gets them).
- **Copy from Postgres back to SQLite.**
- **An admin API for realm settings**, only if ever wanted; it would need lifting the non-goal above.

## Product requirements (FR)

| ID | Requirement | Reason |
| --- | --- | --- |
| FR-01 | Each realm MUST publish an OIDC discovery document at `<issuer>/.well-known/openid-configuration` that holds every field OpenID Connect Discovery requires, the configured endpoint URLs, and an `issuer` identical to the `iss` of the tokens it issues. | Client libraries configure themselves from discovery, and strict ones reject a missing field or an issuer that differs by one character (UC-1 to UC-4). |
| FR-02 | The authorize endpoint MUST accept an authorization code request by GET and by form POST, require `openid` in `scope` and ignore every other scope, take a provider hint and pass `prompt`, `max_age` and `login_hint` on to the provider where it has an equivalent, answer `prompt=none` without a usable browser session with `login_required`, and answer every invalid request with the error listed for it in DESIGN.md ("Errors in the authorization request"). | Apps use standard libraries that send these parameters; a user must be able to switch accounts after logout; an app must learn why a request failed. |
| FR-03 | An unknown `client_id`, or a `redirect_uri` that is not an exact match of a registered one, MUST get an error page and MUST NOT be redirected. | Redirecting to an unverified address would hand codes or errors to an attacker. |
| FR-04 | Without a provider hint the authorize endpoint MUST show a page with one button per enabled, non-hidden provider, or go straight to the provider when exactly one is enabled and not hidden; with a hint naming an enabled provider it MUST go straight to that provider, and a hint naming an unknown or disabled provider MUST show the page. | Users choose how to sign in; apps with their own provider buttons skip the page. |
| FR-05 | The callback MUST accept a provider's result only for a sign-in in progress that was started in the same browser and sent to the provider named in the callback path, then obtain a verified identity (subject, email, whether it is verified, name, time of sign-in), and MUST return the user to the app with the error listed in DESIGN.md ("Errors during login") when the user cancels or the provider fails or cannot be reached. | Binds the result to the user who started it and to the right provider; an app must close its browser tab and show a reason. |
| FR-06 | After a successful provider sign-in the service MUST find or create the user (FR-12) and return to the app's redirect URI a single-use code valid for `tokens.code_lifetime` (default 60 seconds), the original `state` when one was sent, and `iss`, in the requested response mode (`query`, `fragment` or `form_post`). | The standard authorization code response; `iss` tells the app which server answered (RFC 9207). |
| FR-07 | The token endpoint MUST exchange a code only for the client it was issued to, after that client's authentication (a secret by `client_secret_basic` or `client_secret_post` for a confidential client), with the same redirect URI and a PKCE verifier that matches the challenge; it MUST refuse a reused code and revoke the session made from it, and refuse a code whose user, client or realm was disabled or removed after it was issued. | A stolen or intercepted code must be useless to anyone else (RFC 6749, RFC 7636, RFC 9700). |
| FR-08 | The token endpoint MUST accept a refresh token only from the client it was issued to (a confidential client authenticates every time), MUST rotate it on every use for a public client and for a confidential client unless its rotation is off, and with rotation MUST revoke the whole session when an already rotated token is used after the grace window. | Mobile apps stay signed in for months (UC-1) while a copied refresh token is detected when both copies are used. |
| FR-09 | The userinfo endpoint MUST accept GET and POST with an access token, look the user up, and return `sub` and the realm's selected user claims; an invalid token, or a user who is missing or disabled, MUST get `401` with `WWW-Authenticate: Bearer error="invalid_token"`. | Apps and APIs read the profile, and can use it as an online check that the user still exists (UC-4). |
| FR-10 | Each realm MUST publish every active and verify-only public signing key in its JWKS, each with `use: sig`, `alg` and `kid`, cacheable for 300 seconds, so that a token can be verified with the JWKS alone and a tampered token is refused. | APIs verify tokens offline (UC-4), also across a key rotation. |
| FR-11 | The logout endpoint MUST accept GET and form POST (RP-Initiated Logout) and these four kinds of request: (1) with a valid `id_token_hint`, also an expired one, it MUST end the session the hint names and redirect only to a return URL registered for that client, and a hint that fails verification, a `client_id` that does not match it or an unregistered URL MUST get the error page and end nothing; (2) without a hint but with a `client_id`, it MUST end nothing and redirect only to a return URL registered for that client; (3) with neither, it MUST end nothing and redirect only a return URL that arrived in a legacy parameter name and is registered in the realm, and otherwise show the signed-out page; (4) a POST with a refresh token (with its client's id or authentication) or with an access token MUST end the session it names and answer `204`. | Users and apps sign out, from the browser or from the app's own code, without opening an open redirect. |
| FR-12 | Sign-in MUST find the user by the provider identity first, then link to an existing user only under the automatic linking rules (SEC-04), and otherwise create a new user and identity; at most one user of a realm may hold a given verified email. | One person keeps one account across sign-ins and safely across providers. |
| FR-13 | `DELETE /account` MUST delete the user, their identities and their sessions, revoke a stored Apple token at Apple, and answer `204`, only for an access token of a client allowed to delete accounts and a sign-in no older than `tokens.account_delete_max_auth_age`; a client not allowed MUST get `403` (`insufficient_scope`), a sign-in that is too old MUST get `401` with an answer that tells the app to sign the user in again (RFC 9470), and a missing or disabled user MUST get `401` (`invalid_token`). | App stores require in-app account deletion (UC-7); a stolen or old token must not delete an account. |
| FR-14 | Each provider MUST be reached through one adapter behind a common interface; any single-issuer OIDC provider MUST work from configuration alone, and every provider's endpoints MUST be overridable in configuration. | New providers and test or regional endpoints need no code change. |
| FR-15 | Realms, clients and providers MUST be loaded from the configuration directory and be changeable without rebuilding the image. | Operators change settings as data, not code (goal 4). |
| FR-16 | `GET /healthz` MUST report that the process is alive, and `GET /readyz` MUST report readiness, answering `503` while the database cannot be reached (and during shutdown, OPS-13). | Docker, proxies and deploy scripts send traffic only to an instance that can serve it. |
| FR-17 | The configuration directory and, optionally, the listen address MUST be settable by environment variables (`FEATHERAUTH_CONFIG_DIR`, default `/etc/featherauth`, and `FEATHERAUTH_LISTEN`), everything else MUST come from files, and startup MUST fail with a clear error when `server.yaml` or `database.yaml` is invalid or no realm file is valid. | Containers set paths from the environment; a broken install must fail loudly, not run half configured. |
| FR-18 | The service MUST reload its configuration on a file change or `SIGHUP`, validate it first and keep the last good configuration when it is invalid, reload each realm independently, apply the options marked `live` the same way, and report every other changed option of `server.yaml` and `database.yaml` as `restart required` without applying it. | A typo must never take the service down; an operator must know when a restart is needed. |
| FR-19 | Configuration MUST be human-editable text, with an explanatory comment on every field in the shipped examples, MUST reject unknown fields, and MUST reference secrets by file path only. | Operators edit files by hand; a typo must be caught, and secrets must stay out of the files that are shared and reviewed. |
| FR-20 | The binary MUST provide the commands `serve`, `config init`, `config check`, `backup`, `keys generate` (signing keys, and encryption keys with `--type encryption`), `user ...`, `session list`, `session revoke`, `import`, `db copy`, `healthcheck` and `version` (which prints the build version), each exiting `0` on success and non-zero on failure. | Every operator task has a command that scripts can call (UC-6). |
| FR-21 | The realm MUST be taken from the URL path and applied to every lookup, token, key and client; an unknown realm MUST get `404`, and a disabled realm MUST refuse sign-ins and refreshes while its discovery and keys stay available. | Realms are isolated tenants (UC-5); tokens already issued must stay verifiable. |
| FR-22 | Each realm's `user_data` settings MUST decide which user attributes are stored, which claims tokens and userinfo carry, and the format of the ids of the users the realm creates. | Keep only the data each product needs (privacy) and match the id type of the apps' databases. |
| FR-23 | The `featherauth user` commands MUST let a script read, update, disable, enable, delete, link and unlink users, writing an audit record for each change. | Operators support users and fix accounts without a database client (UC-6). |
| FR-24 | With SQLite the service MUST write a consistent daily snapshot of the database while it runs, and `featherauth backup` MUST write one on demand; a snapshot MUST open and hold the users and tokens. | Copying a live database file is not safe; operators need a restorable copy every day and before an upgrade. |
| FR-25 | Database settings MUST come from `database.yaml`, a file separate from the realm files, read at startup. | A database change needs a restart and a data copy, unlike realm settings. |
| FR-26 | Endpoints called from a browser (token, userinfo, sessions, JWKS, discovery) MUST support cross-origin calls from the `web_origins` registered for a client; which origins are allowed is owned by SEC-18. | Single-page apps (UC-2) call these endpoints from JavaScript. |
| FR-27 | `featherauth import` MUST load users from a documented generic JSON format, keeping their ids when given, writing nothing when the file is invalid, and MUST be safe to run twice. | Moving from another login system keeps every user's `sub`, so apps keep their data. |
| FR-28 | Endpoint paths, the provider-hint parameter names, the logout-return parameter names and the refresh token format MUST be settable in configuration, with the standard values as defaults. | Some client libraries and existing provider registrations expect fixed URLs or formats; they must work without code changes. |
| FR-29 | Each endpoint path MUST be configurable as a template with the placeholders `{prefix}`, `{realm}` and `{provider}`, validated at load, and discovery MUST list the configured paths. | Deployments behind a path prefix, and apps that build URLs themselves. |
| FR-30 | Configuration validation (at load, at reload and in `config check`) MUST reject a realm named `admin`, `healthz` or `readyz`, naming the file and the reserved word. | These names would collide with the service's own paths. |
| FR-31 | The provider events path MUST accept Apple's server-to-server notifications, verify the signed payload, act on each event as DESIGN.md lists ("Provider account events"), and answer `200` for an event that was handled, unknown or repeated, `400` for one that fails verification, and `503` while Apple's keys cannot be fetched. | When a user stops using Sign in with Apple or deletes the Apple account, their sessions or account must end; Apple retries only on an error answer. |
| FR-32 | Configuration validation MUST reject, naming the file, line and reason: a redirect or post-logout URI with a fragment, a wildcard, the scheme `javascript`, `data` or `file`, or plain `http` on a host other than `127.0.0.1` or `[::1]`; a loopback redirect on a confidential client; refresh rotation off on a public client; the PKCE exception on a public client with a refresh idle lifetime above 24 hours or a session lifetime of `0` or above 720 hours; a realm without exactly the active signing keys its algorithm needs; a provider timeout above 30 seconds; a duration of zero or less where zero has no defined meaning; and an enabled Facebook provider without a contact address or with a flow other than `oauth`. | Unsafe settings must be impossible to deploy, not just discouraged. |
| FR-33 | Browser pages MUST carry the headers of SEC-12 and load their stylesheet and provider logos from the service itself, and the `form_post` answer page MUST deliver the result with and without JavaScript under a content security policy that allows only its own submit. | Pages must work under a strict policy, and `form_post` must work in every browser. |
| FR-34 | Each realm MUST serve a data-deletion instructions page. | Meta requires one for a live app. |
| FR-35 | With `driver: postgres` the service and the command line MUST run on Postgres with the same behaviour as on SQLite, also under concurrent requests. | Several instances need a shared database (FR-54); some operators already run Postgres. |
| FR-36 | `featherauth db copy --from <file> --to <file>` MUST copy every table from a SQLite database to an empty Postgres database, refuse a target that holds rows, and verify row counts and checksums before it commits. | The way from SQLite onto Postgres must lose nothing and never overwrite data. |
| FR-38 | The revocation endpoint MUST accept a POST with a `token` and client authentication (RFC 7009), end the session of a refresh token or access token of that client, answer `200` for any other token, and be listed in discovery. | Standard libraries revoke tokens at logout. |
| FR-39 | A logout with an access token and `all_sessions=true` MUST end every session of the user when the client is allowed to manage sessions, and `featherauth session list` and `session revoke` MUST list and end a user's sessions, each ending written as an audit record. | "Sign out of all devices" for a user who lost a phone (UC-7); the operator can do the same (UC-6). |
| FR-40 | The provider events path of a Facebook provider MUST accept Meta's `signed_request`, verify it, delete or unlink the user as for Apple's account deletion, and answer with a confirmation code and the URL of the data-deletion page. | Meta's data-deletion callback for apps that use Facebook Login. |
| FR-41 | When `user_data.access_token_claims` is set, it MUST decide the user claims of access tokens, while ID tokens and userinfo keep the claims of `user_data.claims`. | Access tokens reach every API and its logs; a realm can keep emails and names out of them (privacy). |
| FR-42 | The sessions endpoint MUST list the sessions of the access token's user, and a logout with an access token and `session=<id>` MUST end that one session, for a client allowed to manage sessions. | A user sees where they are signed in and ends one device's session (UC-7). |
| FR-43 | Every ending of a session of a client with `backchannel_logout_uri` MUST queue a logout token, the service MUST deliver it with retries, and discovery MUST list back-channel logout support. | An app's server learns at once that a session ended (OpenID Connect Back-Channel Logout). |
| FR-44 | For a client with DPoP on, the token endpoint MUST bind the session and its tokens to the key of a valid DPoP proof and require that key at every refresh, and the service's own token-checking endpoints MUST accept a bound access token only under the `DPoP` scheme with a valid proof. | A refresh token copied off a device is useless without the device's private key (RFC 9449). |
| FR-45 | With `sso.enabled`, a completed sign-in MUST start a browser session, an authorization request that meets the conditions in DESIGN.md ("Single sign-on session") MUST be answered from it without a provider, also with `prompt=none`, and a logout in that browser MUST end it. | Users of several apps of one product sign in once; web apps renew silently. |
| FR-48 | The provider events path of a Google provider MUST accept Google's security event tokens and act on each event as DESIGN.md lists ("Google Cross-Account Protection"), and MUST treat the token's issuer, and the issuer of each event's subject, as equal to the issuer of Google's configuration when the two differ only by one trailing slash; no other check is relaxed. | When Google ends a user's sessions or disables the account, FeatherAuth's sessions for that user end too; Google's documents spell its issuer both with and without the slash, and a refused event would leave the sessions open. |
| FR-50 | The binary MUST ship a complete Indonesian (`id`) translation, turned on by listing its code, and a translation file in the configuration directory MUST be able to replace single messages of it. | Indonesian-speaking users; operators can adjust wording without a rebuild. |
| FR-52 | With `tls.mode: files` the service MUST end TLS itself with a certificate from files, redirect plain HTTP to HTTPS, and load a changed certificate without a restart. | Hosts without a reverse proxy. |
| FR-53 | With `rate_limit.store: database` the rate limit MUST be counted in the database for all instances together, and a failure of that count MUST fall back to the instance's own in-memory limit. | With several instances the limit must hold across them, and an outage of the count must become neither an outage of sign-in nor no limit. |
| FR-54 | With `driver: postgres`, several instances MUST be able to serve one database, with migrations and back-channel deliveries done once, and a rolling deploy MUST complete with no failed request. | Zero-downtime upgrades and room to grow. Accepted risk: a request on a connection that the stopping instance's system has accepted but the service has not yet taken when it stops listening is cut off, a window of microseconds when the CPU is not saturated, once per replaced instance, because no proxy can safely repeat a written `POST`. |
| FR-55 | Each realm MUST be able to set its login page's display name, logo, accent color, contact address and order of provider buttons, with the contact shown on the error and data-deletion pages, while the built-in providers' buttons keep their vendor's branding. | Each product looks like itself, and provider branding rules are met. |
| FR-56 | Every provider MUST support the common options (enabled, hidden, display name, scopes, trust in its email, automatic linking, profile sync, call timeout, endpoint overrides), and the built-in adapters MUST offer the provider-specific options DESIGN.md lists (for example Google's hosted domain, Apple's team, key and notification audiences, GitHub's sign-up and verified-email rules, Facebook's Graph version, fields and required email). | Each provider's real setup and restrictions can be expressed in configuration (an umbrella under FR-14). |
| FR-57 | The pages MUST be shown in the browser's preferred language among the realm's supported languages, otherwise in the realm's default language (English unless set), a message missing from a translation MUST fall back to English, and a language added by a translation file MUST apply without a restart. | Users read the pages in their own language; a partial translation never shows an empty text. |
| FR-58 | A request with a method an endpoint does not accept MUST get `405` with an `Allow` header listing the accepted methods, and change nothing. | Clients and proxies learn the right method; nothing is changed by a wrong one. |
| FR-59 | The built-in snapshot schedule MUST keep the newest `backup.keep` snapshots (default 7) and delete older ones, and a failed snapshot MUST be logged at error level, leave older snapshots alone, and never stop the service. | Backups must not fill the disk, and a full disk must not take sign-in down. |
| FR-60 | The service MUST delete expired records (sign-ins in progress, codes, posted callbacks, refresh tokens, remembered events and proofs, rate-limit windows, browser sessions) at least once an hour, and MUST keep audit records. | The database stays small at a steady size; the audit trail is kept. |
| FR-61 | The repository MUST ship a runnable example React single-page app, with its own package manifest so that FeatherAuth gains no dependency, that uses the oidc-client-ts library as a public client to sign in with the authorization code flow and PKCE, verifies the ID token's signature with the jose library, keeps tokens in memory only, shows the user's claims, refreshes with the refresh token only when the user presses a button, and signs out by RP-initiated logout; the client entry it needs MUST ship with it as a copyable file `examples/web-app/example-web-client.yaml` (not in the quick start configuration or the shipped realm example); CI MUST build it and run it end to end in a browser against a FeatherAuth test server, failing when any of these steps fails. | Developers adopt a login service faster from working code (UC-8), and an example that is not tested drifts from the product. |

## Operations requirements (OPS)

These are checked at each release by the release check in [RELEASING.md](RELEASING.md), not by `make trace`. Several product and security requirements are also operational and are not repeated here: health endpoints (FR-16), configuration and reload (FR-15, FR-17, FR-18, FR-19, FR-25), the command line (FR-20, FR-23), backups (FR-24, FR-59), Postgres and its copy tool (FR-35, FR-36), built-in TLS (FR-52), rate limits (SEC-11, FR-53), several instances (FR-54), secret files (SEC-09), HTTPS and page headers (SEC-12), log hygiene in the service (SEC-13), dependencies (SEC-15), container hardening (SEC-31) and signed images (SEC-42).

| ID | Requirement | Reason |
| --- | --- | --- |
| OPS-01 | Each release MUST be published as one container image tagged with its version `vMAJOR.MINOR.PATCH`, holding only the binary, running as a non-root user, and printing that version with `featherauth version`. | Operators pick and verify exactly what they run; configuration and data stay outside the image. |
| OPS-02 | A release image MUST be built only from a commit of the main branch that has passed the full checks (tests, static checks, vulnerability scan), and a tag of any other form MUST publish nothing; a published release tag MUST never be moved, overwritten or deleted, which is a duty of the release process, checked by the release check. | An operator who pins a version must get the code that was tested, forever. |
| OPS-03 | The shipped compose files MUST name no default image tag, and the container images and CI actions the project uses MUST be pinned to an immutable reference (a digest or a commit hash). | A host must never run an image nobody chose, and an upstream change must not enter a build unseen (supply chain). |
| OPS-04 | A new release MUST start on the data of the previous release and apply its database migrations by itself at startup, with no manual step. | An upgrade is "run the new image" (UC-6). |
| OPS-05 | After the new release has migrated a database, the previous release MUST still start and serve sign-ins and refreshes on it, and each migration MUST take under 1 second on a database seeded like the load test (1,000 users with their refresh tokens). | Rollback by image and rolling deploys need old and new versions on one database; the restart budget is 5 seconds (NFR-11). Neither condition is checked by a test yet; both need new checks. |
| OPS-06 | An operator MUST be able to roll back by running the previous image tag, and to restore the data as of a backup taken before the upgrade. | A bad release must be undone quickly. |
| OPS-07 | The documented off-server backup MUST encrypt every snapshot and every copy of the configuration directory before it leaves the server, with only the public key on the server, so that a copy cannot be read without the private key; the service MUST hold no credentials for the backup destination. | Backups hold emails, names, identity links and key files; a stolen backup or a compromised server must not expose them. |
| OPS-08 | A documented restore MUST bring a clean host back from an encrypted off-server copy, for SQLite and for Postgres, with users and sessions intact. | A backup is only worth the restore that works. |
| OPS-09 | With Postgres, `featherauth backup` MUST refuse with a message that names `pg_dump`, and no built-in schedule MUST run. | An operator must never believe a backup exists when none was made. |
| OPS-10 | A planned rotation of a signing key MUST be possible by configuration alone, with no failed token check, before, during or after it, for a verifier that honours the JWKS cache time. | Keys are rotated regularly without an outage. |
| OPS-11 | A written runbook MUST cover an exposed signing key, an exposed encryption key and an exposed client secret, stating what fails and for how long, and every command it names MUST exist. | Decisions made under pressure need a tested procedure. |
| OPS-12 | The shipped container's health check MUST run `featherauth healthcheck` every 10 seconds and report the container unhealthy only after 6 failed checks in a row. | A single late answer under load must not restart a healthy service, while a real outage is seen within about a minute. |
| OPS-13 | On `SIGTERM` the service MUST answer `/readyz` with `503` at once, stop taking connections, let requests in flight finish for up to 30 seconds, and exit `0`. | Deploys and restarts must not cut requests off. |
| OPS-14 | A transient failure (a restart, a database outage) MUST be answered with `503` (`temporarily_unavailable` where an OAuth error is due), and never with `invalid_grant`, `invalid_token` or another `4xx`. | Many clients sign the user out on any failed refresh. |
| OPS-15 | TLS MUST be endable either by any reverse proxy, with documented and tested Caddy and nginx setups for a Let's Encrypt and for a bought certificate in which plain HTTP answers a redirect to HTTPS, or by the service itself (FR-52); the service MUST refuse to start with a public URL that is not `https` unless an explicit local-development setting is made. HTTPS-only use is owned by SEC-12. | Operators use the front door they already have; production never runs without TLS by accident. |
| OPS-16 | The default deployment MUST publish the service's port only on the host's loopback address, so that only a proxy on the same host reaches it; which forwarded addresses are believed is owned by SEC-11. | Nothing may bypass the proxy. |
| OPS-17 | The service MUST write structured JSON logs to standard output, with one line per request holding its duration and status, and lines for every reload result and every `restart required` notice. | Operators debug and measure with the logs alone; metrics are on the roadmap. |
| OPS-18 | The documented proxy configurations MUST keep query strings out of their access and error logs. | Codes, `state` and ID token hints travel in query strings (SEC-13). |
| OPS-19 | The guides MUST tell the operator which stored data is kept in clear (the database, the local snapshots, the Postgres volume) so that the host's disk can be encrypted. Checked by manual check M1 of the release check (RELEASING.md), not by a test. | A stolen or discarded disk must not expose users' emails and names. |
| OPS-20 | Releases MUST follow semantic versioning: a breaking change (an option, default, endpoint, claim or error code renamed or removed; a stricter validation; a database migration that cannot be undone by running the previous image and restoring a backup) MUST come only in a new minor version while the major version is `0`, and only in a new major version from `1.0.0` on, and the release notes MUST name every behaviour change with what the operator or app developer must check. Checked by manual check M1 of the release check (RELEASING.md), not by a test. | Adopters must know which upgrades are safe to take without reading the code. |
| OPS-21 | An operator with only Docker on the host MUST be able to write the initial configuration and generate every key (signing and encryption) with the published image alone, run as a one-off container as the service's user with the configuration directory mounted read-write, with no FeatherAuth binary on the host. | Many hosts run only Docker; the setup and the key runbook (OPS-11) must be doable there. |
| OPS-22 | `database.yaml` MUST offer `postgres.connect_timeout`, default 5 seconds; a connection attempt to an address that does not answer MUST fail within that limit, and `/readyz` MUST then answer `503`. | A slow or half-open network path to Postgres must not hold requests for the operating system's TCP timeout, and readiness must show the outage. |

## Security requirements (SEC)

| ID | Requirement | Reason |
| --- | --- | --- |
| SEC-01 | PKCE with `S256` MUST be required for every client, public and confidential; `plain`, and a challenge without a method, MUST be refused; a challenge that is sent MUST always be verified, and a verifier for a code issued without a challenge MUST be refused; turning PKCE off for one client MUST be an explicit exception, limited to short sessions for a public client (FR-32). | Stops code interception and PKCE downgrade (RFC 9700); the exception exists only for a legacy app while it is updated. |
| SEC-02 | Redirect URIs MUST match a registered URI exactly, with no wildcards, except that a public client's loopback redirect URI may vary in port, and registered URIs MUST be validated at load (FR-32); the port variance applies to redirect URIs only, and a post-logout return URL MUST match a registered one exactly. | Stops open redirects and code theft (RFC 9700, RFC 8252). |
| SEC-03 | Provider ID tokens MUST be checked for signature, issuer, audience (our client id), expiry and `nonce` (and Google's `hd` claim when a hosted domain is set), Apple's identity MUST come from its token endpoint, and calls to Facebook's Graph API MUST prove possession of the app secret. | A forged, replayed or misdirected provider token must not sign anyone in. |
| SEC-04 | Automatic linking MUST attach a new identity to an existing user only when the provider is trusted for email and allowed to link, reports the email verified, the existing user's email is verified too, and the email's domain is on the realm's list of domains that never give an address to another person; it MUST never link on an unverified email, generic OIDC providers MUST default to not trusted, and every automatic link MUST be audited. | Stops account takeover through a reassigned or unverified address. |
| SEC-05 | Access tokens MUST be JWTs following RFC 9068 (header `typ: at+jwt`, claims including `client_id`), valid 15 minutes by default and signed with the realm's algorithm, and ID tokens MUST be signed `RS256`. | APIs verify them with standard libraries; a short life bounds a stolen token. |
| SEC-06 | A refresh token MUST be a server-side record of a 256-bit random secret stored only as a hash, bound to its client, rotated with reuse detection (always for public clients), handed out as an opaque value or a JWT that no API accepts as an access token, with lifetimes per realm and client; a reused login code MUST end the session made from it. | A database leak exposes no usable token; a stolen token is detected. |
| SEC-07 | Signing keys MUST be per realm, loaded from files, carry a `kid` unique across realms, rotate by configuration, and a key removed from the configuration MUST be refused by the service's own checks at once. | Realm isolation and recovery from a key leak. |
| SEC-08 | `state` and `nonce` MUST be random with at least 128 bits, and `state` MUST be checked against the server-side record and bound, by a constant-time comparison, to the browser that started the sign-in through a per-sign-in cookie that is `HttpOnly`, `SameSite=Lax` (never `None`) and `Secure` whenever the service runs on HTTPS, so that parallel sign-ins in one browser do not interfere. | Stops cross-site request forgery on the callback and login fixation. |
| SEC-09 | Provider secrets, signing keys and the encryption key MUST live only in secret files on the server, never in the repository, the image, the database or the logs; every secret file MUST be refused at load and in `config check` when its group or others have any permission (a warning instead with `strict_permissions: false`), certificate files excepted; generated keys MUST be RSA of at least 2048 bits or EC P-256. | Secrets leak through readable files, images and backups. |
| SEC-10 | Stored provider refresh tokens (Apple's) MUST be encrypted at rest with authenticated encryption under a key from `secrets.encryption_key_files`, the first key encrypting and every listed key able to decrypt; a token that cannot be decrypted MUST NOT stop an account deletion (the revoke at Apple is skipped with a warning); storing tokens without a key MUST be a configuration error. | A database or backup leak must not expose tokens that act at Apple; keys can rotate. |
| SEC-11 | The authorize, callback, token, revocation and provider events endpoints MUST be rate limited per client address, and the client address MUST come from `X-Forwarded-For` only when the connection is from a trusted proxy, read from the entries the trusted proxies added. | Slows down guessing and flooding; a client must not pick its own address for the limit and the logs. |
| SEC-12 | The service MUST be used over HTTPS only (how TLS is ended: OPS-15), and every browser page MUST carry HSTS, `X-Content-Type-Options: nosniff`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` and a strict content security policy with `frame-ancestors 'none'`. | Page URLs carry codes and `state`; stops framing, sniffing, caching and referrer leaks. |
| SEC-13 | Logs MUST be structured JSON and, at every level including `debug`, hold no secret (any token, code, `code_verifier`, `state`, `nonce`, `id_token_hint`, client secret, password, `Authorization` or cookie header, DPoP header) and no personal data other than the user id and the client address; emails MUST never be logged; URLs MUST be logged without query, fragment or user information, also inside errors of outgoing calls. | Logs are copied widely; a secret in a log is a leak. |
| SEC-14 | After logout, deletion or disabling, access tokens already issued MUST stay valid until they expire (15 minutes by default) and nothing longer; only `at+jwt` tokens MUST count as access tokens, and the service's own userinfo and account deletion endpoints MUST refuse such a token at once because they look the user up. | APIs verify offline; consuming APIs must know and accept this bound, and an online check is available. |
| SEC-15 | OAuth, OIDC and JWT MUST be handled by vetted libraries, with no hand-written cryptography, and CI MUST scan the dependencies for known vulnerabilities. | Home-made security code is the most common source of flaws. |
| SEC-16 | Tokens, codes, refresh tokens and keys MUST be bound to one realm and refused by every other realm. | Realms are isolated tenants (UC-5). |
| SEC-17 | The service MUST offer no administration over the network: no admin port and no `/admin` path; users MUST be administered only with the command line, which needs access to the server and its data. | Removes a whole class of remote attacks. |
| SEC-18 | Cross-origin calls MUST be allowed only from the registered `web_origins` of the calling client, never with a wildcard. | Another site must not read tokens or claims. |
| SEC-19 | The callback MUST accept a result only from the provider the request was sent to, and every authorization response, success or error, MUST carry `iss`. | Stops mix-up attacks (RFC 9700, RFC 9207). |
| SEC-20 | The service's own token-checking endpoints (userinfo, account deletion, logout and sessions by access token) MUST accept only access tokens (`typ: at+jwt`) of their own realm, and a bound access token only under the `DPoP` scheme with a valid proof. | An ID token, a refresh token or another realm's token must not act as an access token. |
| SEC-21 | Account deletion MUST need an access token of a client allowed to delete accounts and a sign-in no older than `tokens.account_delete_max_auth_age`, and the guides MUST tell apps to also ask the user to confirm, because some providers cannot force a new entry of credentials. | A stolen or old token, or an unlocked browser, must not delete an account silently. |
| SEC-22 | Provider account events MUST be acted on only with a valid provider signature, issuer and audience. | Forged events would end sessions or delete accounts. |
| SEC-23 | A callback posted by form MUST be stored only for a sign-in in progress whose provider returns by form POST, and a sign-in MUST have at most one stored post. | Stops anyone filling the database through the callback. |
| SEC-24 | The rate limit MUST count per IPv4 address and per IPv6 `/64` prefix, and its in-memory table MUST hold at most 100,000 keys, answering `429` to a new key when full. | One IPv6 host controls a whole `/64`; memory must stay bounded under attack. |
| SEC-25 | A reused refresh token or login code whose refusal ended any part of its session not already revoked (an expired one counts) MUST be logged as a warning and audited as `session.reuse_detected`, and a failed client authentication of a known confidential client MUST be logged as a warning with the client id. | The clearest sign of a stolen token must be visible to the operator. |
| SEC-26 | No call to a provider MUST follow an HTTP redirect, and a provider ID token MUST be accepted only when its `azp`, if present, is our client id, and it MUST have one when it has more than one audience. | A wrong or hijacked endpoint must not redirect a call carrying credentials; OIDC Core's audience rules. |
| SEC-27 | A provider event MUST be acted on once, remembered by its `jti` or, without one, by a hash of its payload, until it expires. | A captured event must not be replayed, for example against an account created again. |
| SEC-28 | A sign-in in progress MUST complete at most once: a second callback with the same `state`, also one sent at the same moment as the first, MUST fail and get no code. | Defence in depth against a replayed callback. |
| SEC-29 | Every response the service writes MUST carry `X-Content-Type-Options: nosniff`. | Stops a browser from reading JSON or keys as another type. |
| SEC-30 | Loading the configuration and `config check` MUST warn about a client secret shorter than 32 characters. | A short secret can be guessed over time despite the rate limit. |
| SEC-31 | The shipped compose file MUST run the service with a read-only root filesystem, every Linux capability dropped and `no-new-privileges`. | Limits what an attacker can do inside a compromised container. |
| SEC-33 | Meta's `signed_request` MUST be accepted only with a valid HMAC-SHA256 signature under the provider's client secret and an `issued_at` at most 1 hour old, and MUST be acted on once. | Forged or replayed deletion requests would delete accounts. |
| SEC-34 | A logout by refresh token and a revocation request MUST cause no database write unless the token belongs to the authenticated client and its session can still be ended. | Made-up tokens must not keep the database's write queue busy. |
| SEC-35 | A logout token MUST have the header `typ: logout+jwt`, be signed `RS256`, live 2 minutes, carry `sid`, `sub` and the back-channel event and no `nonce`, be sent only to the client's configured URI over HTTPS (except in local development) without following redirects, and be refused by every token check of the service. | A logout token must not be usable as a credential or sent anywhere else. |

| SEC-39 | Google's security event tokens MUST be accepted only with a valid signature by the keys of Google's RISC configuration, its issuer, our audience, an `iat` at most 24 hours old, and once. | Forged or replayed events would end users' sessions. |

### Accepted risks

These are known and accepted; the guides must state them:

- Access tokens stay valid until they expire after logout, deletion or disabling (SEC-14).
- An access token's audience defaults to the client id, the same as the ID token's, so an API that does not set `audience` tells them apart by the token type alone.
- The database, the local snapshots and the Postgres volume hold emails and names in clear; only off-server copies are encrypted (OPS-07, OPS-19).
- An attacker who sends from 100,000 addresses or `/64` prefixes within a minute can keep the in-memory rate limit table full, so new clients get `429` while it lasts; a firewall or the proxy is the place to stop that (SEC-24).
- Where a provider cannot force a new entry of credentials (Google, Apple, GitHub), a recent sign-in proves only a new pass through the provider in the same browser (SEC-21).
- A public client with the PKCE exception relies on the exact redirect match alone; its sessions are kept short (SEC-01, FR-32).
- A user who removes the app at GitHub or Facebook is not noticed until the refresh token expires (Roadmap: recheck at the provider).

## Performance and size requirements (NFR)

These are checked at each release by the release check in [RELEASING.md](RELEASING.md), not by `make trace`.

Every figure is measured with the load verification in DESIGN.md on the reference machine: the real container image limited to 1 virtual CPU and 512 MB of memory, Caddy in front, a database seeded with 1,000 users and their refresh tokens, no debug logging. The load shapes are:

- **Steady:** 20 requests a second, mixed (sign-in callbacks, refreshes, userinfo, JWKS), for 10 minutes.
- **Held peak:** 1,000 connections kept busy in a closed loop on refresh, userinfo and JWKS for 5 minutes.
- **Burst:** 1,000 refresh requests sent at the same moment.
- **Soak:** the steady load for 1 hour.

Where a target depends on the database, it is given for SQLite and for Postgres separately. Where a target was set from a measurement, it was set at the figure measured then plus 20%, rounded up to a whole unit, so that normal run-to-run variation does not fail a run; a later run that stays under the target meets it, even with less headroom, and the target is not changed. A fixed target that had more than 20% headroom over the measurement when it was set stays as it is, and the memory target of NFR-07 is kept at 120 MB by the owner's decision. "Measured" is the latest recorded result in `docs/RESULTS.md`. A new measurement above a target is investigated, or the owner accepts a new figure, which is then written here.

| ID | Requirement | Reason | Measured |
| --- | --- | --- | --- |
| NFR-01 | Under the steady load, the p95 latency MUST be under 50 ms for refresh at the token endpoint, for userinfo and for the JWKS, on SQLite and on Postgres, with no errors. | The expected real load, with headroom, must feel instant. | SQLite 11.4, 5.5, 4.3 ms; Postgres 11.1, 5.3, 3.6 ms |
| NFR-02 | The held peak MUST complete with no failed request, on SQLite and on Postgres. | Peaks must slow the service down, never break it. | 0 failed on both |
| NFR-03 | Under the held peak, the p95 latency MUST be: on SQLite, under 3 ms for userinfo and under 2 ms for the JWKS; on Postgres, under 5 seconds for userinfo and under 64 ms for the JWKS. | APIs call these endpoints. On Postgres the requests waiting on the database keep the one CPU's queue full: userinfo waits its turn, and so does a JWKS request, which arrives on a new proxy connection; serving the JWKS takes about 0.01 ms. | SQLite 1.8 ms, 1.6 ms; Postgres 3,727 ms, 51.6 ms |
| NFR-04 | The p99 latency of refresh at the token endpoint MUST be: under the burst, under 3 seconds on SQLite and on Postgres; under the held peak, under 15 seconds on SQLite and under 7 seconds on Postgres. | Each refresh costs RSA signatures on one CPU; more capacity comes from a second CPU or `ES256`. | Burst: SQLite 2.5 s, Postgres 2.7 s. | NFR-06 | The service process MUST use under 30 MB of resident memory after 60 seconds idle, on SQLite and on Postgres. | Runs beside other services on a small server. | SQLite 23.2 MB; Postgres 19.7 MB |

| NFR-15 | Back-channel logout notices MUST be delivered with no notice lost, and a receiver that does not answer MUST delay the notices of other clients by at most 20 seconds per delivery round (at most 4 notices a round, each call limited to 5 seconds). | An app's server that hangs must not hold back other apps' logouts for long. | |

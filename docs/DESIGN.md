# FeatherAuth: Design

FeatherAuth is a small, self-hosted login service in Go. Apps send users to it, it runs the sign-in with a social provider, and it returns standard OpenID Connect (OIDC) tokens that any API can verify with public keys.

**How this document relates to the requirements.** [REQUIREMENTS.md](REQUIREMENTS.md) says what FeatherAuth must do and why: its goals, users and use cases (UC), scope, non-goals and roadmap, and the product (FR), operations (OPS), security (SEC) and performance (NFR) requirements with their reasons. This document says how they are met and how each one is tested: every behaviour, option, default, endpoint, table and test. It cites the requirement ids it meets and adds no requirement of its own; a question it cannot answer yet is listed under Open items. The acceptance table at the end ("Acceptance criteria and test plan") is the only map from a requirement to its tests. The requirement tables themselves live only in REQUIREMENTS.md; this document does not copy them.

Names in examples are neutral: realm `main`, clients `web` and `mobile`, host `auth.example.com`.

## How the use cases are served

| ID | How it is served |
| --- | --- |
| UC-1 | Authorization code flow with PKCE in the system browser or an in-app browser tab, returning to a custom URL scheme or an HTTPS app link. Public client (Clients) |
| UC-2 | Authorization code flow with PKCE from the browser, token exchange from JavaScript (CORS allowed for registered origins). Public client |
| UC-3 | Authorization code flow on the server with a client secret. Confidential client |
| UC-4 | Verifies the JWT signature with the realm's JWKS, the header `typ: at+jwt`, and `iss`, `aud` and `exp`. Optionally calls `/userinfo` |
| UC-5 | One realm per product (or per environment), each fully isolated (Realms) |
| UC-6 | The configuration directory, the `featherauth` CLI run where the database is (on the server or in the container), and the deployment files (Deployment and operations) |
| UC-7 | The provider chooser (Provider chooser), RP-initiated logout (Ending a session), sign out everywhere and the sessions of the signed-in user (FR-39, FR-42) and account deletion (Account deletion), each reached through the app |

## Decisions

| Topic | Decision |
| --- | --- |
| Language | Go |
| Protocol | OIDC authorization code flow, PKCE `S256` for every client, redirect-based |
| Clients | Public (mobile, SPA) and confidential (server) |
| Providers | Google, Apple, GitHub, Facebook, plus a generic `oidc` type from config |
| Tenancy | Multiple isolated realms |
| Account linking | Auto-link on a verified email whose domain never gives an address to another person (SEC-04), switchable per provider |
| Configuration | Text files (YAML, commented) in a mounted directory, hot-reloaded, no UI |
| Database | SQLite by default; Postgres as an option (`driver: postgres`, Database configuration); settings in their own file |
| Token consumers | Verify offline through JWKS |
| Token types | Access tokens follow RFC 9068 (`typ: at+jwt`); ID tokens are always `RS256`; access, ID and refresh tokens cannot stand in for one another |
| Hosting | Single VPS, Docker Compose. FeatherAuth needs no particular reverse proxy; nginx and Caddy are documented |
| Backup | Built-in daily snapshot to a local directory, host cron copies it off the server |
| Restart | Up to 5 seconds unavailable per deploy, requests held by the proxy |
| Admin | The `featherauth` CLI only, working on the database directly; no admin HTTP API; realm settings are text files only |
| Provider flow | Providers are reached by the web flow only: towards a provider FeatherAuth is always a web client (the browser goes to the provider and comes back to the callback), towards the apps it speaks standard OIDC. So it needs no per-app audiences and checks no provider token it did not request itself |
| Claims | `user_data.claims` selects the user claims of ID tokens and `/userinfo` (default `name`, `email`, `email_verified`, `preferred_username`), and of access tokens unless `user_data.access_token_claims` names a narrower list; the same minimal set for every client; scopes do not filter them |

## Architecture and login flow

- **App** (mobile or web): sends the user to `/authorize`, then calls `/token`. Use any standard OIDC library.
- **FeatherAuth:** runs the provider login, stores users, issues tokens. The only component that holds provider secrets.
- **Provider:** Google, Apple, GitHub, Facebook or another OIDC provider.
- **API:** verifies access tokens with the realm's public keys.
- **Reverse proxy:** optional and outside FeatherAuth. FeatherAuth serves every page itself (the provider chooser and the error pages) from templates built into its binary, on plain HTTP on a local port. A proxy such as nginx or Caddy is only the public front door: HTTPS, the redirect from port 80, and routing to the right service.

Flow:

1. The app opens `/{realm}/authorize` (GET, or a form POST) with `client_id`, `redirect_uri`, `scope=openid`, `state`, `nonce` and a PKCE challenge, optionally `provider` to skip the chooser, and `prompt`, `max_age` or `login_hint`, which are passed on to the provider (Login hints passed to the provider).
2. The service shows a provider chooser (or redirects straight to the hinted provider).
3. The user signs in at the provider.
4. The provider returns to `/{realm}/callback/{provider}` with a code. The service checks that the provider in the path is the one the stored request was sent to.
5. The service exchanges the code with the provider secret, validates the identity, then finds, links or creates the user. This is the only step that uses a provider secret.
6. The service redirects to the app's `redirect_uri` with a one-time code (valid `tokens.code_lifetime`, 60 seconds by default), the original `state` and `iss` (the realm's issuer, RFC 9207).
7. The app calls `/token` with the code and the PKCE verifier (or client secret for a confidential client).
8. The service returns access, ID and refresh tokens.
9. The app calls the API with the access token; the API verifies it with the JWKS, fetched once and cached.

An app signs in through the system browser session (UC-1), where Sign in with Apple and the other providers are buttons on FeatherAuth's chooser or are reached with the provider hint; on iOS the user therefore sees Apple's web sign-in in the browser tab, not the system's Sign in with Apple sheet.

### Provider chooser

Without a provider hint, `/authorize` shows a minimal page with one button per enabled, non-hidden provider, in the order of `login_page.provider_order` (providers not listed follow), under the realm's `display_name` and `login_page.logo_url` (FR-04, FR-55). When exactly one provider is enabled and not hidden and the request carries no hint, the chooser is skipped and the browser is redirected straight to that provider. A hint (a parameter named in `login.provider_hint_params`) naming an enabled provider, hidden or not, redirects straight to that provider; a hint naming an unknown or disabled provider shows the chooser, and the hint is logged. Each button on the chooser is a link back to the same authorize request with the provider hint added (the first name in `login.provider_hint_params`), keeping every original parameter; the authorization request is stored only when the redirect to the provider is made, so the chooser needs no endpoint of its own. How the buttons are drawn is in Providers (Buttons); the headers and assets of the page are in Browser pages.

### State and the state cookie

`state` and `nonce` are random with at least 128 bits (SEC-08). `state` is checked against the server-side record of the login in progress (`auth_requests`) and bound to the browser by a state cookie per login, whose value is the `state` itself, compared with the `state` parameter in constant time, so that parallel logins in one browser do not overwrite each other. The cookie is named `fa_state_` plus the first 8 hex characters of SHA-256(`state`), with `Path` set to the realm's callback path up to `{provider}` and `Max-Age` set to `tokens.login_timeout`, and it is deleted once used. It is `HttpOnly` and `SameSite=Lax` for every provider, never `SameSite=None`. It is `Secure` because `public_url` is `https` (`require_https`); in local development without HTTPS it drops `Secure` (Apple login needs an `https` return URL, so it is unavailable there anyway). Apple's cross-site `POST` is handled as in Apple's callback, so the cookie is only ever checked on a `GET`. The callback also checks that `{provider}` in its path is the provider the request was sent to (SEC-19).

### Errors during login

If the user cancels at the provider, or the provider returns an error or cannot be reached, the service redirects to the client's `redirect_uri` with `error`, `error_description`, the original `state` and `iss`, using the request's response mode:

| Situation | `error` |
| --- | --- |
| The user cancelled or denied access at the provider | `access_denied` |
| The provider could not be reached, timed out or failed temporarily | `temporarily_unavailable` |
| The login cannot be tied to this browser: the state cookie is missing or does not match, the callback path names another provider, or Apple's handoff id is unknown, used or expired (a login that has completed gets the HTML error page instead, see below) | `access_denied` |
| FeatherAuth refuses the identity: the user is disabled, the realm is disabled, the provider sent no subject, or a provider rule fails (`hosted_domain`, `require_verified_email`, `require_email`) | `access_denied` |
| `max_age` was requested and the provider reports an older `auth_time` | `login_required` |
| Any other provider or internal failure | `server_error` |

The callback handler passes the `error` parameter the provider sent to the adapter in `Callback.Error`, and the adapter's `Exchange` maps it: `access_denied` (for Apple also `user_cancelled_authorize`) gives `ErrCancelled`, and any other provider-sent `error`, including `temporarily_unavailable` and `server_error`, gives an error that is none of the sentinels, so it is a `server_error`. (`temporarily_unavailable` is only for a provider that could not be reached or timed out.) For Apple, `error` is one of the posted values stored under the one-time id, so a cancel reaches `Callback.Error` after the `303`. The error code and description the provider sent are not put into the redirect.

The in-app browser then closes by itself and the app decides what to show. The `state` is echoed whenever the client sent one, because some client libraries ignore an error response without it; a request without `state` gets none. When the request is unknown or has expired, there is nobody safe to redirect to, so the service shows an HTML error page and does not redirect. A login that has already completed gets the same page (Login single use).

### Errors in the authorization request

The authorization request is checked before anything else, in the order below. Until `client_id`, `redirect_uri` and `response_mode` are known to be valid there is nobody safe to redirect to, so those errors show an HTML error page. Every later error redirects to the client with `error`, `error_description`, `state` (when sent) and `iss`, in the request's response mode (OIDC Core 3.1.2.6, RFC 6749 §4.1.2.1).

| Situation | Answer |
| --- | --- |
| `client_id` missing, unknown or repeated; `redirect_uri` missing, repeated or not an exact match | Error page, no redirect |
| `response_mode` other than `query`, `fragment` or `form_post` | Error page, no redirect (the answer cannot be delivered) |
| `response_type` missing, or any other parameter repeated | `invalid_request` |
| `response_type` other than `code` | `unsupported_response_type` |
| `scope` missing or without `openid` | `invalid_scope` |
| `request` present | `request_not_supported` |
| `request_uri` present | `request_uri_not_supported` |
| `prompt=none` combined with another `prompt` value; `max_age` not a whole number of 0 or more | `invalid_request` |
| `code_challenge_method` other than `S256`; a `code_challenge` without `code_challenge_method` (RFC 7636 §4.3 would read that as `plain`, which SEC-01 forbids); a challenge that is not 43 base64url characters | `invalid_request` |
| No `code_challenge` while the client has `require_pkce: true` | `invalid_request` |
| `prompt=none` without a usable browser session (Single sign-on session) | `login_required` (there is no session to reuse); with a usable one, a code |
| A provider hint naming an unknown or disabled provider | Not an error: the chooser is shown and the hint is logged |

A `response_mode` in the request wins; the client's `response_mode` setting is used when the request names none. `display`, `ui_locales`, `claims` and `acr_values` are ignored without error; `id_token_hint` is read only with `prompt=none` (Single sign-on session) and is otherwise ignored.

Details the table leaves open:

- A repeated `response_mode` is an `invalid_request` like any other repeated parameter; since the request names no usable mode, it is answered in the client's `response_mode` setting.
- The `state` is echoed only when the request carries it exactly once; a repeated `state` is an `invalid_request` answered without `state`.
- `max_age` is written in decimal digits only: no sign, space or fraction (`007` is 7). A value too large to be a duration of that many seconds (above 9223372036) is an `invalid_request`; it is not shortened.
- `prompt` is a space-separated list. A value other than `none`, `login`, `select_account` and `consent` is ignored; when more than one of `login`, `select_account` and `consent` is given, the first is passed on to the provider (Login hints passed to the provider).
- A form `POST` is read from its body only (its query string is ignored); a body that cannot be read as a form gets the error page with status `400`.
- A realm with `enabled: false` answers `/authorize` with the error page with status `403`, before the request is read.

## Realms

A realm is an isolated tenant. All state and configuration below is per realm, and nothing is shared between realms except the process and the database.

- **Issuer:** `public_url` followed by the `urls.issuer` path, by default `{prefix}/{realm}` (the prefix is empty by default), so a deployment behind a path prefix issues tokens with the URL its clients actually use. Tokens carry the issuing realm's issuer; an API trusts only the realm it expects.
- **Keys:** each realm has its own signing keys and JWKS.
- **Users:** the same person in two realms is two users with different `sub` values. Email uniqueness and auto-link apply only inside one realm.
- **Providers:** each realm enables its own providers with its own credentials and redirect URIs.
- **Clients:** each client belongs to one realm; `client_id` is unique inside a realm.
- **Settings:** token lifetimes, user data, login page and headers are per realm, and clients can override lifetimes.
- **Routing:** the realm comes from the URL path. An unknown realm is 404 (JSON on API endpoints, HTML on browser endpoints).
- **Lifecycle:** a realm is added, changed or removed by editing its file; no rebuild, no restart.
- **Isolation:** a code, refresh token or access token from one realm MUST be rejected by every other realm.

## Clients

| Setting | Meaning |
| --- | --- |
| `name`, `description` | Display name and a free-text note, for humans and logs only |
| `type` | `public` (no secret) or `confidential` (secret from a file, compared in constant time, never logged or stored in the database). PKCE is required for both |
| `redirect_uris` | Exact match, no wildcards. Mobile: custom scheme (`com.example.app:/callback`), HTTPS app link, or loopback (`http://127.0.0.1:{port}/callback` or `http://[::1]:{port}/callback`; the port may vary, for public clients only, RFC 8252 §7.3). Web: HTTPS URLs. Validated at load (FR-32): a URI with a fragment (RFC 6749 §3.1.2), a wildcard, the scheme `javascript`, `data` or `file`, or `http` on any host but `127.0.0.1` or `[::1]` is rejected, and `http://localhost` is rejected with a hint to use `127.0.0.1` (RFC 8252 §8.3); the same rules apply to `post_logout_redirect_uris` |
| `post_logout_redirect_uris` | Allowed return URLs after logout; defaults to `redirect_uris`. A return URL matches only exactly, also on loopback: the port variance of a public client's loopback `redirect_uris` does not apply to logout |
| `web_origins` | Origins allowed to call `/token`, `/userinfo`, JWKS and discovery from a browser (CORS). Empty for native apps |
| `require_pkce` | Default true. May be set false for a legacy client that cannot send a challenge. For a public client this does not meet RFC 9700 §2.1.1, which requires PKCE for public clients: the code is then protected only by the exact redirect URI match, so an app that claims the same custom scheme can redeem an intercepted code. Use it only as a temporary exception while the app is updated, and keep that client's refresh lifetimes short until it sends a challenge. The effective values (the client's own, else the realm's) must be at most 24 hours for `refresh_idle_lifetime` and above 0 and at most 720 hours for `session_max_lifetime`, or the load rejects the client (FR-32) with the reason `client <id>: a public client with require_pkce: false needs refresh_idle_lifetime of at most 24h`, or `client <id>: a public client with require_pkce: false needs session_max_lifetime above 0 and at most 720h`. A confidential client is not limited. The limit keeps a code intercepted through a custom scheme from becoming a long session (RFC 8252 §8.1) |
| `response_mode` | Used when the request names none; default `query`. `fragment` for browser clients that read the result from the URL fragment. `form_post` optional. A `response_mode` in the request wins |
| `audience` | Value of the `aud` claim in access tokens issued to this client. Set it to the API's own identifier when an API consumes the tokens; the default (the client id) equals the ID token's `aud`, so the API then relies on the `typ` check alone (an accepted risk; `config check` gives no warning for it, because it would fire for every simple setup) |
| Lifetime overrides | `access_token_lifetime`, `refresh_idle_lifetime`, `session_max_lifetime` |
| `refresh_token_rotation` | Confidential clients only: override the realm's rotation setting. Public clients always rotate |
| `allow_account_delete` | Whether this client's access tokens may call `DELETE /account` (default false) |

**Public and confidential clients.** The two types describe whether the app can keep a secret. Code that ships inside an app a user installs or opens (a mobile app, a single-page web app) can be taken apart, so it cannot hold a secret: it is a **public** client and is protected by PKCE instead. Code that runs on a server you control can hold a secret: it is a **confidential** client and proves its identity at `/token` with that secret.

| Use case | Client type | Proves its identity at `/token` by | PKCE |
| --- | --- | --- | --- |
| UC-1 Native mobile app | `public` | `client_id` only (`none`) | Required |
| UC-2 Single-page web app | `public` | `client_id` only (`none`) | Required |
| UC-3 Server-rendered web app or backend for frontend | `confidential` | `client_id` and secret, in the body (`client_secret_post`) or an `Authorization: Basic` header (`client_secret_basic`) | Required |
| UC-4 API that verifies tokens | not a client of FeatherAuth | it only reads the public keys | n/a |

Guidance by platform:

- **iOS and Android:** use the system browser session (ASWebAuthenticationSession, Custom Tabs) through a library such as AppAuth, and an app-claimed HTTPS link where possible, because custom schemes can be claimed by other apps. PKCE protects the code either way.
- **Cross-platform (React Native, Flutter):** the same flow through an AppAuth wrapper or an in-app browser.
- **SPA:** keep tokens in memory; its refresh token always rotates.
- **Server-side web:** use a confidential client; keep tokens on the server.

## Providers

Every provider is one entry in the realm's `providers` map and one adapter behind a common interface. A provider's `type` defaults to its own name; `type: oidc` defines extra providers from config alone. Common options: `enabled`, `hidden`, `display_name`, `scopes`, `trust_email`, `auto_link`, `sync_mode`, `client_id`, `client_secret_file`, and `endpoints` overrides (`authorize`, `token`, `userinfo`, `jwks`).

| | Google | Apple | GitHub | Facebook |
| --- | --- | --- | --- | --- |
| Type | OIDC | OIDC (special client secret) | OAuth2 + API | OAuth2 + API |
| Authorize | Google OIDC discovery | `https://appleid.apple.com/auth/authorize` | `https://github.com/login/oauth/authorize` | `https://www.facebook.com/{version}/dialog/oauth` |
| Token | Google OIDC discovery | `https://appleid.apple.com/auth/token` | `https://github.com/login/oauth/access_token` (`Accept: application/json`) | `GET https://graph.facebook.com/{version}/oauth/access_token` |
| Callback | Redirect with query | **POST form** (`form_post`) | Redirect with query | Redirect with query |
| Client secret | Static file | Generated per request: JWT signed ES256 with the `.p8` key (header `kid` = Key ID; `iss` = Team ID, `sub` = Services ID, `aud` = `https://appleid.apple.com`, `exp` at most 6 months) | Static file | Static file |
| Identity | Validated ID token; with `hosted_domain`, its `hd` claim must equal that domain | The ID token from the token endpoint response, validated (keys at `https://appleid.apple.com/auth/keys`); `sub` stable per user and team | `GET https://api.github.com/user` (with a `User-Agent` header), numeric `id` | `GET {graph}/me?fields=id,name,email&appsecret_proof=...`, `id` |
| Email verified | `email_verified` claim | `email_verified` claim; relay addresses possible | Primary verified address from `GET /user/emails` (scope `user:email`) | Not reported, so never trusted |
| Name | ID token | Only in the `user` field of the first authorization (unsigned, so used for the name only) | `name` | `name` |
| PKCE to provider | Yes | No | Yes (`S256`) | No |
| Defaults | `trust_email: true` | `trust_email: true` | `trust_email: true`, `require_verified_email: true` | `trust_email: false`, no auto-link |

Provider-specific options:

- **Google:** `hosted_domain` (restrict to one Workspace domain). It is sent as the `hd` parameter, which only steers Google's screen, and enforced by checking the ID token's `hd` claim, as Google's documentation requires. The domain is compared case-insensitively. Google's issuer is always `https://accounts.google.com` and is not configurable.
- **Apple:** `scopes` is honoured like any provider's, within the two scopes Apple defines: each value must be `name` or `email`, at most once, and the list may be empty. Anything else is a configuration error at load, at reload and in `config check`, on the line of the value: `providers.<key>.scopes: Apple supports only the scopes name and email`, or for a repeat `providers.<key>.scopes: <value> is listed twice`. The authorize URL carries the values joined by one space in the configured order (`scope=name email` with the default `[name, email]`), and no `scope` parameter when the list is empty; the response mode stays `form_post`. The other Apple options are `team_id`, `key_id`, `private_key_file`, `client_secret_lifetime` (default 5 minutes), `store_refresh_token` (default true, so deletion can revoke it), `notification_audiences` (see Provider account events). With `store_refresh_token`, every login that returns a refresh token seals it (SEC-10) and stores it on that login's identity row, replacing the one stored before; a login that returns none leaves the stored token as it is.
- **GitHub:** `allow_signup`, `require_verified_email`, `pkce`. Every API call carries a fixed `User-Agent` header, which GitHub's API requires. `endpoints.userinfo` replaces the URL of `GET /user`, and `GET /user/emails` keeps its fixed URL; the `authorize` and `token` overrides apply, and `jwks` has no effect.
- **Facebook:** `graph_version`, `flow` (only `oauth`: `oidc` is not supported, Facebook stays on the `oauth` flow, and load, reload and `config check` reject any other value on `providers.<key>.flow` with the message `"<value>" is not supported (pending confirmation against Meta's documentation); use oauth`), `fields`, `require_email`. Every Graph call carries `appsecret_proof` (HMAC-SHA256 of the access token, keyed with the app secret), so the Meta app can have "Require App Secret" on.
- **Generic `oidc`:** `issuer` (discovery derived from it). Any OpenID Connect provider with a single issuer needs only config; a multi-tenant issuer (such as Microsoft Entra's `common` endpoint, whose ID tokens carry a per-tenant `iss`) is not supported. A missing `email_verified` claim means unverified, and `trust_email` defaults to `false`. For `google` and generic `oidc` providers `openid` is always requested: it is added to the configured `scopes` when missing. The adapter authenticates at the token endpoint with `client_secret_basic` and takes the identity from the ID token; a user-info call is made only when `endpoints.userinfo` is set (see User-info call). It fetches the discovery document when it is built; what happens when that fails is for the registry to decide.

**Buttons (FR-55).** The chooser draws each built-in provider's button by that provider's branding rules (Google's Sign in with Google branding guidelines, Apple's Human Interface Guidelines for Sign in with Apple, and Meta's and GitHub's brand guidelines), with the logos built into the binary and served from the assets path. `login_page.accent_color` applies only to the page itself and to generic providers. The button text is "Sign in with {name}" (message id `chooser.sign_in_with`), and the Facebook button says "Log in with {name}" (message id `chooser.log_in_with`), which is how Meta's login guidelines word it; `{name}` is the provider's `display_name`. All buttons have the same size and appear without scrolling on a phone screen, and the mark of the Apple logo is drawn at least as tall as the 20 px marks of the GitHub and Facebook buttons (the bundled Apple image has its mark inside a larger square, so the image is drawn larger and the button clips it). App Store Review Guideline 4.8 requires an iOS app that offers a third-party login such as Google, Facebook or GitHub to also offer Sign in with Apple or an equivalent; `config check` warns when a realm has a public client with a custom-scheme redirect URI and one of those providers enabled, but Apple disabled or `hidden`.

**Provider calls.** Every call FeatherAuth makes to a provider (the code exchange, the user-info call, key fetches) uses the provider's `timeout` (default `10s`, covering connecting and waiting for the response). The single-use code exchange is never retried, because the code cannot be used twice. **Provider key cache (SEC-03).** A provider's signing keys (its JWKS, and for Google's security events the keys its RISC configuration names) are cached; they are fetched again only for a token whose `kid` is not among the cached keys, and a failed fetch is retried once. A provider whose discovery document cannot be fetched when its configuration is loaded does not make the configuration invalid: the provider stays listed, discovery is retried on use (at most once every 30 seconds, a fixed interval that is not an option), and while it fails a login through that provider ends with `temporarily_unavailable`. A timeout, a transport failure or a `5xx` answer from the provider is a failure that redirects the user to the client with `temporarily_unavailable` (see Errors during login); a `4xx` answer or any other error from the token endpoint is a `server_error`. The time a user takes at the provider is a different limit, `tokens.login_timeout`. No call to a provider follows an HTTP redirect: every client of a provider adapter refuses one, so a `3xx` answer from the discovery, token, key, user-info, revoke, Graph or GitHub API call is the answer, and it is a failure of that call handled as a `4xx` answer is (above), or, from discovery and the key endpoint, as an unreachable provider. A provider ID token from the web flow is accepted only when its `azp` claim, if present, equals our client id, and a token with more than one `aud` value must have an `azp` claim (OIDC Core 3.1.3.7, rules 3 to 5); an `azp` that is not a string is refused. The registry's warnings pass the error under `err`, so the logger cleans any URL in it (SEC-13).

**User-info call.** For a generic `oidc` or `google` provider, FeatherAuth calls the provider's user-info endpoint only when `endpoints.userinfo` is set; an endpoint found by discovery is never called. The call is made after the ID token is validated, with the access token from the token response and the provider's own client and `timeout`. It fills only the claims the ID token lacks (`email`, `email_verified` and `name`) and never replaces an ID token claim, and `email_verified` counts only when it is the JSON boolean `true`. A claim the ID token carries with the wrong type, or empty, counts as lacking (for `email` and `name`); `email_verified` from the user-info answer is used only when the ID token has no `email_verified` claim at all, and only when the user-info answer's email is the identity's email. If the token response has no access token, the call cannot be made and the login fails with a `server_error`. Its `sub` must equal the ID token's, otherwise the login is refused (`access_denied`). A timeout, a transport failure or a `5xx` answer is `temporarily_unavailable`, and any other failure is a `server_error`. Apple has no user-info endpoint and ignores the option. For GitHub the override replaces the URL of `GET /user` (`GET /user/emails` keeps its fixed URL), and for Facebook the URL of `GET /me`; each is still that provider's one identity call.

**Login hints passed to the provider.** A client's `prompt`, `max_age` and `login_hint` are passed on to the provider where it has an equivalent (OIDC Core 3.1.2.1), unless the single sign-on browser session answers the request (Single sign-on session: use and end). Without this, a user could never switch accounts after logout, because the system browser keeps the provider's session.

| Request | Google | Apple | GitHub | Facebook | Generic `oidc` |
| --- | --- | --- | --- | --- | --- |
| `prompt=login`, or `max_age` | `prompt=select_account` (Google has no forced re-login) | nothing (Apple's web sign-in always asks the user to confirm) | `prompt=select_account` | `auth_type=reauthenticate` | `prompt=login` and `max_age` passed on |
| `prompt=select_account` | `prompt=select_account` | nothing | `prompt=select_account` | nothing | passed on |
| `prompt=consent` | `prompt=consent` | nothing | nothing | nothing | passed on |
| `login_hint` | `login_hint` | nothing | nothing | nothing | passed on |

For Google, a request with `prompt=consent` and a `max_age` is sent as the space-separated `prompt=select_account consent` (OIDC Core 3.1.2.1 allows several values), because `max_age` alone becomes `prompt=select_account` and `prompt` carries one value in the request.

`auth_time` in FeatherAuth's tokens is the provider ID token's `auth_time` when it has one, otherwise the time the callback completed, which is the last time the user acted at the provider. When the request carried `max_age` and the provider reports an `auth_time` older than that, the login fails with `login_required`. A provider's `auth_time` is the time the user last signed in there. Without one, a recent `auth_time` proves only that the user went through the provider again in this browser: where the table above maps `prompt=login` to an account choice or to nothing (Google, Apple, GitHub), a person holding that unlocked browser passes with a tap and enters no credentials.

Apple details follow Apple's documentation ("Request an authorization to the Sign in with Apple server" and "Processing changes for Sign in with Apple accounts"): `response_mode` is `form_post` when scopes are requested; the return URL is `https` with a domain name (no IP address, `localhost` or fragment); the success fields are `code`, `id_token`, `state` and `user`, the error fields `error` and `state`; the only error code of the web flow is `user_cancelled_authorize`, the error Apple returns when the user cancels (a real cancelled login posted it); Apple's `code` is valid five minutes. Facebook's `flow: oidc` variant is not supported, and Facebook stays on the `oauth` flow (Providers). The `graph_version` default is `v26.0`; Meta retires old versions, so the default is checked against Meta's documentation once a year. Two adapter rules guard against known Apple quirks: `email_verified` and `is_private_email` in the ID token are accepted as either a boolean or the strings `"true"` and `"false"`, and the name arrives only in the `user` field of the first authorization, so it is stored then (`keep_name_if_missing`).

### Apple's callback (form POST)

Apple returns the result with a cross-site `POST`, and a `SameSite=Lax` cookie is not sent on that. So the service does not check the cookie on the `POST`:

1. On the `POST` to the callback path, it looks up the login of the posted `state`. Only a login in progress (not expired, of this realm) whose provider is the provider of the path, and that provider returns by form `POST` (Apple), has its values stored: the posted values (`code`, `id_token`, `state`, `user` and `error`, but not `error_description`) go server-side under a random one-time id (128 bits, valid 60 seconds), and the answer is `303 See Other` to `GET <callback path>/continue?id=<id>&state=<state>`, with the posted `state`. In every other case nothing is stored and the answer is the HTML error page for an unknown or expired request (status `400`). A login has at most one handoff (a unique index on `callback_handoffs.auth_request_id`): a second `POST` for the same login replaces the first, whose id stops working.
2. On that `GET` the browser sends the `Lax` state cookie. The service checks the cookie and the `state` parameter as for any other provider, takes the stored values (the id is single-use; their `state` must equal the parameter), and continues the login. The `state` in the URL is what lets every failure below find the login and redirect to the client.
3. A `GET` to `continue` with an unknown, used or expired id, or without the cookie, is answered by an `access_denied` error redirect as in Errors during login. When the login of its `state` has already completed, the answer is instead the HTML error page for an unknown or expired request (status `400`), whatever the id (Login single use).

The id carries no token and is useless without the cookie. This was tested in Chromium, Firefox and Safari (macOS, and iOS in the Simulator), and with real Apple logins in Safari and Firefox: a `Lax` cookie is not sent on the cross-site `POST` and is sent on the `GET` after the `303`. `/authorize` with a provider hint still stores one login row for each request; the rate limit and the hourly job bound that.

The posted values are not trusted on their own. The adapter exchanges the posted `code` and validates the ID token from Apple's token endpoint, a server-to-server call authenticated with the client secret; if it also reads the posted `id_token`, that one must have the same `sub`. The `user` JSON is unsigned, so it supplies only the name, and only when the user is created; the email always comes from the ID token.

### Provider account events

Apple sends server-to-server notifications about a user's Apple account to the URL registered for the app in the Apple Developer account. That URL is `urls.endpoints.provider_events` with `{provider}` set to `apple`. Apple posts JSON whose `payload` field is a JWT signed by Apple. The service verifies it with Apple's keys, requires `iss` to be `https://appleid.apple.com` and `aud` to be the provider's `client_id` or one of its `notification_audiences`, requires an `exp` that has not passed when the payload has one (a payload without one is checked as described below), and then acts on the event. The `events` claim is a JSON object or a string that holds that JSON:

| Event | Action |
| --- | --- |
| `consent-revoked` (the user stopped using Sign in with Apple for this app) | Revoke every session of the user who holds that Apple identity and drop the stored Apple refresh token. The user and their `sub` stay, so a later Apple login returns to the same account |
| `account-delete` (the Apple account was deleted; Apple's documentation names it `account-deleted`, and both names get this action) | If Apple is the user's only identity, delete the user as `DELETE /account` does (without the Apple revoke); otherwise unlink the Apple identity and revoke the user's sessions |
| `email-disabled`, `email-enabled` (relay forwarding changed) | Logged; nothing else changes |

An unknown subject or event type is answered `200` and logged, so Apple does not retry; a payload that fails verification gets `400`, and one whose keys cannot be fetched gets `503`, so that Apple sends it again. A provider that is not enabled or has no account events gets `404`, and a change that fails in the store gets `500`, so that the provider retries. A provider event is acted on once (SEC-27). Every verified event is remembered in `provider_event_ids` in the same transaction as its action, under its `jti` or, when it has none, under the SHA-256 of the payload's `payload` field. A remembered id is kept until the payload's `exp`; a payload without `exp` keeps it for 24 hours from the later of its `iat` and the time it is received. A payload whose id is remembered is answered `200`, logged, and changes nothing, and an action that fails remembers nothing, so the provider's retry is acted on. A repeated `consent-revoked` for a known user therefore writes no second `identity.consent_revoked` row, while a second notification with its own `jti` writes one more. A repeated `account-delete` finds no user, is answered `200` and logged, and writes no audit row. Every action is written to the audit log. A session that the event revokes is one of the revocations that queue a back-channel logout token (Back-channel logout), so an app whose client has `backchannel_logout_uri` is told. Otherwise its access tokens end as in SEC-14, and the app's own records stay until the app removes them.

Apple's documented notification and the notifications Apple really sends differ in form, and each form is accepted. The `events` claim may be a JSON object (the documented samples) or a string that holds that JSON (the real notifications). The deletion event is `account-deleted` in the documentation, and `account-delete` is accepted too; both get the same action. The documented samples carry `iat` and `jti` and no `exp`, while a real notification carried all three: a payload without `exp` is accepted when its `iat` is at most 24 hours old and at most 5 minutes ahead, and a payload with `exp` is checked as above. Apple's `aud` in the samples is the app's identifier, which `notification_audiences` covers. The notification is a signed JWS whose `alg` is checked; `is_private_email` is a string in the samples and is read as either form (above).

Meta requires a live app to offer data deletion. Each realm serves a data-deletion instructions page (`urls.endpoints.data_deletion`), which tells the user to delete the account in the app or to write to `login_page.contact`; its URL is entered in the Meta app settings. Google's Cross-Account Protection events are received at the same path (Google Cross-Account Protection).

**Meta's data-deletion callback (FR-40, SEC-33).** Meta posts a form with one field, `signed_request`, to the URL entered in the Meta app; that URL is the provider events path with `{provider}` set to the Facebook provider's key. The value is two base64url parts joined by a `.`: a signature and a JSON payload. The body must be a form (whatever its content type) with exactly one non-empty `signed_request`, and the value must be exactly two non-empty parts; the parts may carry `=` padding, so a signature re-encoded with padding is accepted, and the payload part is always used exactly as received. The signature is checked before anything of the payload is used. The service checks that the payload's `algorithm` is `HMAC-SHA256`, that the signature is the HMAC-SHA256 of the payload part exactly as received, keyed with the provider's client secret (compared in constant time), and that `issued_at` (a number of seconds) is at most 1 hour old and not more than 5 minutes ahead (exactly 1 hour and exactly 5 minutes are accepted); the payload must be a JSON object and its `user_id` a non-empty string. A request that fails any of this gets `400` `invalid_request`. A request is acted on once: the SHA-256 of its payload part is remembered until 1 hour after the later of its `issued_at` and the time it is received (as for Apple's notifications without an `exp`) in `provider_event_ids`, in the same transaction as the action, and a repeat changes nothing and gets the same answer with a new code. The payload's `user_id` is the Facebook subject: if Facebook is the user's only identity the user is deleted as `DELETE /account` does, otherwise the Facebook identity is unlinked and the user's sessions are revoked, with the audit rows of Apple's `account-delete` (actor `provider:<key>`). An unknown subject changes nothing. For a request that verifies, the answer is `200` (a store failure is `500` and remembers nothing) with the JSON `{"url": "<data-deletion page URL>?code=<code>", "confirmation_code": "<code>"}`, where the code is 22 random letters and digits (Meta asks for an alphanumeric code). Every answer of the endpoint to such a request, the `200` included, carries `Cache-Control: no-store` and `Pragma: no-cache`, and the `200` has `Content-Type: application/json`. Nothing of the request (the `signed_request`, its parts, the `user_id`) or the client secret is ever logged; the service writes the usual line of an event, naming only the provider and the event. The deletion is finished before the answer is sent, so the data-deletion page, when opened with one `code` parameter of exactly 22 ASCII letters and digits, adds one sentence saying that deletion requests are carried out at once and showing the code; it keeps no record of codes, and a `code` of another form, or a repeated one, is ignored. The page stays the instructions page for users. This is Meta's documented format: a `POST` with `signed_request`, the HMAC-SHA256 of the encoded payload under the app secret, the payload fields `algorithm`, `issued_at`, `expires` and `user_id`, and the JSON answer with `url` and `confirmation_code`. Meta requires the callback URL to be `https`.

### Email rules

Email decides whether two logins are the same person, so the rules are fixed:

- **Comparison:** emails are compared after trimming and lowercasing, nothing provider-specific (no dot or plus-address handling). The normalised value is stored in `users.email_key`; `users.email` keeps the value as the provider sent it.
- **One verified user per email:** within a realm, at most one user may hold a given verified email (a unique partial index on `realm_id` and `email_key` where `email_verified` is true). Users with unverified, relay or missing emails may share a value or have none.
- **Auto-link:** a new identity is linked to an existing user only when all of these hold (SEC-04): the provider has `trust_email: true` and `auto_link: true`, it reports the email verified, a user with that verified email exists, and the email's domain is in `user_data.auto_link_domains`. That list holds mailbox domains whose addresses are never given to another person (default `gmail.com`, `googlemail.com`, `icloud.com`, `me.com`, `mac.com`). A company domain is not on it by default, because a company can give a former employee's address to a new one, and providers keep an address marked verified after its owner changed: Google documents this for addresses outside Gmail and Workspace, and GitHub keeps addresses verified indefinitely. Linking on such an address would join one person's login to another person's account. An operator may add their own domain once they accept that risk. Each auto-link is written to the audit log. In every other case the login behaves as with `auto_link: false`.
- **New user, email already held:** if no link happens (for example `auto_link: false`) but another user already holds the verified email, the new user is created with `email_verified` false so the one-verified-user rule holds.
- **Email change at the provider:** the identity row is updated at every login. The user's email changes only with `sync_mode: force`; if the new email is held by another verified user, the old email is kept and the conflict is logged. A provider that sends no email never blanks the stored one.
- **Apple's private relay and one person with several providers:** accounts are joined across providers only by a verified email on an auto-link domain. Apple's private relay address never equals another provider's email, so a person who signs in with Apple and with another provider gets two accounts. The same Apple user always returns to the same account, because Apple's `sub` is stable per user and developer team (to be checked against Apple's current documentation). An operator can merge two accounts by hand with the CLI's `user link` command; account linking by the user is not offered (it is on the roadmap of REQUIREMENTS.md).

### Provider decisions

- **Facebook stays on the `oauth` flow.** Meta's OpenID Connect token for apps (Limited Login) is a provider SDK login, which the web-flow-only rule leaves out, and Meta's OpenID Connect code flow for the web is marked "still in testing" in its documentation and is missing from its discovery document. `flow` has the one value `oauth`.
- **Google Cross-Account Protection (FR-48, SEC-39).** Google sends security event tokens (RFC 8417) about a user's Google account to a receiver URL; that URL is the provider events path with `{provider}` set to a Google provider's key. The body is the token itself; the content type is not checked, because Google's documentation names none. The service verifies it with the keys and the issuer that Google's RISC configuration document names (the issuer of that document, compared by the issuer rule below; it is not the ID token issuer), fetched with the provider's `timeout` and cached by the provider key cache rule (Provider calls). The document's URL is Google's by default and set by the provider option `endpoints.risc_configuration` (Google only). It requires `aud` to contain the provider's `client_id`, refuses a token whose `iat` is more than 24 hours old or more than 5 minutes ahead, and acts on each event in `events` whose `subject` has `subject_type` `iss-sub` and the issuer of the document:

  | Event (last part of its URI) | Action |
  | --- | --- |
  | `sessions-revoked`, `tokens-revoked`, `account-disabled` (whatever its `reason`) | Revoke every session of the user who holds that Google identity, and delete their browser sessions; the user and the identity stay |
  | `token-revoked` (its subject is a token, not a user), `account-enabled`, `account-credential-change-required` | Logged; nothing else changes (FeatherAuth stores no Google token) |
  | `verification` | Logged with its `state` |

  The answer is `202` for a token that verifies (also for an unknown subject or event type, which is logged), `400` for one that does not, `503` when the keys cannot be fetched, `500` when the store fails. Tokens are acted on once by `jti` (SEC-27), remembered for 24 hours when the token has no `exp` (the `iat` limit makes that enough). Google's deliveries come under the rate limit of the provider events path like any caller. Each revocation that ended at least one session writes the audit row `identity.sessions_revoked` (actor `provider:<key>`, details `{provider, event}`). Registering the receiver URL and the event types with Google's RISC API is an operator task with a service account; the user guide gives the commands. Checked against Google's documentation: the configuration document's URL, the `POST` of the token to the receiver, the answers `202` and `400`, the claims `iss`, `aud` (one of the project's client ids), `iat`, `jti` and `events` with no `exp`, the seven event types of the table, the `iss-sub` subject, and the registration through the RISC API with a service account that has the RISC Configuration Admin role (`stream:update`, and `stream:verify` with a `state` for the verification event). Google sends no events for Google Workspace users. Further rules: only `RS256` is accepted; **the issuer rule (FR-48):** two issuers match when each, after removing one trailing `/` if it has one, gives the same text, that text is not empty, and that text does not itself end in `/`. So two trailing slashes never match, and nothing else is normalised (not the case, the scheme, a space or a path). With the document's `https://accounts.google.com`, the `iss` values `https://accounts.google.com` and `https://accounts.google.com/` are accepted, and `https://accounts.google.com//`, `HTTPS://accounts.google.com`, `https://Accounts.google.com`, `http://accounts.google.com`, `accounts.google.com` (the variant without a scheme that go-oidc allows for Google's own issuer), `https://accounts.google.com/x`, ` https://accounts.google.com`, `https://accounts.google.com ` and an empty `iss` are refused with `400`. With a document issuer `https://accounts.google.com/`, the `iss` values `https://accounts.google.com` and `https://accounts.google.com/` are accepted and `https://accounts.google.com//` is refused. A document issuer that is empty, `/`, or ends in `//` matches nothing, so every event is refused with `400` until the document is fixed. The same rule compares the issuer inside each event's `iss-sub` subject with the document's issuer, so an event whose subject issuer has or lacks one trailing slash is acted on; those two comparisons are the only ones relaxed, and every other check of the token (signature, `aud`, `iat`, `jti`, the subject's `subject_type` and `sub`) is unchanged; the token needs a non-empty `jti` and an `iat`, and a token without either is `400`; `events` must be a JSON object whose members are JSON objects, and an empty object is accepted and acts on nothing; an event whose subject is not `iss-sub` with that issuer has no subject, so it is logged as an unknown subject and never acted on; a token is remembered until the later of its `iat` and the time it is received, plus 24 hours (the rule of Apple's payloads without `exp`), so that a token with an `iat` ahead of the clock is remembered as long as it is accepted; the configuration document is read once and then kept, and a document that cannot be read, that has no string `issuer`, or whose `jwks_uri` is missing or empty, gives `503` (an `issuer` that is present but empty is kept, matches nothing by the issuer rule, and so gives `400`) and is read again at the next event; a `verification` event is logged with its `state` under the key `verification_state`.
- **Page language (FR-57).** A page is shown in the language of the browser's `Accept-Language` header that is among the realm's `login_page.supported_locales`, otherwise in `login_page.default_locale` (`en` unless set). A message missing from a translation falls back to English. Translation files are reloaded with the configuration, so a language added by a file applies without a restart.
- **Indonesian (FR-50).** The binary ships a translation of every message id for `id` (Indonesian) besides `en`. `login_page.supported_locales` has the default `[en]`; listing `id` turns it on with no file. A file `locales/<code>.yaml` in the config directory adds a language, or replaces single messages of a built-in one (an id missing there falls back to the built-in translation of that language, then to English). The provider button texts in Indonesian follow each provider's own published wording for that language where it has one. A test fails when the built-in `id` translation lacks a message id.

## Tokens and claims

**Access token** (JWT following RFC 9068, default 15 minutes): header `typ: at+jwt`, signed with `tokens.algorithm`; claims `iss`, `sub`, `aud`, `client_id` and `azp` (both the client id), `exp`, `iat`, `jti`, `auth_time`, `sid` (session id), `scope`, `nonce` (when sent), plus the user claims selected by `user_data.access_token_claims` when it is set, else by `user_data.claims` (default `name`, `email`, `email_verified`, `preferred_username`).

**ID token:** header `typ: JWT`, always signed `RS256` (OpenID Connect Discovery requires every provider to support it, and some libraries accept nothing else by default); claims `iss`, `sub`, `aud` (client id), `exp`, `iat`, `auth_time`, `sid`, `nonce` (when sent), `at_hash`, plus the same user claims. `exp` is the issue time plus the client's access token lifetime.

**Refresh token:** a server-side record (a 256-bit random secret stored hashed), rotated on every use (always for public clients, and for confidential clients unless `refresh_token_rotation` is off); reuse after a short grace window revokes the whole session. The value handed to the client has the format set by `tokens.refresh_token_format`: `opaque` (default; the random secret itself) or `jwt`, for clients that decode it: a JWT with header `typ: refresh+jwt`, signed with `tokens.algorithm`, with `aud` set to the realm's issuer so that no API accepts it as an access token, and the claims `iss`, `sub`, `azp`, `exp`, `iat`, `jti`, `sid`, `nonce` (when sent) and `typ: Refresh`. Validity is always decided from the server-side record, never from the JWT alone.

**Token types are not interchangeable.** An API (UC-4) and FeatherAuth's own bearer endpoints (`/userinfo`, `DELETE /account`, the sessions path, bearer `POST /logout`) accept a token only when its header is `typ: at+jwt`, and a bound one only under the scheme `DPoP` with a valid proof (DPoP). An ID token (`typ: JWT`) and a JWT refresh token (`typ: refresh+jwt`, `aud` the issuer) fail that check, so neither can be used as an access token, and the bound in SEC-14 holds. There is no token-introspection endpoint (a non-goal of REQUIREMENTS.md); an app or API that needs an online check calls `/userinfo`, which looks the user up and so refuses the token of a deleted or disabled user at once (SEC-14).

**Bearer endpoint answers.** A request to a bearer endpoint with no `Authorization` header, more than one, a header that is not of the form `Bearer <token>`, or another scheme gets `401` with `WWW-Authenticate: Bearer error="invalid_token"` (RFC 6750 §3), the same answer as an invalid token; the scheme name is matched without regard to case (RFC 7235 §2.1). A failure of the store is never `invalid_token`: an outage gets `503` `temporarily_unavailable`, any other store error `500` `server_error`, so that a client does not treat a transient fault as a revoked token.

**Account deletion (FR-13, SEC-21).** `DELETE /account` accepts only a bearer access token (`typ: at+jwt`) whose `azp` is a client with `allow_account_delete: true` (otherwise `403` with `WWW-Authenticate: Bearer error="insufficient_scope"`) and whose `auth_time` is no older than `tokens.account_delete_max_auth_age` (otherwise `401` with `WWW-Authenticate: Bearer error="insufficient_user_authentication", max_age=<seconds>`, RFC 9470, so the app signs the user in again with `max_age` or `prompt=login` and retries). It then looks the user up (a missing or disabled user gets `401` with `error="invalid_token"`), deletes the user, identities and refresh tokens, revokes a stored Apple token at Apple, and answers `204`. A second call with the same token therefore gets `401`. A recent sign-in is only as strong as the provider's re-authentication (Login hints passed to the provider), so the guides tell apps to ask the user to confirm the deletion in their own interface as well.

**Userinfo and CORS.** The `Origin` of a `/userinfo` request is checked against the `web_origins` of the access token's `azp` client. An origin that does not match is not refused: the claims are served as usual, without `Access-Control-Allow-Origin` (so a browser does not hand them to the page), and with `Vary: Origin`. A token whose `azp` client was removed from the realm since it was issued still gets its claims, with no `Access-Control-Allow-Origin` and without the `allowed-origins` claim. A `401` for an invalid token carries no `Access-Control-Allow-Origin`.

FeatherAuth checks a token in this order: the header `typ` (a missing `typ` is the wrong type), then `iss`, which must equal the realm's issuer, then the signature, then `exp`. A token without a numeric `exp` is expired. An ID token hint's `exp` is not read. A token with another realm's `iss` is refused as a token of another realm before its signature is looked at. A token whose `kid` is missing or not a key of the realm (so also a token signed by another realm's key that carries this realm's `iss`), whose `alg` is `none`, or whose `alg` is not the one allowed for that token fails the signature check. An access token is accepted only with the realm's `tokens.algorithm`, and an ID token hint only with `RS256`. FeatherAuth's own check does not look at `aud`; an API checks it (UC-4).

**Sessions and refresh rotation.**

- **Session:** a login creates a session. Its id is generated when the login code is issued, stored with the code, and copied to every refresh token of that login (`refresh_tokens.session_id`). The same value is the `sid` claim in tokens. `session_started_at`, `auth_time` and the request's `nonce` are stored with the code and copied the same way, so refreshed tokens carry the original `auth_time` and `nonce` (OIDC Core 12.2 keeps `iss`, `sub`, `aud` and `auth_time` of the original ID token).
- **Rotation and reuse:** public clients always rotate (RFC 9700 §4.14.2); confidential clients follow `refresh_token_rotation`. Inside `refresh_reuse_grace`, an already-rotated refresh token none of whose successors has been used yields another fresh successor each time it is presented, so a retry after a lost response and two refreshes sent at once with the same token both succeed. These successors all stay valid until one of them is used; that use revokes every other refresh token of the session, so from then on only one refresh token of the session is active. After the grace window, presenting an already-rotated token revokes the whole session. The window starts when the token was first rotated (the creation of its first successor) and is checked before the token's own expiry: it exists for retries after a lost response, so it depends on neither the expiry of the rotated token nor that of its first successor, and an expired rotated token still inside the window gets a successor.
- **Binding:** a refresh token works only for the client it was issued to (`refresh_tokens.client_id`), and a confidential client authenticates on every refresh. A disabled user, a removed client or a disabled realm gets `invalid_grant`. For a removed client, `invalid_grant` is what another client presenting its token gets; a request that names the removed client itself fails client authentication with `invalid_client` (an unknown client).
- **Login single use (SEC-28).** The login in progress (its `auth_requests` row) is deleted in the transaction that creates its login code, and that transaction creates no code when the delete removes no row. So a `state` completes at most one login: of two callbacks for one login at the same instant, the one that deletes the row issues the code, and the other gets the HTML error page for an unknown or expired request (status `400`) and no code. A later callback with the same `state`, and a replayed Apple handoff of a completed login, get that page too. A login that failed keeps its row until it expires, so a replayed Apple handoff of a failed login still gets `access_denied`.
- **Code reuse:** a second use of a login code fails with `invalid_grant` and revokes the session created from it (RFC 6749 §4.1.2).
- **Reuse is recorded (SEC-25).** A reused refresh token or login code is refused as above, and the revocation it causes ends the session's refresh tokens that were not revoked before (an expired one that is not revoked counts, as `SessionLive` counts it). When that ends at least one, the service logs a warning with the user id, the client, the session id and `kind` (`refresh_token` or `code`), and writes one `audit_events` row: action `session.reuse_detected`, actor `system`, the user id, details `{client, session, kind}`. The client is the one the session belongs to, whichever client presented the token. The row is written in its own transaction after the revocation has committed; if it cannot be written, the failure is logged as an error and the refusal is still given. When the revocation ends nothing (the session was already revoked, by an earlier reuse or by a logout), the service logs an information line and writes no row, so a client that refreshes after logout raises no alarm and the holder of a stale token cannot grow the audit table. A failed client authentication of a known confidential client (a wrong or missing secret, at the token endpoint or at the logout path with `refresh_token`) is logged as a warning with the client id, and writes no audit row. The logs and the rows never hold a token, a code or a secret.
- **Rotation off:** for a confidential client with `refresh_token_rotation: false`, each use keeps the same token and moves its expiry forward by the Expiry rule below (with the `jwt` format the same JWT is returned, so its `exp` claim stays the original one; validity is decided from the stored expiry).
- **Reuse after a successor was used:** a rotated token presented inside the grace window after one of its successors has already been used counts as reuse and revokes the session, as it would after the window. So does presenting a successor that was revoked because another successor was used: only a copy that is no longer current can be presented, so it is treated like a stolen one. (Presenting any other revoked token, for example after logout, is `invalid_grant`; its session is already revoked.)
- **Expiry:** a new refresh token expires at the earlier of now plus `refresh_idle_lifetime` and `session_started_at` plus `session_max_lifetime`; a `session_max_lifetime` of `0` means no cap.
- **Ending a session (logout):** no cookie identifies a session at logout; the request itself must name it. The logout path accepts GET and form POST, as RP-Initiated Logout 1.0 requires, and three kinds of request:
  1. **RP-initiated logout** (GET query or POST form): `id_token_hint`, `post_logout_redirect_uri` (or another name in `logout.redirect_params`), `client_id` and `state`, all optional; `ui_locales` and `logout_hint` are ignored. The hint's signature is checked against the realm's keys, including verify-only keys; an expired ID token is accepted; its `sid` names the session and its `aud` the client. A `client_id` sent with it must equal that `aud`. The session is revoked and the browser is redirected to the return URL with `state`, when the URL is registered for that client. The POST form keeps the ID token out of URLs and proxy logs.
  2. `POST <logout path>` with `refresh_token=<token>` in the body, sent by the app from its own code, with `client_id` (public client) or client authentication (confidential client) matching the token's client.
  3. `POST <logout path>` with `Authorization: Bearer <access token>` (`typ: at+jwt`): its `sid` names the session, so a client or an API holding the token can end the session without the refresh token. With the form field `all_sessions=true` it ends every session of the token's user instead, and with the form field `session=<id>` it ends that one session of the token's user; see Sign out everywhere and Sessions of the signed-in user below.

  Any of the three revokes the whole session, so its refresh tokens stop working at once; the access tokens already issued stay valid until they expire (SEC-14). The other cases:
  - A hint that fails verification (bad signature, another realm, not an ID token), a `client_id` that does not match the hint, or a return URL that is not registered: an error page, nothing revoked, no redirect.
  - No hint but a `client_id`: the return URL must be registered for that client; the browser is redirected and nothing is revoked, because nothing identifies the session.
  - Neither a hint nor a `client_id`: nothing is revoked, and the browser is redirected only when the return URL arrived in a legacy parameter (a name in `logout.redirect_params` other than the standard `post_logout_redirect_uri`) and is registered as a post-logout URI of a client in the realm; an unregistered one gets the error page. A return URL in `post_logout_redirect_uri` is not redirected in this case, because RP-Initiated Logout 1.0 does not confirm the target without a hint or a `client_id`: the signed-out page is shown. When the request carries `post_logout_redirect_uri` and a legacy parameter, the standard parameter counts and the legacy one is ignored, so there is no redirect. A client that sends only a legacy parameter, such as an older release of an app that used a library's browser logout (`redirect_uri`), is in the redirect case; its session ends at the session lifetime.
  - No return URL: a short page saying the user is signed out (GET or form POST), or `204` for the app requests 2 and 3.

  Details the cases leave open:
  - **Which kind a request is.** A `POST` with a non-empty `refresh_token` field is request 2. Otherwise a `POST` whose `Authorization` header uses the scheme `Bearer` (case-insensitive), or `DPoP` (DPoP), is request 3. Any other request, including every `GET` and a `POST` with another scheme such as `Basic`, is request 1. An empty value (`refresh_token=`, `id_token_hint=`, `client_id=`, a return URL or `state`) counts as absent everywhere.
  - **Repeats.** A repeated `id_token_hint`, `client_id`, `state` or return URL parameter (any name in `logout.redirect_params`) is refused like the cases above: the error page with status `400`, nothing revoked. A repeated `refresh_token` gets `400` `invalid_request`, nothing revoked. A repeated `client_id` in request 2 gets `400` `invalid_request` from client authentication (as at the token endpoint).
  - **Request 2.** The token's session is revoked even when the token has expired, was rotated or was already revoked (the answer is `204` again). A token that is unknown, or was issued to another client, gets `400` `invalid_grant` and nothing is revoked; the two cases look the same. Client authentication failures are answered as at the token endpoint. The token is looked up in a read transaction, and a write transaction starts only when the token is known, belongs to the client and its session still has a refresh token that is not revoked (SEC-34): a made-up token, another client's token and a token of a revoked session write nothing, and their answers do not change.
  - **Redirect.** The answer is a `302` to the registered URL with `state` added as a query parameter, joined with `&` when the URL already has a query; without `state` the URL is used as registered.
  - **Realm and records.** A realm with `enabled: false` does not block logout. A logout writes one information line to the service log and no `audit_events` row.
  - **Store failure.** When the store fails, nothing is revoked or redirected: an unavailable store gets `503` (`temporarily_unavailable` for requests 2 and 3, the error page for request 1), any other failure `500` (`server_error`, or the error page).

  A request with a hint can be triggered by another site that holds an ID token, which is accepted: the redirect goes only to a registered URI and the ID token is already a credential of that user. FeatherAuth ends its own browser session (Single sign-on session: use and end) and no provider session, so RP-Initiated Logout's question "log out of the OP as well?" has nothing to ask about and is not shown.

- **Sign out everywhere (FR-39).** The bearer logout (`POST <logout path>` with `Authorization: Bearer`, request 3 of Ending a session) accepts a form field `all_sessions`. With `all_sessions=true` it revokes every session of the token's user in the realm, of every client, and answers `204`. That is allowed only when the token's `azp` client has the option `allow_session_management: true` (Sessions of the signed-in user, below); otherwise `403` with `WWW-Authenticate: Bearer error="insufficient_scope"` and nothing is revoked. A value other than `true` is `400` `invalid_request`, and so is a repeated `all_sessions` field; with an empty or absent field the request ends only the session the token's `sid` names. The checks run in this order: the bearer token (`401` `invalid_token`, also for a disabled user), the value of the field (`400`), then the option (`403`); so a bad value is `400` from any client. A client removed since the token was issued counts as without the option. The field counts only in request 3: a request with a `refresh_token` is request 2 and ignores it. When at least one session ended it writes one audit row: action `user.sessions_revoked`, actor `system`, details `{sessions}` (the number of sessions ended); this and the `session` logout are the only logouts that write an audit row. All the answers of the request, the `400`, `403` and `503` ones included, carry `Cache-Control: no-store`, and the request writes the usual information line of a logout, naming the number of sessions ended. A `GET` or a request 1 or 2 ignores the field.
- **Sessions of the signed-in user (FR-42).** A client option `allow_session_management` (default `false`) lets a client's access tokens list and end the sessions of their user. The one option covers listing, ending one session and Sign out everywhere.
  - `GET` to the path `urls.endpoints.sessions` (default `{prefix}/{realm}/sessions`, `restart`) with a bearer access token answers `200` with a JSON list of the user's sessions that still have an active refresh token, in the realm, of every client: `session_id`, `client_id`, `started_at`, `auth_time`, `last_used_at`, `expires_at` (the fields and time format of `featherauth session list`) and `current` (`true` for the session the token's `sid` names). Without the option: `403` with `error="insufficient_scope"`. The bearer answers, CORS (as `/userinfo`), `405` and the response headers are those of `/userinfo`.
  - The bearer logout accepts a form field `session` with a session id: it revokes that session when it is a session of the token's user, and answers `204`; a session id that is not the user's, or is unknown, is `400` `invalid_request` and nothing is revoked; a session of the user that is already revoked answers `204` with no audit row. Like `all_sessions`, the field counts only in request 3 and is ignored in a request with a `refresh_token`. Without the option: `403`. `session` together with `all_sessions` is `400` `invalid_request`. It writes the audit row `user.sessions_revoked` (actor `system`, details `{sessions: 1}`).
  - A repeated `session` field is `400` `invalid_request`, as a repeated `all_sessions` is; an empty `session` is absent. `session` with `all_sessions=true` is `400` `invalid_request` from any client.
  - The checks run in this order: the bearer token (`401`), the fields (`400`, as above and for a bad `all_sessions` value), the option (`403`), then the session itself (`400` when it is not a session of the token's user).
  - The sessions path answers the bearer errors as `/userinfo` does: a store failure is `503` `temporarily_unavailable` or `500` `server_error`, and a user removed since the token check is `401` `invalid_token`. Every answer of the sessions path and of the bearer logout carries `Cache-Control: no-store`. The `Access-Control-Allow-Origin` of an answer after a valid token follows the rule of `/userinfo` for the token's client, the `403` answer included; a `401` carries none.
- `sub` is the stable internal user id and never changes. Its format for a user FeatherAuth creates is set by `user_data.id_format` (`uuid` by default, or `ulid`); changing the option never changes the id of an existing user.
- FeatherAuth checks its own tokens (bearer endpoints, ID token hints) with no clock leeway (an access token is expired from the second of its `exp`; an ID token hint is accepted whatever its `exp`), because it issued them with the same clock; APIs choose their own leeway.
- `iat` is the real issue time (clients derive clock skew from it) and `nonce` is present in the access, ID and refresh token whenever the request carried one (some clients reject the login otherwise).
- `preferred_username` is the email when stored, otherwise `sub`.
- **Selectable claims:** `user_data.claims` decides which user claims go into the ID token and `/userinfo`, and into the access token unless `user_data.access_token_claims` is set. Default: `name`, `email`, `email_verified`, `preferred_username`. Optional: `allowed-origins` (array of the calling client's `web_origins`, for an API that derives its CORS allow-list from the token). A claim with no value for a user is omitted. `email_verified` is omitted when the user has no email. `user_data.access_token_claims` names the user claims that access tokens carry, all of them from `user_data.claims` (a name outside it is a configuration error); an empty list puts none in access tokens. Access tokens reach every API and its logs, so a realm can keep the email and name out of them while the ID token and `/userinfo` keep them (FR-41). Claims are chosen per realm, not per client: every client gets the same minimal set, and anything else about a user is for the app or API to keep in its own data.
- **Scopes:** `openid` is the only recognised scope and is required; a login request without it is rejected with `invalid_scope`. Every other scope (`profile`, `email`, anything a library adds) is ignored: it is not an error and is not echoed. The `scope` claim is always `openid`. Scopes do not filter claims: the claims present depend only on `user_data.claims`, so a client that asks only for `openid` still gets them.
- Token JSON payloads are ASCII-only (non-ASCII written as `\uXXXX`), and the ASCII characters `>`, `?`, `~` and DEL (0x7F) are escaped the same way. ASCII alone is not enough: base64url differs from plain base64 only in `-` and `_`, and among ASCII bytes only those four produce `-` or `_` (when they are the third byte of a 3-byte group). With them escaped, a naive consumer that decodes the payload with plain base64 (adding the padding) gets the same JSON.
- Signing algorithm: ID tokens are always `RS256`. `tokens.algorithm` (`RS256`, the default, or `ES256`) signs access tokens and JWT refresh tokens, so an `ES256` realm holds an active RSA key and an active EC key.

Token response: `access_token`, `id_token`, `refresh_token`, `token_type=Bearer`, `expires_in`, `refresh_expires_in`, `scope`.

### DPoP (sender-constrained tokens)

- **DPoP (FR-44, SEC-36).** Demonstrating Proof of Possession (RFC 9449) binds a client's tokens to a private key that stays on the device, so a copied refresh token is useless without the key.
  - The client option `dpop`: `off` (default; a `DPoP` header is ignored and the client gets bearer tokens, except that a refresh token that already has a `dpop_jkt` always needs a proof of that key, whatever `dpop` now says), `allowed` (a request with a proof gets bound tokens, a request without one gets bearer tokens) or `required` (a code grant or a refresh without a proof is `400` `invalid_request`).
  - **The proof** is the JWT in the `DPoP` request header. It is accepted when: there is exactly one `DPoP` header; its header has `typ: dpop+jwt`, an `alg` of `ES256` or `RS256`, and a `jwk` that is a public key (no private parts) of that algorithm (an RSA key of 2048 bits or more); the signature verifies with that `jwk`; `htm` equals the request method; `htu` equals `public_url` followed by the endpoint's configured path, compared without query and fragment, after lower-casing the scheme and host and dropping a default port (RFC 9449 §4.3); `iat` is at most 5 minutes old and at most 1 minute ahead; and its `jti` (at most 255 characters) was not used before with that key: the SHA-256 of the key thumbprint and the `jti` is remembered for 7 minutes (longer than any proof can stay valid) in the table `dpop_proofs` (`proof_hash` primary key, `expires_at`), and a row that exists refuses the proof until the hourly job deletes it after `expires_at`. The row is written with an insert that does nothing on a conflict and reports whether it wrote, so a repeat is a refusal and not a database error. At an endpoint called with an access token the proof must also carry `ath`, the base64url SHA-256 of that access token. Anything else is an invalid proof. No server nonce (`DPoP-Nonce`) is used, and the `dpop_jkt` authorization parameter is ignored. Proofs are verified with the JWT library of the Tech stack. The checks bind clients as follows: the `jti` must be present and not empty; `typ` and `htm` are compared case-sensitively, so `DPOP+JWT` and `post` are invalid; an `htu` with user information is never equal to the endpoint, so it is invalid; an `iat` with a fraction of a second is accepted.
  - **At the token endpoint**, for a client whose `dpop` is not `off`, a proof is checked whenever one is sent, in this order, so that nothing is written for a caller that fails earlier (SEC-34): client authentication; the grant is looked up in a read (this read only decides whether the proof is looked at: when the code or refresh token is unknown, used, rotated, revoked, expired or fails another check of its grant, the request is handled exactly as for a client with `dpop: off`, including the write that uses up a code and the revocation after a reuse, and the proof is not checked and no `jti` is remembered); the proof (an invalid one is `400` with `error` `invalid_dpop_proof`, a code new to the token endpoint); then the `jti` is remembered in the grant's own write transaction. A failing proof does not use up the code or the refresh token. The proof is checked inside the grant's own write transaction, after the grant's other checks; a refusal rolls that transaction back, so a refused request uses up nothing and remembers no `jti`.
    - **Public client.** With a valid proof, a code grant binds the session to the key: the JWK SHA-256 thumbprint (RFC 7638) is stored with the refresh token (the nullable column `refresh_tokens.dpop_jkt`, copied to every successor), the access token carries the claim `cnf` with the member `jkt`, and the token response has `token_type` `DPoP`. A refresh of a bound token needs a valid proof of the same key: a missing one is `invalid_request`, another key's is `invalid_grant`. A refresh token that is not bound stays unbound; a proof sent with it is still checked, and the refresh answers with bearer tokens. A bound token needs its key even when the client's `dpop` is `off`, and it is answered with DPoP tokens, the access token bound to that key. Inside `refresh_reuse_grace`, a just-rotated refresh token that is bound needs a valid proof of its own key before its successor is returned, checked as at any other refresh: a missing proof is `invalid_request`, another key's is `invalid_grant`, and a passing proof's `jti` is remembered. An unbound rotated token is unchanged, except on a `required` client: there, inside the grace window, it is checked exactly as a normal refresh of an unbound token on a `required` client (no proof is `invalid_request`, an invalid proof `invalid_dpop_proof`, and a valid proof is accepted with its `jti` remembered and the session left unbound). `required` wins over the grace rule.
    - **Confidential client.** As RFC 9449 §5 says, its refresh token is not bound (the client secret protects it, and the client may change its key). Each grant or refresh that carries a valid proof gets an access token bound to that proof's key and `token_type` `DPoP`; one without a proof gets bearer tokens, or `invalid_request` when `dpop` is `required`.
    - `required` applies to both grants of the client: code and refresh.
  - **At FeatherAuth's bearer endpoints** (`/userinfo`, `DELETE /account`, the bearer logout, the sessions path): wherever this document says a request is recognised by the scheme `Bearer` (Which kind a request is, in Ending a session), the scheme `DPoP` counts the same. An access token with a `cnf.jkt` is accepted only under the scheme `DPoP` (`Authorization: DPoP <token>`) with a valid proof whose key has that thumbprint; presented as `Bearer`, or with a bad proof, it gets `401` with `WWW-Authenticate: DPoP error="invalid_token", algs="ES256 RS256"` (for a bad proof `error="invalid_dpop_proof"`). An unbound token under the scheme `DPoP` gets the same `401` with `error="invalid_token"`. The access token is checked first and the proof after it, and the proof's `jti` is remembered only for a token that passed. An API that verifies tokens offline (UC-4) decides for itself whether it checks `cnf`. A bound token presented under the scheme `DPoP` with no `DPoP` header is `401` `invalid_dpop_proof`; a valid proof of another key than the token's `cnf.jkt` is `401` `invalid_token`; a repeated `jti` is `401` `invalid_dpop_proof`. Every `DPoP` answer carries `algs="ES256 RS256"`. The proof's `jti` is remembered once the token, the proof and the user have passed, before the endpoint's own checks and action: a refusal before that (a bad token, a bad proof, a disabled user) remembers nothing, and a refusal after it (for example insufficient scope) keeps the `jti`, because the proof passed.
  - **Not bound:** a logout by refresh token and the revocation endpoint need no proof, because ending a session is never withheld. The ID token carries no `cnf`.
  - Discovery lists `dpop_signing_alg_values_supported: ["ES256", "RS256"]` when a client of the realm has `dpop` other than `off`. CORS preflights of the token, userinfo and sessions paths allow the request header `DPoP` besides `Authorization` and `Content-Type`. The logger hides the `DPoP` header and the key `dpop` (added to the list of SEC-13).

## Long-lived sessions

Goal: a mobile app stays signed in even if it is not opened for a year or more.

**Mechanism, by configuration alone: a sliding, rotating refresh token.**

- The access token stays short (15 minutes by default).
- A refresh token is valid as long as it was used within `refresh_idle_lifetime`. Every use issues a new refresh token and starts a new idle window, so a regularly used app never reaches the limit.
- `session_max_lifetime: 0` removes the absolute cap; otherwise the session ends at a fixed age even when used daily.
- On the next launch after a long absence the app presents its stored refresh token; if it is still inside the idle window it receives new tokens and no login screen is shown.
- Set it per client so only the mobile client gets long lifetimes and web clients keep short ones:

```yaml
clients:
  mobile:
    refresh_idle_lifetime: 17520h  # 2 years unused
    session_max_lifetime: 0        # no absolute limit
```

**Trade-offs**

| Concern | Detail | Control |
| --- | --- | --- |
| Long-lived secret on the device | The refresh token becomes a credential valid for years. Store it in the iOS Keychain or Android Keystore, not in plain app storage | App guidance (see Clients) |
| Rotation can force a re-login | If a refresh succeeds but the response is lost, or an app sends two refreshes at once with the same token, the old token still works within `refresh_reuse_grace` (each use gets a fresh successor, and all of them work until one is used); a reuse after that, or a successor presented after another one was used, revokes the whole session (theft protection, but it signs that user out). An app that keeps one of two concurrent successors is safe; one that uses one successor and then stores the other is signed out | Raise `refresh_reuse_grace` to a few minutes. Public clients always rotate; only a confidential client may set `refresh_token_rotation: false` |
| A copied refresh token works | The refresh token is a bearer credential: whoever copies it from the device (a backup, malware) can use it, and rotation notices only once both copies are used after the grace window | Secure storage on the device; DPoP (RFC 9449, the client option `dpop`) binds the token to a private key that stays on the device (DPoP) |
| No self-service sign-out | A lost phone keeps working until the token expires or an operator acts | `featherauth user disable` stops refresh at once; self-service "sign out all devices" is a bearer logout with `all_sessions=true` (Sign out everywhere, FR-39) |
| Apple and Google report account changes | Apple tells FeatherAuth when a user stops using Sign in with Apple or deletes the Apple account, which ends their sessions (Provider account events); Google reports its changes by security event tokens (Google Cross-Account Protection, FR-48). If a user revokes the app at GitHub or Facebook, FeatherAuth does not notice until the refresh token expires | An accepted risk; a recheck at the provider for long sessions is on the roadmap of REQUIREMENTS.md |
| Database growth | Rotation keeps one row per refresh until the session expires | Small at the target load; the hourly job prunes expired rows |

**Single sign-on session: start (FR-45, SEC-37).** With `sso.enabled`, a login that completes at the callback for a client with `sso: true` creates a browser session: a random 256-bit id, stored only as its SHA-256 in the table `sso_sessions` (`id_hash` primary key, `realm_id`, `user_id`, `identity_id`, `provider`, `auth_time`, `created_at`, `last_used_at`, `expires_at`; index on `user_id`; deleted with the user), and set as a cookie named `fa_sso_` plus the realm name. The cookie is `HttpOnly`, `Secure` as the state cookie is, `SameSite=Lax`, with `Max-Age` the idle lifetime and `Path` the longest common directory of the realm's authorize and logout paths (so it reaches both and nothing wider than needed). The token session that a login or a silent use starts remembers its browser session (the nullable column `refresh_tokens.sso_id_hash`, copied to successors; it travels from the callback or the authorize request to the token session on the login code, the nullable column `auth_codes.sso_id_hash`). At the start, the last use is now, and the expiry is the earlier of now plus `sso.idle_lifetime` and `created_at` plus `sso.max_lifetime`, which at the start is now plus the lesser of the two. A new login replaces the browser session of that browser: when the request carries the cookie of a browser session of this realm, that session's row is deleted in the same transaction that creates the new one. The code is issued first and the session stored after it; when the store cannot keep the session, the login fails with `server_error`, no code is delivered and no cookie is set.

**Single sign-on session: use and end (FR-45, SEC-37).**
- **Use.** An authorization request (after all checks of Errors in the authorization request) is answered from the browser session, with no chooser and no provider, when the cookie names a session of this realm that is not expired, its user exists and is not disabled, the client has `sso: true`, the session's provider is still enabled in the realm and the user still holds the identity the session was made with, the request has no `prompt` of `login`, `select_account` or `consent`, its `max_age` (if any) is not less than the age of the session's `auth_time`, and its provider hint (if any) names the session's provider. `login_hint` plays no part. An `id_token_hint` plays a part only with `prompt=none` (below); without it a hint is ignored, also when it names another user. The answer is a login code as after a provider login, with the session's `auth_time` and a new token session (`sid`). The session's `last_used_at` and expiry move forward (the earlier of now plus the idle lifetime and `created_at` plus the max lifetime) and the cookie is set again. In every other case the request goes on to the chooser or the provider, as for a browser without a session. A cookie is deleted only when the session itself cannot be used (it is missing or expired, its user is disabled or gone, its identity or its provider is gone, or the realm's `sso` is off); when only this request rules the session out (the client's `sso`, the `prompt`, `max_age` or a provider hint naming another provider), the cookie and the row are left alone and the request goes on to the chooser or the provider. A store failure while the session is read, the code is issued or the session is moved on answers `server_error` (no code, and the cookie is not set again).
- **`prompt=none`.** With a usable browser session (the conditions above) the request is answered with a code; without one, with `login_required`. An `id_token_hint` whose `sub` is another user than the session's gives `login_required`; a hint that fails verification is ignored.
- **End.** The browser session ends, and its row is deleted, when:
  - an RP-initiated logout arrives with the cookie: the cookie is cleared, whether or not the request has a hint. Without a hint only the browser session ends and no token session is revoked. Another site can cause this with a cross-site link; that is accepted, because the only effect is that the next login goes to the provider again.
  - a token session that came from it is revoked, for any reason (through `refresh_tokens.sso_id_hash`: a logout, the revocation endpoint, a `session` logout, a reuse, `session revoke --session`), so an app that logs out from its own code, without the browser, is not signed in again silently and the user can switch accounts;
  - the user is disabled or deleted, or all the user's sessions are revoked (the session commands without `--session`, Sign out everywhere, a revoking provider event): every browser session of the user is deleted;
  - the identity it was made with is unlinked or its provider says the user is gone (`user unlink`, Apple's `consent-revoked` and `account-delete`, Meta's callback): the browser sessions made with that identity are deleted.
  A realm-wide revocation ends every browser session of the realm (`DeleteByRealm`). The hourly job deletes expired rows. Ending a browser session, or a logout at one client, does not end the token sessions of other clients that were started from it; they end by their own logout, their lifetimes, or a revocation of all the user's sessions. If the browser session cannot be ended, the logout answers its error page and keeps the cookie.
- **Limits.** The cookie is `SameSite=Lax`, so it is sent only on a top-level navigation with `GET`: an authorization request sent as a cross-site form `POST` does not carry it and goes to the provider, and silent `prompt=none` renewal works as a top-level redirect only, never in a hidden frame (the pages also forbid framing, SEC-12).
- **Security (SEC-37).** The id is checked by hash; the cookie is never `SameSite=None`; every client of a realm with `sso: true` gets a code without the user acting, which is intended for the apps of one product and is why the option is off by default and can be switched off for a client. A reload that sets `sso.enabled: false` stops the use at once; the rows expire.

**Long refresh tokens and the single sign-on session together.** With the single sign-on session FeatherAuth keeps its own browser session cookie, so when the refresh token has expired the user is sent to `/authorize` and is signed in again without choosing a provider (and silent `prompt=none` renewal becomes possible for web apps). It also relies on the provider's own browser session, so re-login is often one tap. It is less dependable on mobile than long refresh tokens (system browsers and in-app tabs may not keep cookies, and users clear them), so it complements long refresh tokens rather than replacing them.

### Back-channel logout

- **Back-channel logout (FR-43, SEC-35).** OpenID Connect Back-Channel Logout 1.0, so that an app's server learns at once that a session ended.
  - The client option `backchannel_logout_uri` (default empty: no notification): an `https` URL without a fragment (`http` is accepted only with `require_https: false`, for local development; SEC-35 says `https` for every other case).
  - Whenever a session of that client is revoked, for any reason (the three logouts, the revocation endpoint, a reuse, disabling or deleting the user, a provider event, the session commands, sign out everywhere), one notification row is written in the transaction that revokes: the table `logout_notifications` (`id`, `realm_id`, `client_id`, `user_id`, `session_id`, `attempts`, `next_attempt_at`, `created_at`; primary key `id`; index on `next_attempt_at`; `user_id` is plain text with no foreign key, because the user may be deleted in the same transaction and the token still needs `sub`). A session gets a row when the revocation revoked at least one of its refresh tokens, also one that had already expired (the client's own server session may outlive it); a session whose refresh tokens were all revoked before gets none, because it was notified then. The refresh rotation's sibling cleanup (`RevokeOthers`) ends no session, so it writes no row: the rows come from the calls that end a session (`RevokeSession`, `RevokeUser` and the deletion of a user's tokens). A revoking command of the CLI (`session revoke`, `user disable`, `user delete`) reads the configuration to find the clients' URIs. When it cannot load the configuration, the command still revokes, disables or deletes, queues no logout notification and logs one warning. `user delete` still refuses when the configuration is unusable (User administration and import), because it must revoke the stored provider tokens (SEC-10); only the queue is decided here. A loaded configuration that does not name the realm gives its sessions no URI, so their revocation queues nothing.
  - A worker in the service sends each row: a `POST` to the URI with `Content-Type: application/x-www-form-urlencoded` and one field `logout_token`. The logout token is a JWT with header `typ: logout+jwt`, signed `RS256` with the realm's active RSA key, with the claims `iss`, `aud` (the client id), `iat` (the time of the try), `exp` (`iat` plus 2 minutes), `jti` (new for each try), `sub`, `sid`, and `events` with the one member `http://schemas.openid.net/event/backchannel-logout` whose value is `{}`. It carries no `nonce`.
  - A claim is one short write transaction that selects at most 4 due rows in the order of `next_attempt_at` (on Postgres with `FOR UPDATE SKIP LOCKED`, so two instances take different rows), returns each with the `attempts` it had before this claim (so a row that already has 5 attempts is the one the worker deletes unsent), adds 1 to its `attempts` and sets its `next_attempt_at` to the next try: 1 minute, 5 minutes, 30 minutes and 2 hours after the first, second, third and fourth try. The HTTP call runs outside any transaction, with a 5 second timeout, following no redirect; the response body is read up to 64 KB and discarded. A `200` or `204` answer deletes the row. Any other answer or a failure leaves it for its next try, and a failed fifth try deletes it with a warning that names the client and the session id. A crash during a call therefore counts as a failed try. **Rounds (NFR-15).** The rows of one claim are posted one after another, never concurrently, so a round takes at most 4 calls of at most 5 seconds each: a receiver that does not answer delays the other rows of its round by at most 20 seconds, and the next round starts only when the round before has ended. A row whose call failed or timed out keeps its place in the queue and is tried again at its `next_attempt_at`, so a slow receiver never makes another client's notice be dropped. "No notice lost" (NFR-15) means exactly this: no notice is lost because of another client's delay; a notice is dropped only after its own fifth failed try, with the warning above. The worker looks for due rows every 5 seconds (rows are also queued by the CLI and by other instances), and a due row whose `attempts` is already 5 is deleted with the warning and not sent. Delivery is at least once: after a lost answer the token is sent again with a new `jti`, and a receiver that must not act twice goes by `sid`. A client that was removed from the configuration, or lost its URI, has its rows deleted. On shutdown the worker stops after the calls in flight; rows wait for the next start.
  - Discovery lists `backchannel_logout_supported: true` and `backchannel_logout_session_supported: true`. The token verifier refuses a `logout+jwt` token everywhere (it is not an access token, and not an ID token hint).
  - What stays true: an access token already issued still verifies offline until it expires (SEC-14); the notification lets the client's own server end its session.

## HTTP endpoints

All endpoints are served over HTTPS, behind a reverse proxy or by the service itself with `tls.mode: files`. API errors use OAuth2 error JSON, and bearer endpoints also set `WWW-Authenticate` (RFC 6750); browser endpoints show a plain HTML page. A request body larger than 64 KB gets `413` (SEC-45). Answers the router itself gives (an unknown realm `404`, `413`, the rate limit's `429`, a recovered panic's `500`) are, on API endpoints, the OAuth error JSON with `error` `invalid_request` and description `unknown realm` (404), `invalid_request` and `request body too large` (413), `temporarily_unavailable` and `too many requests` (429) or `server_error` (500), and on browser endpoints a plain HTML error page; a path that matches no endpoint is a plain `404`. A request whose method an endpoint does not accept (the methods are those of the table below) gets `405` (FR-58) with an `Allow` header listing the accepted methods, `OPTIONS` included where CORS applies; on API endpoints the body is the OAuth error JSON with `error` `invalid_request` and description `method not allowed`, and on browser endpoints a plain HTML error page; nothing is changed. Discovery and the JWKS keep answering every method. `/healthz` and `/readyz` accept `GET` and `HEAD`; any other method gets `405` with `Allow: GET, HEAD` (every accepted method is listed, FR-58) and a plain-text body (`method not allowed`). Every other endpoint accepts exactly the methods of the table below, plus `OPTIONS` where CORS applies (token, revocation, userinfo, sessions); a `HEAD` to one of them that does not list it is a `405` like any other method. The service uses fixed timeouts (SEC-45): 5 seconds to read the request headers, 10 seconds to read the whole request, 60 seconds to write the response (a callback waits on its provider, whose `timeout` is at most 30 seconds) and 120 seconds for an idle keep-alive connection. `{prefix}` is `urls.path_prefix`, empty by default. The paths shown are the defaults; each is set by `urls.endpoints.*` (see `server.yaml` and Path templates in the Configuration reference).

Every response of the router carries `X-Content-Type-Options: nosniff` (SEC-29), whatever its endpoint: the OAuth JSON answers, discovery, the JWKS, the assets, the health endpoints and the router's own answers listed above, including the `405` and the CORS preflight answers. Browser pages carry it with the other headers of SEC-12. The router sets it before any endpoint handler runs, so the handlers do not set it. Answers that net/http writes itself before a request reaches the router (a malformed request line, an oversized request header, a read timeout) are outside this rule.

| Method | Path | Caller | Auth | Returns |
| --- | --- | --- | --- | --- |
| GET | `{prefix}/{realm}/.well-known/openid-configuration` | Apps, APIs | None | Discovery JSON |
| GET, POST | `{prefix}/{realm}/authorize` | App via browser | None | Provider chooser or redirect |
| GET, POST | `{prefix}/{realm}/callback/{provider}` | Provider | `state` parameter and cookie (Apple's `POST` is answered with a `303`; see Apple's callback) | Redirect to app with code |
| GET | `{prefix}/{realm}/callback/{provider}/continue` | Browser, redirected after Apple's `POST` | One-time id, `state` and state cookie | Redirect to app with code |
| POST | `{prefix}/{realm}/token` | App | PKCE verifier, client secret or refresh token | Tokens |
| POST | `{prefix}/{realm}/revoke` | App | Client authentication as at the token endpoint, and a `token` | 200 with an empty body |
| GET, POST | `{prefix}/{realm}/userinfo` | App, API | Bearer access token (`typ: at+jwt`) | User claims |
| GET | `{prefix}/{realm}/sessions` | App, API | Bearer access token (`typ: at+jwt`) of a client with `allow_session_management` | The user's sessions |

The service makes no outgoing call other than those this document names (SEC-46): to its database, to the configured providers (their authorize redirects are made by the browser; the service calls their token, user-info, key, discovery, revocation, Graph, GitHub API and security-event configuration endpoints, Provider calls) and to the `backchannel_logout_uri` of configured clients (Back-channel logout). It sends no telemetry. `featherauth healthcheck` calls only the service's own `/readyz` on its listen address: a call to the service itself, which sends nothing anywhere else. The code that can open an outgoing connection lives only in `internal/provider/`, `internal/oidc/backchannel_deliver.go`, `internal/store/postgresconn.go` and `cmd/featherauth/health.go`; the row "No telemetry" checks this by a source scan, and checks a sign-in, a refresh and the back-channel worker by recording their connections. The provider events, backup, import and the other commands are covered by the source scan only, not by recording: there is no dialer seam for them, and none is required.

### Browser pages

Every browser page (the chooser, the error pages, the signed-out page, the data-deletion page and the `form_post` answer page) carries `Strict-Transport-Security` (`security_headers.hsts`, effective over HTTPS only), `X-Content-Type-Options: nosniff`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer` (page URLs carry codes, `state` and handoff ids, and the logo may come from another host), `Cache-Control: no-store`, and the content security policy of `security_headers.content_security_policy`, whose default holds `frame-ancestors 'none'` (SEC-12). The chooser's stylesheet and the built-in provider logos are built into the binary and served from the assets path (FR-33); only `login_page.logo_url` may name another host. The `form_post` answer page replaces the realm's policy with its own, which allows exactly its submit script (by hash) and the target origin as `form-action`, and it holds a submit button, so that the result reaches the client with and without JavaScript (FR-33). The realm's `login_page.contact` is shown on the error pages and the data-deletion page (FR-55).

### Discovery document

`GET <issuer>/.well-known/openid-configuration` returns a JSON document built per realm. The issuer is `public_url` followed by `urls.issuer` with its placeholders filled in (for example `https://auth.example.com/main`); the document never uses the request's `Host` header.

| Field | Value |
| --- | --- |
| `issuer` | The issuer above, with no trailing slash |
| `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint`, `jwks_uri` | The configured `urls.endpoints.*` paths, as full URLs under `public_url` |
| `end_session_endpoint` | The logout endpoint |
| `revocation_endpoint` | The revocation endpoint |
| `token_endpoint_auth_methods_supported` | `["client_secret_basic", "client_secret_post", "none"]`: `/token` accepts the first two from confidential clients and `none` (client id only, protected by PKCE) from public clients |
| `revocation_endpoint_auth_methods_supported` | The same list as `token_endpoint_auth_methods_supported` |
| `response_types_supported` | `["code"]` |
| `subject_types_supported` | `["public"]` |
| `id_token_signing_alg_values_supported` | `["RS256"]`: ID tokens are always RS256, and Discovery 1.0 requires `RS256` in this list |
| `scopes_supported` | `["openid"]` |
| `claims_supported` | The realm's configured `user_data.claims`, in that order, followed by the standard ID token claims `iss`, `sub`, `aud`, `exp`, `iat`, `auth_time`, `sid`, `nonce`, `at_hash` |
| `response_modes_supported` | `["query", "fragment", "form_post"]` |
| `grant_types_supported` | `["authorization_code", "refresh_token"]` |
| `code_challenge_methods_supported` | `["S256"]` |
| `authorization_response_iss_parameter_supported` | `true` (RFC 9207) |
| `backchannel_logout_supported`, `backchannel_logout_session_supported` | `true`: back-channel logout is delivered for each session of a client with `backchannel_logout_uri` (FR-43) |
| `request_parameter_supported`, `request_uri_parameter_supported`, `claims_parameter_supported` | `false`. Listed on purpose: Discovery 1.0 assumes `true` for `request_uri_parameter_supported` when the field is missing |

- **Required by the OpenID Connect Discovery specification:** `issuer`, `authorization_endpoint`, `token_endpoint`, `jwks_uri`, `response_types_supported`, `subject_types_supported`, `id_token_signing_alg_values_supported`. Recommended: `userinfo_endpoint`, `scopes_supported`, `claims_supported`. Strict client libraries reject a document that lacks a required field (AppAuth-iOS checks all seven; oidc-client-ts also requires `userinfo_endpoint`; Spring Security requires `jwks_uri`), so all of them are always present.
- **`end_session_endpoint`** is not part of the discovery specification (it comes from the RP-Initiated Logout specification), but libraries enable logout only when the field is present, so it is listed. `revocation_endpoint` lists the standard revocation endpoint (see Revocation endpoint); sessions can also be ended through the logout path (see Ending a session).
- **Issuer exactness:** the `issuer` string is identical in the discovery document, in every token's `iss`, and in the URL the document is fetched from (`<issuer>/.well-known/openid-configuration`), as the specification requires. It has no trailing slash, and `featherauth config check` rejects a configuration that would produce one. Spring Security fails on a one-character difference.
- **JWKS:** each key in the keys document carries `use: sig`, `alg` and `kid`.
- **Caching:** the discovery document and the JWKS are served with `Cache-Control: public, max-age=300`.
- **Methods:** the discovery endpoint answers every HTTP method with the document; it does not check the method.

### Token endpoint behaviour

- **Request:** `POST` with `Content-Type: application/x-www-form-urlencoded` only; any other content type is `invalid_request`. Client authentication is as in FR-07.
- **Response headers:** every token response, success or error, carries `Cache-Control: no-store` and `Pragma: no-cache`, so no proxy or browser keeps a token.
- **CORS:** `OPTIONS` (preflight) is answered with the methods `POST` and `OPTIONS` and the headers `Authorization, Content-Type` (plus `DPoP` on this path, see DPoP; `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`) for an origin registered in any client's `web_origins` of the realm, and without CORS headers for any other origin. The `POST` itself is allowed only for a registered origin of the authenticated client (SEC-18): a `POST` with any other `Origin` is answered `invalid_request` without CORS headers, before the code or refresh token is looked at, so it is not used up. The same preflight on `/userinfo` announces `GET, POST, OPTIONS` (the request is checked against the access token's `azp` client), and on the JWKS and discovery `GET, OPTIONS` (any client of the realm may register the origin); every CORS answer carries `Vary: Origin` and the allowed origin is the request's own, never a wildcard.
- **Codes and PKCE:** a `code_verifier` that is not 43 to 128 characters of `A-Z a-z 0-9 - . _ ~` is `invalid_request` (RFC 7636 §4.1); a verifier that does not match the challenge, a missing verifier for a code issued with a challenge, a verifier for a code issued without a challenge, and a reused or expired code are `invalid_grant`, and a reused code also revokes the session created from it (FR-07). A code is used up by the first request that names it, so a request that fails a client, redirect URI or PKCE check also uses it up (a malformed verifier is refused before the code is looked at and does not). A reused code revokes its session whichever client presented it. A request for a realm that has issued no code is `invalid_grant` and writes nothing.
- **Errors:** a JSON body with `error` and `error_description`, using the standard codes `invalid_request`, `invalid_client`, `invalid_grant` and `unsupported_grant_type`. A `scope` parameter is ignored. Sending both client authentication methods is `invalid_request` (RFC 6749 §2.3). A public client that sends a non-empty `client_secret` gets `invalid_client`; an empty one counts as absent. An unknown client, a missing `client_id` and a confidential client with a wrong or missing secret get `invalid_client`; a `client_id` in the body that differs from the one in the `Authorization: Basic` header is `invalid_request`, and so is a `client_id` or `client_secret` sent more than once (RFC 6749 §3.2). An `Authorization: Basic` header without a valid credential is `invalid_client`. The client is authenticated before the grant is looked at, and a missing or unknown `grant_type` is `unsupported_grant_type`. The status is `400` for all of them except `invalid_client`, which is `401` with a `WWW-Authenticate: Basic` header when the client authenticated with `client_secret_basic`, and `400` otherwise. A transient failure is `503` with `temporarily_unavailable`, never a `4xx` (Restart specification, OPS-14).

### Revocation endpoint

`POST` to the path `urls.endpoints.revoke` (default `{prefix}/{realm}/revoke`, `restart`), following RFC 7009. The body is a form with `token` (required; missing, empty or repeated is `invalid_request`: an empty value counts as absent, as in Ending a session) and `token_type_hint` (optional; any value is accepted and only steers which kind is tried first; when it is repeated the first value counts). The client authenticates as at the token endpoint, with the same errors. A refresh token of that client revokes its whole session, with the same code as `POST /logout`, also when it is expired, rotated or already revoked. An access token (`typ: at+jwt`, valid, of this realm, `azp` the authenticated client) revokes the session its `sid` names; the user is not looked up, so the token of a disabled or deleted user is revoked like any other. Any other token (unknown, malformed, of another client, an expired access token, an ID token) changes nothing. In all these cases the answer is `200` with an empty body, `Cache-Control: no-store` and `Pragma: no-cache`. Every error answer of the endpoint (`400`, `401`, `503`) also carries `Cache-Control: no-store`. An unavailable store is `503`. A realm with `enabled: false` does not block revocation, as it does not block logout. Discovery lists `revocation_endpoint` and `revocation_endpoint_auth_methods_supported` (the values of the token endpoint). CORS, the rate limit and the `405` answer are those of the token endpoint. Every request that reaches the token lookup writes exactly one information line to the log, whether or not a session ended, with the realm, the client and whether a session was revoked, never the token, and no audit row, like a logout.

## Runtime configuration

Everything that varies is data in a mounted directory. The image contains only the binary. The directory is the one `FEATHERAUTH_CONFIG_DIR` names (default `/etc/featherauth`); `FEATHERAUTH_LISTEN`, when set, overrides `listen` of `server.yaml`. Nothing else is read from the environment (FR-17). The service does not start when `server.yaml` or `database.yaml` is invalid or no realm file is valid, and says why on standard error.

```text
/etc/featherauth/
  server.yaml                 public URL, listen address, rate limits, log level, endpoint paths and parameter names
  database.yaml               database driver and connection, backup schedule (restart needed)
  realms/
    main.yaml                 one file per realm
  secrets/
    main/google_client_secret one file per secret, referenced from the realm file
    main/signing-2026-10.pem
```

Reload behaviour:

- Watched for file changes, and reloaded on `SIGHUP`.
- A reload builds a complete new configuration, validates it, then swaps it in atomically; in-flight requests keep the old one.
- If validation fails, the error is logged with file, line and field, the last good configuration keeps serving, and `/readyz` stays 200. `featherauth config check <dir>` shows the same diagnostics without the service.
- Each realm reloads independently; a broken realm file never affects another. A reload that would leave no valid realm is not applied, as at startup: the error is logged and the last good configuration keeps serving.
- A file in `realms/` whose name starts with a dot (an editor's lock or swap file) is ignored.
- Changes apply to the next request. Issued tokens keep their claims. Removing a client or disabling a realm fails new authorization requests at once and refresh tokens on next use.
- Key rotation is config only, in two steps, so that no verifier sees a token signed by a key it has not cached: (1) add the new key as `verify_only` and wait at least 5 minutes, the JWKS `max-age=300`; (2) make the new key `active` and the old one `verify_only`, then remove the old key once the longest token it signed has expired (the access token lifetime; an ID token an app keeps for logout is replaced at its next refresh).
- **Emergency key rotation.** The emergency key runbook of the user guide (`docs/USER_GUIDE.md`, OPS-11) describes what to do when a signing key is exposed: add a new key as `active` and remove the exposed key from the realm file in one change (no `verify_only` period), reload, and expect failures until every verifier has fetched the JWKS again (at most its cache time, 300 seconds for a verifier that honours `max-age`); FeatherAuth's own endpoints refuse tokens of the removed key at once; then revoke the sessions that could have been forged (`session revoke` for a user, or `session revoke <realm> --all` for the realm, described in User administration and import), and replace the secret file. It also covers an exposed encryption key (`secrets.encryption_key_files`; the key is read at startup, so the service is restarted, and the exposed key stays listed after the new first key until `keys reseal` or `keys clear-sealed` has left no value it sealed, which `keys sealed` shows, User administration and import) and an exposed client secret (refused at the token endpoint with `invalid_client` from the reload on, with no grace period; no session ends). Every `featherauth` command the runbook names must exist, which a test checks against the command list.
- Secrets are read from files at load, never logged, never returned by the status endpoint. A secret file holds the value as text, and one trailing newline is ignored. A client secret file (of an enabled provider or of a client) that is empty, or holds only whitespace, is an error at load and in `config check`. An encryption key file holds 32 random bytes as base64 (44 characters). Signing keys are PEM files; an RSA key has at least 2048 bits. The secret of a confidential client (its `client_secret_file`) that is shorter than 32 characters is a warning at load and in `config check`, not an error (SEC-30): the secret is the only thing between an attacker and that client's identity at `/token`, and the rate limit alone does not protect a short one. A character is a Unicode code point, counted in the secret as the service compares it, after the trailing newline is dropped. The warning gives the realm file, the line, the field `clients.<id>.client_secret_file` and the message `secret file <file> is shorter than 32 characters; use a client secret of at least 32 characters`, where `<file>` is the option's value. Provider secrets are not checked.
- **Secret file permissions (SEC-09).** At load and in `config check`, every file named by a `*_file` option, and every key file, is checked: any permission for its group or for others (mode bits `0077`) is an error, or a warning with `strict_permissions: false`. The one exception is a certificate file, which is public: `postgres.root_cert_file` is a `*_file` option read without that check. The loader checks the mode bits only, not the owner.
- **Sealed provider tokens (SEC-10).** Stored provider refresh tokens (Apple's) are encrypted with AES-GCM under the first key of `secrets.encryption_key_files`; every listed key can decrypt. A key is 32 bytes; its id is the first 8 hex characters of the SHA-256 of the 32 raw key bytes (not of their base64 text), and the id is bound to the ciphertext as the AES-GCM additional authenticated data. A stored value is the key id, a `.`, and the unpadded base64url of a random 12-byte nonce followed by the AES-GCM ciphertext and tag; a value whose key id matches no listed key cannot be decrypted. If a stored token cannot be decrypted at account deletion, the deletion still completes, the Apple revoke is skipped and a warning is logged. A configuration with `store_refresh_token: true` and no encryption key is an error at load.
- Unknown fields are errors, so a typo is caught instead of silently ignored. A file with more than one YAML document is an error at the line where the second document starts.
- `server.yaml` is watched too. Its `live` options apply on reload; when a `restart` option or anything in `database.yaml` changes, the service validates the new content, logs `restart required` with the option names and keeps running on the old values. An invalid file is reported and ignored, as for realm files; so is a secret file of `server.yaml` or `database.yaml` (an encryption key file or `postgres.password_file`) that cannot be read: the previous secrets stay in use and the realms still reload. These secrets are read at startup and are not replaced by a reload. The restart is always started by the operator, after `featherauth config check <dir>`; the service never restarts itself.

The repo ships annotated examples in `deploy/config.example/`; a test fails if a code field has no comment there. `featherauth config init <dir>` writes them, and `featherauth config check <dir>` validates offline.

### Configuration reference

Every option, its default, what it does and the values that make sense. Durations use Go syntax (`30s`, `15m`, `720h`). A duration must be greater than zero unless its row gives `0` a meaning (`session_max_lifetime`, `refresh_reuse_grace`), and a negative duration is always rejected; a provider `timeout` of zero, for example, would mean no timeout at all. Paths of secret files are relative to the config directory. "Required" means no default. Unknown options are errors.

#### `server.yaml`

"Takes effect" is `live` when the service applies a change without a restart, and `restart` when the service reports `restart required` and keeps running on the old value until it is restarted.

| Option | Default | Explanation | Possible values | Takes effect |
| --- | --- | --- | --- | --- |
| `public_url` | required | External base URL of the service. Part of every issuer and redirect URL | `https://host`, no trailing slash | restart |
| `listen` | `":8080"` | Address the service listens on behind the proxy; the environment variable `FEATHERAUTH_LISTEN` overrides it (FR-17) | `host:port` or `:port` | restart |
| `tls.mode` | `none` | `none`: a proxy ends TLS. `files`: the service ends TLS with a certificate from files | `none`, `files` | restart |
| `tls.listen` | `":443"` | Address of the HTTPS listener (`files`) | `host:port` or `:port` | restart |
| `tls.http_listen` | `":80"` | Address of the plain listener that answers every request with a `301` to the same URL under `public_url`; empty opens none | `host:port`, `:port` or empty | restart |
| `tls.cert_file` | required with `files` | PEM certificate chain | file name | restart |

With `files`: `public_url` must be `https`; the HTTPS listener serves every endpoint; the plain `listen` address stays, must then be a loopback address, serves only `/healthz` and `/readyz` (any other path is `404`), and is what `featherauth healthcheck` calls; and `trusted_proxies` must be empty (a configuration error otherwise), because no proxy is in front. TLS 1.2 is the lowest version accepted, with Go's default cipher suites. A change of either file, and a `SIGHUP`, loads the pair again without a restart (a pair that cannot be loaded is logged and the old one stays). The client IP on these listeners is the connection's address. The example `server.yaml` for this mode (`deploy/config.example/server.tls.yaml.example`, written by `config init` with the other examples) sets `tls.listen` to `:8443` and `tls.http_listen` to `:8081`, and `deploy/compose.tls.yaml` publishes them as the host's ports 443 and 80, so the container needs no capability and the settings of SEC-31 stay.

Decisions for the built-in TLS options (`files`). A relative `tls.cert_file` or `tls.key_file` is read from the configuration directory, as the other file options are; an absolute path stays as it is. A loopback address is an IP address in `127.0.0.0/8` or `::1`; a host name such as `localhost` is refused. The loopback rule applies to the address in use, so an address set in `FEATHERAUTH_LISTEN` that is not loopback stops the service at startup when `tls.mode` is `files`. A missing or broken pair stops the service at startup, and `config check` reports it; a reload does not read the pair, so a broken pair never rejects a reload: the certificate is loaded again on a file change and on `SIGHUP`, and a pair that cannot be loaded keeps the previous one serving. Setting `tls.cert_file` or `tls.key_file` while `tls.mode` is `none` is not checked. A key that does not match its certificate, or a certificate that is not PEM, is reported on `tls.key_file`. The file watch waits for the same debounce as the configuration watch. The HTTPS listener negotiates HTTP/1.1 only. The redirect listener writes no request log line. Two listeners on one address fail at startup with a bind error; no check reports it before that.

Path templates:

- **Placeholders:** `{prefix}` is `urls.path_prefix`, `{realm}` the realm name, `{provider}` the provider name (callback and provider events only). The app (client) is identified by `client_id` in the request, never by the path.
- **One path per endpoint:** the configured path is served and listed in discovery. Some client libraries build endpoint URLs from a fixed template instead of reading discovery, and an existing provider app has a registered redirect URI; setting the matching path per endpoint serves both without code changes.
- **Validation (load, reload and `featherauth config check`):** a realm named `admin`, `healthz` or `readyz` is rejected (the shorter `{prefix}/{realm}` paths could collide with the service's own paths when the prefix is empty; `admin` is reserved as well, and the service serves no `/admin` path, SEC-17); every template must contain `{realm}`; `callback` and `provider_events` must contain `{provider}`, and no other template, nor `urls.issuer`, may; a template may contain no placeholder other than `{prefix}`, `{realm}` and `{provider}`; two endpoints may not resolve to the same path; every path must start with `/`. A violation keeps the last good configuration.

| `sso` | `true` | Whether the client takes part in the realm's single sign-on session (FR-45): `false` keeps its logins out of it, so they start no browser session | `true`, `false` |

## Database configuration

SQLite by default; Postgres is supported (`driver: postgres`). The database has its own file, read at startup only, because a database change needs a restart and a data copy (FR-25).

The options are in the Configuration reference above (`database.yaml`).

Both drivers sit behind the same repository interfaces; migrations are ordered and shared, with a dialect-specific file only where the SQL differs, and the store contract suite runs against both drivers. Rules that keep the two drivers alike: no SQLite-specific SQL, IDs and times generated in Go, explicit transactions, no `rowid`.

**Driver (FR-35).** `driver: postgres` in `database.yaml` starts the service on Postgres with the options of the `postgres` block, through `pgx` and `database/sql`. Postgres 15 or newer is supported.

**Processes.** With `driver: sqlite` there is one service process per database file. With `driver: postgres` several service processes may run on one database, behind a proxy that health-checks them, which allows a deploy with no failed request (More than one instance below).

**Pools and health.** One connection pool (`postgres.max_open_conns`, `max_idle_conns`, `conn_max_lifetime`) serves reads and writes. `/readyz` pings the database through one connection of its own, outside that pool, so that it does not wait behind the reads and writes (FR-16). Every connection, of the pool and of `/readyz`, is opened with `postgres.connect_timeout` (OPS-22), passed to `pgx` as its connect timeout, and every query runs under the request's context as well. When the `/readyz` connection is lost, the next `/readyz` opens a new one under that limit, so a server that does not answer makes `/readyz` answer `503` at most `postgres.connect_timeout` after the request (default 5 seconds; `featherauth healthcheck` gives up after 3 seconds and reports not ready in that case too). A start whose first connection fails within the limit stops with the reason, holding no password, as any other database error at startup.

**`db copy` (FR-36).** `featherauth db copy --from <file> --to <file>` copies every table from the SQLite database named by one `database.yaml` to the Postgres database named by another; secret paths in each file are relative to that file's directory. It is the way onto Postgres, which several instances need. The other direction is not built: the SQLite file is not changed by the copy, so going back means starting the service on that file again, without what was written to Postgres since. A source that is not SQLite or a target that is not Postgres is a usage error. It applies the migrations to the target, refuses (exit `1`, nothing written) when any table of the Data model holds a row in the target or when the source's schema version is not the one this binary expects, reads the source in one transaction that sees one state and writes the target in one transaction. Before it commits it compares, table by table, the row count and a SHA-256 checksum of both sides. The checksum is computed in Go, the same way for both drivers: the rows sorted by the bytes of their primary key (column by column in key order where the key has several columns), and each column value written as a marker for null or not null, the length of its canonical text and that text (a text as its bytes, a number in decimal, a boolean as `0` or `1`). It prints one line for each table (`<table> <rows> ok`) and `copied` at the end; on any difference it rolls the target back, prints the table, and exits `1`. The service must be stopped first: a row written to the source after the copy began is not copied.

**`db copy` checks, checksums and output.** The tables are those the migrations create, in the order the migration files create them, so a table is copied after the tables it refers to; a table added by a later migration is copied too. The source is checked first, so a refused copy writes to neither database: it is opened without migrating it, and a source with no schema version, with another one, or with tables that differ from the schema is refused with exit `1`. The target is checked for rows before the migrations run on it, so a target that holds rows is not migrated, and again inside the write transaction. A `--from` or `--to` file that cannot be read exits `1`; both files are validated as `config check` validates them, and their diagnostics are printed as `file:line: severity: field: reason` and exit `1`. `--from` and `--to` are required, each once, and any other argument is a usage error (exit `2`); a file that names the wrong driver is a usage error too. The secret files of `--to` are read relative to its directory, and `strict_permissions` is read from `server.yaml` in `FEATHERAUTH_CONFIG_DIR`, as for the other commands. Each table is read in key order by byte (SQLite's default order, and Postgres with the `C` collation); rows that come out of that order fail the copy with exit `1`. A row is encoded column by column, in the column order of the migrations: one byte `0` for a null or `1` for a value, the length of its canonical text as 8 bytes big-endian (`0` for a null), then the text. A table's checksum is the SHA-256 of its encoded rows, and it is computed the same way for the source and the target. The output has one line per table, in copy order: `<table> <rows> ok` when the target matches, or `<table> <source rows> <target rows> differs` when it does not. A copy whose tables all match ends with `copied` on its own line. A difference rolls the target back and exits `1` without `copied`.

**CLI.** Every command that opens the database (`user`, `session`, `import`, `db copy`) works on both drivers through `database.yaml`.

**Concurrent writes.** On SQLite one write connection puts all writes in a row. Postgres has no such queue, so the Postgres store keeps the rules of Sessions and refresh rotation and Code reuse with row locks. Write transactions run at `READ COMMITTED`. A write transaction that decides on a row (the login code, the refresh token presented, the login in progress, the handoff, the user) reads it with a row lock (`SELECT ... FOR UPDATE`), so a second transaction for the same row waits and then sees what the first one did: of two exchanges of one code the second finds it used, and of two refreshes with one token the second finds it rotated and, inside the grace window, gets its own successor. Rows that may exist only once (a verified email, a provider identity, a remembered event id, the one handoff of a login) rely on their unique keys. A transaction that Postgres ends with a deadlock or a serialization failure (SQLSTATE `40P01` or `40001`) is run again from its start with its results reset, at most 3 runs in all; the next run sees the rows the other transaction wrote. If the third run fails the same way, the request is answered as an unavailable store (`503`). A unique-key violation on one of the once-only keys (SQLSTATE `23505`) is the exception to the 3-run rule: it is run again once, the next run finds the row the other transaction wrote, and a second violation is the conflict (`ErrConflict`, as for any duplicate), not `503`, because then the key is taken, not the store busy. Only `40P01` and `40001` use all 3 runs and end in `503`. A caller that maps such a violation to its own conflict inside its transaction (linking an identity that is linked already, an admin change that gives an email a second verified holder) is not run again: the violation means the other transaction committed the same key, so the next run would conflict in the same way. The rule is the same on both drivers; SQLite never returns these SQLSTATEs. Read transactions run at `REPEATABLE READ, READ ONLY`, so one read sees one state, as on SQLite. The CLI uses the same store and the same rules. The store contract suite tests this with concurrent requests on both drivers.

The same tables, columns, keys and indexes as the Data model, with the nearest Postgres types (`text`, `bigint`, `boolean`); ids and times are still generated in Go. Migrations are shared, with a Postgres file only where the SQL differs. Migrations run at startup as on SQLite; on Postgres they run under a session advisory lock, so that several processes starting together apply them once (Processes, and More than one instance).

## Backup

- The service writes a consistent snapshot with `VACUUM INTO`, safe while running (FR-24). Copying the live file with `cp` is not safe.
- Snapshots go to `backup.directory` as `featherauth-YYYYMMDD-HHMM.db` at `backup.at`; the newest `backup.keep` are kept and older ones deleted (FR-59). `featherauth backup` takes one on demand (cron or before a deploy). The schedule runs on the service's clock at `backup.at` in server local time (today if that minute is still ahead, otherwise tomorrow), creates `backup.directory` when it is missing, and is off when `backup.directory` or `backup.at` is empty. A snapshot that fails (a full disk, a snapshot of that minute that exists already) is logged at `error` level with the reason, leaves any older snapshot alone, and the schedule tries again the next day; it never stops the service.
- The off-server copy is done by a host cron job, `deploy/ops/backup-offsite.sh`; the service holds no credentials for the external location (OPS-07). The script encrypts the newest snapshot with `age -r <public key>` before it copies it with `rclone` or `rsync`, because snapshots hold emails, names and identity links. With `CONFIG_DIR` set it also encrypts a tar of the configuration directory (which holds the key files) and copies it as its own file, `featherauth-config-YYYYMMDD-HHMM.tar.age`; nothing is copied in clear. `BACKUP_DIR` names the snapshot directory (default `/var/backups/featherauth`, the path inside the container). The script only adds files at the destination. Only the public key is on the server; the private key is kept off the server and used only to restore.
- Provider refresh tokens are encrypted at rest; the encryption key files (`secrets.encryption_key_files`) are server secrets kept apart from the data and backed up separately. A snapshot without its key cannot be used to revoke the stored tokens.
- The config directory is backed up by the same cron job.
- Restore: stop the service, decrypt the copy with the private key, copy the snapshot to `sqlite.path`, start (OPS-08). Rehearse it after any schema change.
- The built-in snapshot (`VACUUM INTO`) is for SQLite only. With `driver: postgres` the `backup` options are not used, no schedule runs, and `featherauth backup` exits `1` with a message that names `pg_dump` (OPS-09). The guides give a `pg_dump` cron job that pipes the dump into `age`, so that no clear copy is written, and fails when `pg_dump` fails (`bash -o pipefail`), with a restore by `pg_restore` (OPS-07, OPS-08).
- The database, the local snapshots and the Postgres volume hold emails and names in clear; only the off-server copies are encrypted, so the guides tell the operator to encrypt the host's disk (OPS-19).

## User administration and import

- **CLI:** `featherauth serve` (no arguments) starts the service in the order of the Restart specification (open the database, apply migrations, load the configuration, open the listener), writes its JSON logs to standard output, reloads on `SIGHUP` and on file changes, and on `SIGTERM` or `SIGINT` shuts down as the Restart specification says; it exits `1` with the reason on standard error when it cannot start. `featherauth user get|list|update|disable|enable|delete|link|unlink <realm> ...`, `featherauth import` and `featherauth backup` open the database named in `database.yaml` in `FEATHERAUTH_CONFIG_DIR` directly, so they run where the data volume is: on the host for a plain install, or inside the container (`docker compose exec featherauth /featherauth user ...`; the binary is `/featherauth` in the image). They may run while the service runs: SQLite serializes the two processes' writes (WAL mode and `sqlite.busy_timeout`), and the service reads users from the database on every request, so a change applies at once. Each change writes its `audit_events` row with actor `admin` and prints the audit line to standard error. The service opens no admin port, answers no `/admin` path and has no admin HTTP API (SEC-17). `featherauth keys generate [--type rsa|ec|encryption] [--bits N] <file>` writes a new key to `<file>` with mode `0600` (default: RSA, 2048 bits). It refuses to overwrite: if `<file>` already exists it fails with exit code 1 and leaves the file unchanged. Every command exits `0` on success, `1` on failure (including `config check` errors) and `2` on a usage error. `config init <dir>` writes every file of `deploy/config.example/` (embedded in the binary): `server.yaml`, `server.tls.yaml.example`, `database.yaml`, `realms/example.yaml` and `locales/en.yaml.example`, with mode `0644`, creating the directory and `realms/` and `locales/` with mode `0755` when missing, and prints `wrote <path>` for each. It writes no secret or key file. It first checks every target and fails with exit code 1, writing nothing, when any of those files exists already; a file that appears between the check and the write is not overwritten either. `config check <dir>` prints each diagnostic as `file:line: severity: field: reason` on its own line to standard output, and `ok` when there is none; it exits `1` when any is an error and `0` when there are only warnings. `keys generate` writes an RSA or EC P-256 key as a PKCS 8 PEM file, or an encryption key as 44 base64 characters, creating missing parent directories and printing `wrote <file>`; `--bits` is for `--type rsa` only, must be 2048 or more, and any other value, a type other than `rsa`, `ec` or `encryption`, an unknown flag or a wrong number of arguments is a usage error. The user commands take the realm first: `user get <realm> <id>`, `user list <realm> --email <address>` (users whose email equals the address ignoring case and spaces), `user update <realm> <id> [--name <text>] [--email <address>] [--email-verified true|false] [--disabled true|false]` (at least one flag; `--disabled` disables or enables the user in the same transaction as the other changes, with its own audit row; when a new `--email` clears `email_verified` and `--email-verified` is not given, a notice on standard error says so and names `--email-verified true` as the way to keep it), `user disable|enable|delete <realm> <id>` and `user link|unlink <realm> <id> <provider> <subject>`. `get` and `list` print JSON (`id`, `email`, `email_verified`, `name`, `disabled`, `created_at`, `updated_at` and, for `get`, `identities` as `{provider, subject}`); a change prints nothing but its audit line on standard error. A user, realm or identity that is not found, a conflict and an invalid value exit `1`. The session commands take the realm first as well. `session list <realm> <user id>` prints a JSON list of the user's active sessions, one object each with `session_id`, `client_id`, `started_at`, `auth_time`, `last_used_at` and `expires_at`; a session is active when it has a refresh token that is neither revoked nor expired at the time of the command. Its times are those of its newest active refresh token: `started_at` and `auth_time` as the session has them, `last_used_at` when that token was created and `expires_at` when it expires, written as `user get` writes times. The list is ordered by `started_at`, then by `session_id`, and a user with no active session gets `[]`. `session revoke <realm> <user id>` revokes every active session of the user, and `session revoke <realm> <user id> --session <id>` revokes one; each run that ended at least one session writes one `user.sessions_revoked` row (actor `admin`, details `{sessions}`, the number of sessions ended). `session revoke <realm> --all` (no user id) revokes every active session of the realm, of every user, for the emergency key rotation (Runtime configuration, Emergency key rotation: the sessions that a forged token could have made); it writes one `realm.sessions_revoked` row (actor `admin`, no user id, details `{sessions}`) when it ended at least one. A session id that is not a session of the named user, or is unknown, exits `1` and changes nothing. A session of the user that is not active (revoked or expired) exits `0` and changes and audits nothing, as does a revocation when no session is active; a revocation prints nothing but its audit line on standard error. `--all` together with a user id or `--session`, a missing or empty `--session` value, and any other wrong argument are usage errors (exit `2`). `user delete` loads the configuration to revoke the stored provider tokens at their providers. When the configuration cannot be loaded, or its encryption key cannot be used, it exits `1` with the reason on standard error and deletes nothing; `user delete <realm> <id> --skip-revocation` deletes anyway, without revoking, and logs a warning that the provider tokens are not revoked. `featherauth import <file> --realm <name> [--include-without-identity]` (the file may also come after the flags) needs a valid configuration directory and a realm that is in it, so a reserved or misspelled realm name is refused before anything is written, and when the configuration is invalid it prints the diagnostics (file, line and reason); it prints a JSON report `{created, existing, skipped}`, where `skipped` lists the numbers of the rows skipped, and one audit line for each user written on standard error. A file that fails validation, a conflict, an unknown realm and an unreadable file exit `1` and write nothing. `featherauth backup` writes one snapshot to `backup.directory` (created when missing), keeps the newest `backup.keep`, prints `wrote <path>`, and fails with exit `1` when `backup.directory` is empty or a snapshot of that minute exists already. `healthcheck` sends `GET /readyz` to the listen address (`FEATHERAUTH_LISTEN`, else `listen` of `server.yaml` in `FEATHERAUTH_CONFIG_DIR`; a missing host means `127.0.0.1`) with a 3 second timeout, prints `ready` and exits `0` on a `200` answer, and exits `1` on any other answer, on an error or on the timeout.
- **Sealed provider tokens by key id (SEC-43, SEC-47).** Three commands find and remove the stored provider tokens an encryption key sealed, so that an exposed key can be removed on evidence. A stored value is "sealed by key id `<id>`" when its text starts with `<id>.` (the layout of Runtime configuration, Sealed provider tokens); the commands match that prefix and never decode the rest to decide. The match is a scan of the realm's identities with a stored value; no index is added. `<id>` must be exactly 8 lowercase hex characters; any other value, a missing or repeated `--key-id`, a missing realm, an unknown flag or an extra argument is a usage error (exit `2`). An unknown realm exits `1`, as for the other commands. They open the database named in `database.yaml`, like the `user` commands, and may run while the service runs.
  - `featherauth keys sealed <realm> --key-id <id>` prints a JSON list of the identities of the realm whose stored token that key sealed, one object each with `user_id`, `provider` and `subject` (the provider's subject, as `user get` prints identities), ordered by `user_id`, then `provider`, then `subject`; `[]` when there is none. It never prints a token or any part of a stored value. It reads no encryption key, so it works for a key id that `secrets.encryption_key_files` no longer lists. It writes one audit row, action `keys.sealed_listed`, actor `admin`, no user id, details `{key_id, identities}` (the number listed), also when the list is empty, and prints its audit line on standard error. Exit `0`.
  - `featherauth keys reseal <realm> --key-id <id>` loads the configuration (as `user delete` does) and needs the key `<id>` among `secrets.encryption_key_files` and a first key whose id is not `<id>`: otherwise it exits `1`, changes nothing, and says why on standard error (`key <id> is not in secrets.encryption_key_files`, or `key <id> is the first key; add a new first key before resealing`). For each identity of `keys sealed`, it decrypts the value with key `<id>`, encrypts the token under the first key (a new nonce), and replaces the value in one write transaction with its audit row: action `identity.token_resealed`, actor `admin`, the user id, details `{provider, from_key, to_key}`. A value that does not decrypt is left as it is and counted as failed, with no audit row.
  - `featherauth keys clear-sealed <realm> --key-id <id>` sets the stored value of each identity of `keys sealed` to none in one write transaction with its audit row: action `identity.token_cleared`, actor `admin`, the user id, details `{provider, key_id}`. It reads no key and revokes nothing at the provider (that needs the key; `keys reseal` keeps the token usable for a later revoke instead).
  - Both change commands replace a value only if it is still the value they read (`... WHERE id = ? AND provider_refresh_token_enc = ?`), so a token the service replaced or dropped in the meantime (a new Apple login, `consent-revoked`, a deletion) is left alone and counted as skipped, with no audit row. A run that ends part way leaves every finished identity done and audited, and running it again does the rest. They print a JSON report on standard output, `{"resealed": n, "skipped": n, "failed": [...]}` or `{"cleared": n, "skipped": n}`, where `failed` lists `{user_id, provider, subject}`, and the audit lines on standard error. `keys reseal` exits `1` when `failed` is not empty and `0` otherwise; `keys clear-sealed` exits `0` unless the store fails. A store failure exits `1` and, for the identity in progress, changes nothing. After either command `keys sealed` for that key lists no identity in the realm, unless values failed to reseal.
  - The emergency key runbook of the user guide uses them for an exposed encryption key: add a new first key and restart, run `keys sealed` in each realm, then `keys reseal` (or `keys clear-sealed`), then remove the exposed key and restart again.
- A script may change `name`, `email`, `email_verified` and `disabled`. `sub` and `realm_id` are immutable. An email is stored trimmed of surrounding spaces, as `email_key` is. Changing a user's email to a different address (a different `email_key`) sets `email_verified` to false unless the same change sets it, because a verification belongs to the address it was given for and a verified email feeds auto-linking (SEC-04); an empty email is stored as none, and `email_verified: true` needs an email.
- Disabling a user revokes all their sessions and rejects new logins at once; enabling them again does not bring the sessions back, so they sign in again. Issued access tokens live until they expire (SEC-14).
- Every change is audit-logged in `audit_events` and the log (who, when, what; never secret values or emails), and so are the changes the service makes by itself: auto-links and the actions taken on provider account events. Auto-links use the action `identity.auto_link`, with the actor `provider:<key>` of the provider that logged in and the details `{provider}`; a provider's `consent-revoked` event writes `identity.consent_revoked` (details `{provider}`), and its `account-delete` event writes `user.delete` or `identity.unlink` as described in Provider account events, all with the actor `provider:<key>`; the administration operations write `user.update` (details `{fields}`, the names of the changed fields, never their values; a change that alters nothing writes nothing), `user.import` (one row for each user an import writes), `user.delete`, `user.disable`, `user.enable`, `identity.link` and `identity.unlink` (details `{provider}` for the identity actions and `{revoke_at_provider}` for `user.delete`; no emails), `user.sessions_revoked` and `realm.sessions_revoked` (details `{sessions}`; the session commands of this section), `identity.sessions_revoked` (details `{provider, event}`, written by a Google security event that ended at least one session; Google Cross-Account Protection), with the actor of whoever asked (`admin` for the CLI, `provider:<name>` for a provider event, `system` otherwise). `featherauth backup` changes no data and writes no audit row. Disabling or enabling a user who is already in that state changes and audits nothing, and `identity.link` is refused when the provider identity is already linked to any user (unlink it first). A failure of the provider revoke at deletion, or a provider that has no revoker, is logged as a warning like an undecryptable token and never stops the deletion. `session.reuse_detected` (actor `system`, details `{client, session, kind}`) is written when a reuse ends a session (Sessions and refresh rotation). The key commands write `keys.sealed_listed`, `identity.token_resealed` and `identity.token_cleared` (Sealed provider tokens by key id). Audit rows are kept; the hourly job never deletes them (FR-60).
- **Import:** `featherauth import <file> --realm <name>` reads a JSON list of `{id?, email, email_verified, name, disabled, identities: [{provider, subject}]}`. Ids are kept when given, so an existing `sub` survives; a row without an `id` gets a new one in the realm's `user_data.id_format`. The run is idempotent, prints a report, and writes nothing if the file fails validation. Users with no identities are skipped unless `--include-without-identity` is given; such users are linked by email at their first social login under the auto-link rule (SEC-04): both emails verified and on an auto-link domain. Importers for specific systems convert their export to this format. A leading UTF-8 byte order mark in the file is ignored. Validation covers the whole file before anything is written: it must be a JSON list; an `id` may not be given twice nor have surrounding spaces; `email_verified: true` needs an `email`; a user without identities needs an `email`; an identity needs a `provider` and a `subject` and may not be given twice; two users in the file may not hold the same verified email. A user that exists already (by `id` when given, else by one of its identities, else, with no identities, by email) is left as it is and counted as existing. A new user whose verified email another user of the realm already holds, or whose `id` or identity exists already for another user, fails the whole import. The realm's row is created when it has none. Each user written gets one `user.import` audit row. The report lists the users created, the users that existed and the numbers (from 1) of the rows skipped.

## Performance verification

The performance and size targets are NFR-01 to NFR-14 of REQUIREMENTS.md. This section says how they are measured (Load verification), what the recorded baseline is, and the estimate behind them (Capacity estimate). Moving to Postgres changes only the repository package and `database.yaml`; the code is kept small enough to audit by using no web framework and only the modules of the Tech stack (NFR-14).

### Load verification

The run is repeated before each release that changes request handling, dependencies or the database layer, and its results are recorded with date, commit and machine (NFR-13).

1. **How it runs.** `make load` runs `TestLoadScenarios` (`deploy/load_test.go`, build tag `load`) for SQLite, and `make load LOAD_DRIVER=postgres` runs `TestLoadScenariosPostgres` with the same scenarios, seeding and checks. The compose stack and the k6 script are in `deploy/load/`; every image there is pinned by digest. The load generator is k6 1.4.2 (`grafana/k6`), run in docker; the proxies are Caddy 2.11.9 and nginx 1.28 with the proxy examples of `deploy/` (the images the proxy checks use). One run at a time: every run uses the one compose project `featherauth-load`, with its fixed ports, subnet and container names, and starts by removing what a previous run left there, so a second run would stop the first and both would measure each other's load. The first load stack of a test process therefore takes an exclusive lock (`flock`, without waiting) on the file `featherauth/load.lock` under the user's cache directory (Go's `os.UserCacheDir`, created when missing) before it removes or starts anything, and holds it until the process exits; the system drops the lock when the process ends in any way, so a run that crashed or was interrupted never blocks the next one, and its leftover containers are removed as before. When the lock is held, the run fails at once, before touching docker, with `another load run is using the compose project featherauth-load (lock <path>); wait for it to end`. It is a failure, not a skip, so that a refused run is never read as a passed one. The lock sees runs of the same user on the same machine, which is how the load run is made (Results); `TestLoadLockRefusesASecondRun` (`deploy/load_lock_test.go`, built only on the systems whose `syscall` package has `Flock`, `darwin || dragonfly || freebsd || illumos || linux || netbsd || openbsd`, not on the rest of `unix` (`aix`, `solaris`) or Windows; `load_test.go`, which takes the lock, carries the same list with its `load` tag; no `load` tag on the lock test, so `make check` runs it) proves it on a lock file in a temporary directory: a second take while one is held fails with that message and changes nothing, a take after the release succeeds, and a take after the holding process (a helper process of the test binary that took the lock and reported it) was killed succeeds.
2. **Environment.** The real image, in a container limited with `cpus: 1` and `mem_limit: 512m`, with Caddy in front; the proxies, k6 and the mock identity provider run on the same machine. `public_url` is `https://auth.example.com`, the log level is the default (`info`), and `rate_limit.per_ip_per_minute` is `0` (the load comes from one address), except in the rate limiter scenario. The database is seeded with 1,000 users, each logged in through the mock identity provider so that it holds a refresh token; the public client rotates the token on use, so each scenario is seeded again. On Postgres, the database is Postgres 18 (the image of `compose.postgres.yaml`) in its own container on the same host, without a resource limit, measured apart from the service; the `postgres` block uses `sslmode: disable` on the compose network and the default pool of 20 connections.
3. **Load.** Each k6 virtual user owns one seeded user and its refresh token.
   - **Idle:** the service restarted on the seeded database, warmed with one discovery and one JWKS request, then 60 seconds with no traffic.
   - **Steady:** 20 iterations a second for 10 minutes (about 23 requests a second, because a login iteration is four requests): 40% refresh, 35% userinfo (with the access token of the last refresh), 20% JWKS, 5% a whole login (authorize, the mock identity provider, callback, code exchange).
   - **Held peak:** 1,000 connections in a closed loop (each sends its next request as soon as the last is answered) taking `/token` (refresh), `/userinfo` and `/jwks.json` in turn, for 5 minutes, with latency recorded per endpoint.
   - **Burst:** 1,000 refreshes sent at the same instant, one per connection (NFR-04).
   - **Soak:** the steady load for 1 hour; memory "does not grow" (NFR-08) when the mean `VmRSS` of the last tenth of the minute samples is at most 20% above the mean of the second tenth (the first tenth is the start-up, while the heap settles).
   - **Restart under load:** the steady load through Caddy for 2 minutes, with `docker compose restart featherauth` a third of the way in.
   - **Restart loops:** 20 refreshes through each example proxy, one every 10 ms, while `docker compose restart featherauth` runs (`TestLoadRestartLoop`); the loop continues past 20 until the restart is over and an answer came after it. Caddy passes with no failed request and the slowest answer under 10 seconds; nginx passes when the service answers again within 5 seconds of the first `502` (NFR-11).
   - **Rate limiter:** the default limit, the steady load for 10 minutes through nginx, which appends a different peer address to the `X-Forwarded-For` header k6 sends for every request, with `trusted_proxies` naming the compose network; it measures the limiter's own cost.
   - **Startup:** `docker stop`, `docker start` and the first answer of `featherauth healthcheck`, docker's overhead included (NFR-10).
4. **Measure.** Memory from `/proc/1/status` of the service process (`VmRSS` sampled during the run, `VmHWM` read 30 seconds after the held peak, which is the figure compared with NFR-07); CPU from `docker stats`; percentiles from k6 (at the client, through Caddy) and from the service's own request log (`duration_ms`). The login overhead (NFR-05) is bounded from above by the sum of the service's p95 for authorize, callback and `/token`. Also recorded: error rate and SQLite busy lines. The service has no `pprof` endpoint, so goroutines are seen through thread counts, stack sizes from `GODEBUG=gctrace=1` and open file descriptors.
5. **Record.** The latest run is recorded in the load section of `docs/RESULTS.md`, the one file that holds the latest run of the load test, the conformance suite, the browser checks and the release gate. The load section holds the date, the commit and the machine, a result for each scenario of step 3 on SQLite and on Postgres, and the k6 version; a test run by `make check` checks that these are there and that the recorded k6 version is the pinned one. Only the latest run is kept.
6. **Decide.** The thresholds of `deploy/load_test.go` are the figures of NFR-01 to NFR-11 as REQUIREMENTS.md publishes them, per driver where they differ (for the held peak: on SQLite userinfo p95 under 3 ms, JWKS p95 under 2 ms and refresh p99 under 15 seconds; on Postgres userinfo p95 under 5 seconds, JWKS p95 under 64 ms and refresh p99 under 7 seconds; for the burst, refresh p99 under 3 seconds on both). A measurement at or above its figure fails the run. There is no recorded-miss line and no margin above a figure: a target set from a measurement was set at the figure measured then plus 20%, so a further margin would let a run pass above the requirement, and the target itself is the regression guard. A failed run is investigated (profile, `GOMEMLIMIT`, goroutine leaks) and either fixed or taken to the requirements owner, who may set a new figure in REQUIREMENTS.md; the test then follows that figure.
7. **Knobs.** `GOMEMLIMIT` and `GOGC` (process environment) and `sqlite.read_connections`. SQLite's `cache_size` and `mmap_size` are not options. Measured on 60-second held peaks: `GOGC=25` lowers the resident memory to about 75 MB at a cost of about 5% of the throughput; `GOMEMLIMIT=48MiB` to about 67 MB at a cost of more than half the throughput; `sqlite.read_connections` of 1 or 2 changes neither memory nor throughput within the run-to-run spread.

**Results.** The figures of the latest run are in `docs/RESULTS.md` (load section) and nowhere else; the "Measured" column of REQUIREMENTS.md copies them. The runs are made on a developer machine with the service limited to 1 CPU (whose single core is faster than most VPS cores); no run on a VPS is planned.

What the measurements showed (these findings explain the targets and do not change from run to run):

- **Held peak refresh tail (SQLite).** All 1,000 connections wait for a refresh, because `/userinfo` and `/jwks.json` are answered in about a millisecond. About 400 refreshes a second fit the Capacity estimate (250 to 500), and the p50 of 1.75 seconds fits a queue of 1,000; the tail does not (p95 7.5 s, p99 11.5 s), while the burst's largest wait is 2.2 seconds. The writes go through one SQLite connection, and `database/sql` hands a freed connection to a random waiting request rather than to the one that waited longest; that is consistent with the spread but not proven (no `pprof`).
- **Held peak userinfo (Postgres).** The wait is the one saturated CPU, shared with the refreshes' RSA signing and applied to each round trip to Postgres: a pool of 100 connections instead of 20 did not change it, Postgres had one or two active backends and used about a quarter of a CPU, no lock waits were seen, and `/userinfo` runs one read-only transaction. More capacity comes from a second CPU or `tokens.algorithm: ES256`.
- **Readiness under saturation.** A readiness ping through the write connection (SQLite) or through the shared pool (Postgres) waited behind the queued refreshes until the health check's 3-second timeout, so `/readyz` answered `503` under the peak. Therefore the ping uses the read pool (SQLite) or a connection of its own (Postgres) (Health endpoints); `TestPingDoesNotWaitForTheWriteConnection` holds the write connection busy and requires the ping to succeed. A `/readyz` answer slower than 3 seconds is a defect to fix, not a reason to loosen the check.
- **Peak memory.** The Go heap and goroutine stacks explain about 45 MB of the 90 to 100 MB of the held peak (`gctrace`: heap at most 40 MB at a collection, 18 MB live after it, stacks at most 5 MB); the rest is the runtime's own memory, memory freed but not yet returned, SQLite's allocations outside the Go heap and the binary.
- **Soak memory.** The live Go heap stayed under 1 MB, threads (8) and file descriptors did not grow, and the WAL stayed at 4.19 MB. The resident memory rose with the database size (about 0.2 MB of anonymous memory per MB of database, consistent with SQLite's page cache filling) and stayed flat for 10 minutes of read-only load with no new rows. A plateau was not reached at the largest size tested (14.8 MB of database).

### Capacity estimate

Back-of-the-envelope figures behind the targets, set against the measured results (`docs/RESULTS.md`). They include every behaviour in this document.

**Memory.** The service keeps almost no state of its own: each request reads or writes SQLite and builds a few small JSON documents. The checks (token types, PKCE downgrade, mix-up, per-login cookies, provider events, login hints) are code paths and a few columns, not resident data.

| Part | Idle | 1,000 concurrent requests |
| --- | --- | --- |
| Go runtime, the binary's code in use, built-in templates and logos | 10–15 MB | the same |
| SQLite page cache (about 2 MB per connection at the default `cache_size`, filled as pages are read; one write connection and `sqlite.read_connections`, default 4) | 1–3 MB | up to 10 MB |
| Per connection: goroutine stack (8–32 KB) and read and write buffers (8 KB) | none | 16–40 MB |
| Request and response data, JWT and JSON building, freed after each request | none | a few MB |
| Caches: realm configs, signing keys, provider keys and discovery, rate-limiter entries | under 1 MB | under 1 MB |
| **Total** | **about 12–20 MB** | **about 30–60 MB** |

So the idle target (under 30 MB, NFR-06) has room, as measured (20 to 23 MB). The estimate for 1,000 concurrent requests is too low: the held peak measured about 93 MB on both drivers, within NFR-07 (under 120 MB); the difference is memory outside the Go heap (What the measurements showed, Peak memory). `GOMEMLIMIT` makes the garbage collector work harder rather than letting the heap grow past it. TLS ends at the proxy, which keeps its buffers out of this process.

**CPU.** One RSA-2048 signature costs roughly 1 ms of CPU in Go, and one ES256 signature roughly 0.03 ms. A refresh signs an access token and an ID token (and a JWT refresh token with `refresh_token_format: jwt`) and commits one SQLite transaction: about 2–4 ms of CPU. One vCPU therefore finishes roughly 250–500 refreshes a second; the held peak measured about 360 a second on SQLite. `/userinfo` verifies one signature (cheap with RSA) and reads one row; the JWKS and discovery are prepared in memory.

**SQLite.** Every refresh writes. The service's writes go through one dedicated write connection, so they queue in Go rather than retrying on `SQLITE_BUSY` (an occasional CLI command, a separate process, waits on SQLite's lock up to `sqlite.busy_timeout`), and WAL mode with `synchronous=NORMAL` keeps each commit short; a few thousand small transactions a second is typical, well above the signing limit.

**What this means for the targets.**

- **Expected load:** 5,000 logins a day plus a refresh per active user every 15 minutes is under 5 requests a second on average. The steady test's 20 a second uses under 10% of the CPU, and p95 under 50 ms is comfortable.
- **1,000 simultaneous requests:** the service survives them without errors and within the peak memory target (NFR-02, NFR-07), but 1,000 refreshes at the same instant need 2–4 seconds of signing on one vCPU, so the last ones wait that long: the burst measured a refresh p99 of 2.5 seconds on SQLite and 2.7 seconds on Postgres, within NFR-04's 3 seconds. That is a property of RSA signing on one core, not of the features in this document; signing every ID token with RS256 adds an RSA signature only in an ES256 realm. When 1,000 connections are held busy, the refresh tail grows (p99 of 11.5 to 12.6 seconds on SQLite and 5.7 to 5.9 seconds on Postgres across runs, within NFR-04's 15 and 7 seconds) and, on Postgres, `/userinfo` waits for the same CPU after each round trip to the database (p95 3.7 seconds, NFR-03). The service answers `/jwks.json` in hundredths of a millisecond, but on Postgres it takes tens of milliseconds at the client (p95 of about 50 ms, within NFR-03's 64 ms), because each request's new proxy connection (Proxy connections) waits its turn on that saturated CPU.

## Deployment and operations

**Docker.** Multi-stage build with `CGO_ENABLED=0`, static binary on distroless or scratch, non-root; the image holds only the binary (OPS-01). `compose.yaml` runs `featherauth` alone, with its port published on `127.0.0.1` only (OPS-16), so it sits behind an existing reverse proxy; `compose.caddy.yaml` adds Caddy for hosts without a proxy. The data volume holds the SQLite file and backups; the config directory is mounted from the host. `compose.yaml` takes `FEATHERAUTH_CONFIG`, optional, the host directory mounted read-only at `/etc/featherauth` (default `./config`), and `FEATHERAUTH_TAG`, the image tag, which has no default: without it compose stops with a message that names it (OPS-03). The health check is `featherauth healthcheck` (calls `/readyz`), run every 10 seconds with a 5 second timeout and a 5 second start period; the container is reported unhealthy after 6 failed checks in a row (`--retries=6` in `deploy/Dockerfile`, OPS-12). Every shipped compose file that runs the service gives it `stop_grace_period: 35s`, so that docker waits for the 30-second drain before it kills the process (Restart specification, Stop timeout). `compose.yaml` runs the service with a read-only root filesystem (`read_only: true`), no Linux capabilities (`cap_drop: [ALL]`) and `security_opt: ["no-new-privileges:true"]` (SEC-31). It also mounts a `tmpfs` at `/tmp` for SQLite's temporary files. The data volume, the backups volume, the read-only config mount and that `tmpfs` are the only paths it uses. `deploy/compose.postgres.yaml` is an optional file, like `compose.caddy.yaml`, that adds a Postgres container with its own volume and a password file. Its `postgres` service uses the official image pinned by version and digest, keeps its data in the named volume `postgres-data` and publishes no port, so only the compose network reaches it; it reads the password from `secrets/postgres_password` in the configuration directory (the file `postgres.password_file` names), mounted read-only into the container, and is healthy when it answers on TCP. The `featherauth` service waits for that health check. Under SEC-09 the file should have mode `0600` and be readable by uid 65532 (the service's user), which should own it: the loader checks the mode bits only (a group or other bit is an error with `strict_permissions`, a warning with `strict_permissions: false`), not the owner. Plain text on the private compose network is accepted: the container serves no TLS in this file, the `postgres` block uses `sslmode: disable`, the traffic never leaves that network, and the container publishes no port. TLS is for a Postgres reached over another network: there the `postgres` block uses `verify-full` with `postgres.root_cert_file`, or `require`. 

**Hardened Postgres service (SEC-44).** The `postgres` service of `compose.postgres.yaml` and of `compose.ha.yaml` (the shipped files that bundle Postgres; the load and conformance stacks are test stacks and keep the image's defaults) runs with `read_only: true`, `security_opt: ["no-new-privileges:true"]`, `cap_drop: [ALL]` and `cap_add: [CHOWN, DAC_OVERRIDE, SETGID, SETUID]`. The add-backs are what the image's entrypoint needs, as measured on the pinned `postgres:18` image: it starts as root, reads the password file, which belongs to uid 65532 with mode `0600` (`DAC_OVERRIDE`), takes ownership of the data and socket directories (`CHOWN`), and drops to the `postgres` user with `gosu` (`SETUID`, `SETGID`); `gosu` gains no privilege, so `no-new-privileges` holds. `FOWNER` is not added: the entrypoint's `chmod` of directories it does not own may fail, and it ignores that failure. The writable paths are the data volume `postgres-data` at `/var/lib/postgresql` and a `tmpfs` at `/var/run/postgresql` (the socket and its lock file); nothing else. There is no `tmpfs` at `/tmp`: Postgres writes its temporary files under its data directory, the service starts and serves without it, and SEC-44 asks for only the writable paths Postgres needs. Plain text on the private compose network stays accepted. The ops check of `make ops` proves the list (Test suites outside `make check`).

`compose.caddy.yaml` keeps Caddy's admin API on, because its container's health check uses it, and keeps Caddy's data directory (`caddy_data`, which holds the certificates) on a volume.

**Setup with the image alone (OPS-21).** A host with only Docker writes the initial configuration and every key with one-off containers of the published image, whose entrypoint is `/featherauth`. Each runs as the service's user, with no network, a read-only root, and the configuration directory mounted read-write, which only these containers do (the running service mounts it read-only):

```bash
sudo install -d -o 65532 -g 65532 -m 700 /opt/featherauth/config
run() { sudo docker run --rm --user 65532:65532 --network none --read-only -v /opt/featherauth/config:/etc/featherauth ghcr.io/yyudhistira/featherauth:vX.Y.Z "$@"; }
run config init /etc/featherauth
run keys generate /etc/featherauth/secrets/main/signing-1.pem
run keys generate --type encryption /etc/featherauth/secrets/encryption_key
sudo mv /opt/featherauth/config/realms/example.yaml /opt/featherauth/config/realms/main.yaml
# edit realms/main.yaml (below), then:
run config check /etc/featherauth
```

A realm with `tokens.algorithm: ES256` also needs `run keys generate --type ec /etc/featherauth/secrets/main/signing-ec-1.pem`. The shipped realm example is named `example` and its `keys` entry names `secrets/example/signing-2026-10.pem` (`kid: example-2026-10`), a file `config init` does not write. The reader therefore edits the realm file: `name: main` (it must equal the file name), and the `keys` entry replaced by `{ kid: main-1, file: secrets/main/signing-1.pem, state: active }`; until then `config check` reports the missing key file. The user guide (section 3.2) gives these exact steps. The keys are owned by uid 65532 with mode `0600`, so `strict_permissions` accepts them as the service reads them. The same form writes a new key during a rotation (the key runbook of the user guide), and `keys generate` still refuses to overwrite a file.

The ops check `deploy/ops/check-setup.sh` runs the same containers but writes the RSA key at the example's own path, `secrets/example/signing-2026-10.pem` (and the EC key at `secrets/example/signing-ec-1.pem`), so that the unedited example passes `config check` with the output `ok`; it checks the commands, not the reader's edit.

**Signed images (SEC-42).** `deploy.yml` signs every image it pushes, by digest, with `cosign sign` using the workflow's own identity (keyless, through GitHub's OIDC token; no signing key is stored). It makes a software bill of materials of the image in SPDX JSON with `anchore/sbom-action` and attaches it with `cosign attest --type spdxjson`, and records the build provenance with GitHub's `actions/attest-build-provenance` when the repository is public: GitHub stores build provenance only for a public repository (a private one answers "Feature not available for user-owned private repositories"), so the step is skipped for a private repository, and `gh attestation verify` then has no record to check. The signature and the SBOM attestation are made for every repository. The build job alone gets the permissions this needs: `id-token: write`, `packages: write` and `attestations: write`. The release guide (RELEASING.md) gives the three checks: `cosign verify`, `cosign verify-attestation --type spdxjson` and `gh attestation verify` (with `--signer-workflow` naming `deploy.yml`), with the issuer `https://token.actions.githubusercontent.com` and an identity pattern that matches this repository's `deploy.yml` on `refs/heads/main` and on a release tag `refs/tags/vMAJOR.MINOR.PATCH`.

**Pinned references (OPS-03).** Every action a workflow uses is pinned by commit hash, and every image pulled from a registry (the base images of the Dockerfiles, the compose files of `deploy/`, the load and conformance stacks) by digest; only images the tests build locally carry a local tag. No compose file names a default image tag for `featherauth`: `FEATHERAUTH_TAG` must be set (the deploy and the ops scripts set it), so a host never runs an image nobody chose.

**CI/CD (GitHub Actions).** `ci.yml` on pull requests: `go vet`, `go test`, `govulncheck`. The `ops` job checks out with `actions/checkout`'s `fetch-depth: 0` and `fetch-tags: true`, so that the upgrade tests find the newest release tag (Test suites outside `make check`, Upgrades with no previous release). A new push to a pull request cancels the older `ci.yml` run of that pull request that is still running; no other run is cancelled (a run of `deploy.yml`, with the checks it calls, never is). `deploy.yml` on push to `main`: same checks, build, tag with the git SHA, push to `ghcr.io`. The deploy job that follows is the project's own example pipeline and meets no requirement of its own: it connects by SSH to one host, runs `docker compose pull && up -d`, then waits up to 30 seconds for `/readyz` and rolls back to the previous tag on failure. Operators may use it or deploy the published images their own way; upgrades and rollbacks (OPS-04, OPS-06) rest on the image tags, the migrations at startup and the backups, not on this job. Only SSH credentials are GitHub secrets. The deploy never touches the config directory. The four secrets are `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY` and `DEPLOY_KNOWN_HOSTS` (the host's `known_hosts` line); the directory on the host that holds `compose.yaml` is the repository variable `DEPLOY_PATH`, and the push to `ghcr.io` uses the workflow's own `GITHUB_TOKEN`. The host must be able to pull the `ghcr.io` package (public, or one `docker login` on the host). The deploy touches only the compose files in `DEPLOY_PATH` (`compose.yaml`, or the files named in `COMPOSE_FILE` on the host) and the running stack; the first deploy on a fresh host is manual (`FEATHERAUTH_TAG=<sha> docker compose up -d`). While the repository variable `DEPLOY_PATH` is not set the deploy job is skipped (there is no host yet) and the image is still built and pushed; with `DEPLOY_PATH` set and a secret missing, the deploy job fails.

**Runner.** Every job of `ci.yml` and `deploy.yml` has `runs-on: ${{ vars.RUNNER || 'ubuntu-24.04' }}`. While the repository variable `RUNNER` is not set the jobs run on the GitHub-hosted runner of that exact Ubuntu release (a floating label such as `ubuntu-latest` is never used, so that an image change cannot break a green pipeline without a commit; the release is changed on purpose). To run on the operator's own machine, set `RUNNER` to a label of a registered self-hosted runner, for example `self-hosted`; that runner needs `docker`, `make`, Go and Chrome, which the hosted image has. A label that is not an exact Ubuntu release and is not read from `RUNNER` is not allowed in a workflow file.

**Repeated checks.** The checks of a push to `main` are skipped only when exactly the same tree was already tested successfully by `ci.yml` on a pull request, and the checks of a pushed release tag only when the same commit was already tested successfully on `main` (below). At the end of a successful `ci.yml` run on a pull request, a last job records the git tree hash of the commit it tested (the pull request merged into its base) as a commit status `ci/tested-tree` (state `success`, the hash as the description) on the head commit of the pull request. On a push to `main`, a first job of `deploy.yml` looks for the merged pull request whose merge commit is the pushed commit, reads the newest `ci/tested-tree` status of that pull request's head commit, accepts it only when `github-actions[bot]` created it, and compares its hash with the tree of the pushed commit. When they are equal the `checks` job is skipped and the build and the deploy go on; the job summary says so. In every other case the checks run as before: a direct push, no merged pull request, no such status, a different hash (for example because `main` moved after the pull request's last run), another creator, and an error or a missing answer from the GitHub API (a documentation-only commit follows its own rule below instead). For a pushed release tag the checks are skipped when the tagged commit already has a run of `deploy.yml` for a push to `main` that ended successfully (the same commit, so the same tests already passed there; GitHub's list of workflow runs filtered by that commit); a tag on a commit without such a run runs the checks, so a commit that never passed on `main` cannot be released. Nothing in these lookups can make a failed or missing answer skip the checks. The decision is made by one script, `deploy/ops/tested-tree.sh`, so that it can be tested with a fake `gh`.

**Documentation-only changes.** A change is documentation-only (a documentation change) when every file it changes, under its new and under its previous name, is a documentation file: `README.md`, `CLAUDE.md`, a file whose name ends in `.md` anywhere under `docs/` (today `DESIGN.md`, `REQUIREMENTS.md`, `USER_GUIDE.md`, `RELEASING.md`, `RESULTS.md` and the files under `docs/audits/`), `deploy/ASSETS.md`, `examples/web-app/README.md`, `tools/trace/pending.txt`, or a file under `.claude/`. No build reads these files, and only the tests and tools of the reader set (below) read them, so a documentation change runs the reader set instead of all checks. A change is also documentation-only when every file it changes is in this list or is a Go file (name ending in `.go`, not under `testdata/`, modified in place: not added, removed or renamed) whose change only adds or removes comment lines (`//` lines, and `/* */` comments that open and close within the changed lines) or blank lines, because the compiled code and every test input stay the same. It is a code change when a changed or neighbouring line holds `Covers:` or `Acceptance:` (`tools/trace` reads them; a blank line changed next to such a line would detach it from its test), a build constraint or other directive (`//go:`, `// +build`, `//export`, `//line`, `/*line`), a cgo preamble, a directive or tool line of a test or linter (`Output:` and `Unordered output:` of an Example, `lint:`, `nolint`, `Deprecated:`), a changed line with a backquote, code on the line of a comment, or a block comment that opens or closes outside the changed lines. The decision reads the `patch` of every file of the list; a missing or incomplete patch makes the change a code change. A changed blank or `//` line may be inside a raw string that the patch does not show, so every Go file that passed these checks is also read at the head commit (the contents API, one request per file, none once the answer is false, and none at all when more than 50 Go files qualify: that is a code change, so that a large change cannot use up the rate limit of the token) and is comment-only only when the whole file holds no backquote (no raw string, no struct tag); a failed, empty, malformed or too large answer makes the change a code change. Accepted risks: a comment-only change that `gofmt -s` would reformat (doc comment layout) or that a staticcheck comment rule flags passes without `make check`, and is found by the next run that does. Every other file makes the change a code change, among them every other file under `examples/` (its browser test builds and runs the example). When the list of changed files cannot be read, or may be incomplete (GitHub lists at most 3000 files of a pull request and 300 of a commit), the change is not documentation-only. On a pull request that is documentation-only, `ci.yml` skips the `check`, `browser`, `ops` and `postgres` jobs and records no tested tree, and runs the scan for private keys in tracked files and the `docs` job (the reader set). `ci.yml` takes a boolean input `docs_only` (default `false`) when another workflow calls it; on any event other than a pull request its `changes` job prints `docs_only` equal to that input, so a call without it runs every job. On a push to `main` whose commit is documentation-only, the `tested` job of `deploy.yml` sets its output `docs_only=true` (its `skip` stays `false`), the `checks` job calls `ci.yml` with `docs_only: true`, so only the key scan and the `docs` job run, the `deploy` job is skipped, and the image is still built, so that every commit of `main` has an image; the job summary says so. This holds for a direct push as well, so a release gate commit may be merged through a pull request or pushed straight to `main`. It applies only when the commit before it already has a `deploy.yml` run for a push to `main` that ended successfully (the lookup of Repeated checks for a release tag): a documentation commit on top of a commit that was never tested, or that failed, or the last commit of a push of several commits, runs the checks, so a documentation commit can never make an untested commit look tested. A failed `changes` job gives an empty `docs_only`, which runs every job and skips `docs`. A release tag follows the rule of Repeated checks and is not affected. The decision is made by one script, `deploy/ops/changed-files.sh`, which holds the list above (its `# BEGIN list` block, the one copy of the list) and the comment rule and prints `docs_only`, so that it can be tested with a fake `gh`. The output `slow_skip` and the separate rule for `pending.txt` are removed: that file is in the list.

**Reader set.** The tests and tools that read the repository's own copy of a documentation file. They are listed in one place, the steps of the `docs` job of `ci.yml`, which checks out with `fetch-depth: 0` (`make trace` compares `pending.txt` with `origin/main` and the branch history, and the no-change claims need the history) and runs, in order: `make trace`; `go test -count=1 ./tools/trace/` (the whole package, under a second; `TestRealDesign` and `TestGitBase` read the real files); and `go test -count=1 -run '^(TestConformanceResultsRecordSuiteVersion|TestLoadResultsRecorded|TestReleaseGateNoChangeClaimsHold|TestReleaseCheckBeforeTheTag|TestReleaseCheckAfterTheTag|TestRepositoryHoldsNoSecretFiles|TestConfigReferenceMatchesDesign|TestEveryDocumentedOptionIsReachableFromSnapshot|TestEveryPossibleValueHasARule|TestServerOptionClassesMatchTheDesign|TestProviderOptionsEveryOptionHasAProof|TestSchemaMatchesDesign|TestRunbookCommandsExist|TestRunbookFlagsExistInUsage|TestEmergencyKeyRotationRunbook)$' ./cmd/featherauth/ ./deploy/ ./internal/config/ ./internal/provider/ ./internal/store/`. Between them they read `docs/RESULTS.md` (and recompute every `no change since` claim of the release gate, No-change claims), `docs/DESIGN.md` (the configuration reference, the provider options, the data model, and, through the release-check tests, the Tech stack), `docs/REQUIREMENTS.md` and `pending.txt` (`tools/trace`), `docs/USER_GUIDE.md` (the runbook commands), and the list of tracked files (`TestRepositoryHoldsNoSecretFiles`, which also checks the names of files under `.claude/`). Two `postgres` tests also read `docs/DESIGN.md` (`TestPostgresSchemaMatchesDesign`, `TestCopyCoversEveryTableOfTheSchema`); they need docker and do not run for a documentation change. Accepted risk: a change of the data model section is checked against the SQLite schema by `TestSchemaMatchesDesign` and against Postgres only by the next run of the `postgres` job.

The guard `TestOnlyTheReaderSetReadsDocumentation` (`deploy`, `make check`) replaces `TestNoCodeReadsADocumentationOnlyFile` and keeps the set complete. Go files fall into three classes by their `//go:build` expression. A file is a `make check` file when the expression is absent, or true with the tags `browser`, `ops`, `postgres`, `manual`, `conformance` and `load` off and every other tag on (operating system, architecture and Go version tags count as on, so `!postgres` files and files limited to a list of operating systems are `make check` files). A file that is not, but whose expression is true with `manual`, `conformance` and `load` off and every other tag on, is a tagged file (for example `postgres`, `browser`, or `conformance || load || ops`). Every other file is not scanned: it runs only at a release. A text names a documentation file when it contains the path or the base name of a file of the list (`README.md`, `CLAUDE.md`, `ASSETS.md`, `pending.txt`, `.claude`), the base name of any `.md` file under `docs/`, or a path `docs/...md`. (1) The list in `changed-files.sh` is the list of this section. (2) Every name in the `-run` pattern is a `Test` function in a `make check` file in one of the packages of that step. (3) A `Test` function is a reader when it, or a declaration of its package that it uses directly or through others, holds a string literal that names a documentation file. Such a declaration is a function, a method or a package-level variable or constant (for example `guidePath` of the runbook tests); a method is linked by its name, whatever its receiver, so the link may over-report but never misses a reader. Every reader in a `make check` file must be in the pattern or in `tools/trace`, and a reader in a tagged file must be one of the two accepted `postgres` readers above. `deploy/changed_files_test.go`, `deploy/changed_files_go_test.go` and `deploy/docs_only_test.go` are not scanned: they name the files only as data for `changed-files.sh` and the workflows. (4) No non-comment line of the `Makefile`, a workflow, a file named `Dockerfile` or starting with `Dockerfile` (the image build), a `.sh` file under `deploy/` or `tools/`, a non-Go file under `tools/`, or a Go file that is not a test names a documentation file, except in `tools/trace/main.go` (run by `make trace`), `deploy/ops/changed-files.sh` (holds the list) and `deploy/ops/release-check.sh` (run by `make release-check`, and in `make check` only through the release-check tests of the pattern). Accepted risk: the guard sees a name written in one string literal; a test that builds the name from pieces or reads files by a pattern (for example the walk of `TestEveryImageAndActionIsPinned`, which would read a `compose.yaml` placed under `.claude/`) is not seen, and review catches it.
**Release tags (OPS-01, OPS-02).** `deploy.yml` also runs when a git tag of the form `vMAJOR.MINOR.PATCH` is pushed (digits only, written `vX.Y.Z` below; any other tag, such as `v1.0`, `vX.Y.Z-rc1`, `X.Y.Z` or `vX.Y.Z.W`, does not start it, so no pre-release tag can publish an image). It runs the checks (unless the tagged commit already passed them on `main`, see Repeated checks), builds the image with `featherauth version` reporting the tag name, and pushes it to `ghcr.io` tagged with the tag name only (the commit-SHA tag of a commit that was built from `main` is left as it is). A tag push never deploys: only a push to `main` does. The workflow fails before pushing anything when the tagged commit is not reachable from `main`. A real release tag is never moved or overwritten; a fix is a new tag. A rehearsal tag (digits-only, lower than every real release, for example `v0.0.1`, and never announced, named in release notes or given to operators) may be deleted together with its package version after the checks; only such a tag is a rehearsal, and every other release-form tag falls under OPS-02 and is never deleted. To release, tag a commit of `main` and push the tag (`git tag vX.Y.Z <commit>`, `git push origin vX.Y.Z`; RELEASING.md gives the full steps). `FEATHERAUTH_TAG`, the deploy and the rollback accept a release tag like any other tag. The workflow does not compare versions: the number is chosen by semantic versioning (OPS-20), and `featherauth version` prints the commit hash for an image built from `main` and the tag name for a release image. The `deploy` concurrency group has `cancel-in-progress: false`, but GitHub keeps only one pending run per group, so a tag run queued behind a running push to `main` can be cancelled when another push to `main` arrives; the release guide says to check that the image tag exists after the run.

**Restart specification.** A restart means restarting the FeatherAuth process; in Docker that is the container (`docker compose restart featherauth`, or recreating it with a new image). The host, the reverse proxy and the database stay up. Realm files and the `live` options of `server.yaml` never need one; a new version, the `restart` options of `server.yaml` and `database.yaml` do. The service never restarts itself.

**Why the proxy opens a connection per request (NFR-11, OPS-13, FR-54).** On `SIGTERM` the service closes its listener and, through Go's `http.Server.Shutdown`, at once closes every keep-alive connection that is idle, that is waiting for its next request (requests in flight finish, as Shutdown says). A proxy that keeps idle connections to the service may pick one of them for a request at that same moment: the request is written into a connection the service is closing, and the proxy gets a reset or an end of stream with no answer. A proxy cannot know whether the service read such a request, so it does not repeat a `POST` it has written: Caddy tries again only after a failed dial and, by default, for `GET` (Go's HTTP client repeats on a reused connection only requests without side effects), and nginx does not repeat a non-idempotent request. The client gets `502` at once, although the proxy is set to hold, and a lost `POST /token` is exactly the failed refresh the hold exists to prevent (a release load run on Postgres saw one: a refresh answered `502` after 2 ms during the restart loop through Caddy). With a new connection per request, a request during the restart meets a refused or failed dial, which Caddy holds and tries again (`lb_try_duration`) and nginx answers with the expected `502` of the gap.
- Not chosen: a drain in the service that stops keep-alive at `SIGTERM` but keeps serving for a while before closing idle connections. Go's `SetKeepAlivesEnabled(false)` closes the idle connections itself, so the drain would need its own handling of each response; and it removes the race only when it lasts longer than the proxy's idle-connection timeout (2 minutes in Caddy by default), so it still needs a proxy setting, while it lengthens every stop (the startup measure of the load verification includes `docker stop`, NFR-10) and keeping the listener open would contradict OPS-13 ("stop taking connections").
- Not chosen: proxy rules that repeat a `POST` that failed after it was written (Caddy's `lb_retry_match`). The proxy cannot tell a request the service never read from one it processed and whose answer was lost. A repeated authorization-code exchange is a code replay, and a repeated refresh after `refresh_reuse_grace` (which may be `0`) revokes the session; both sign the user out.
- Accepted residual risk: a connection that the kernel has accepted into the listen queue but the service has not yet taken from it when the listener closes is reset after the proxy wrote its request, and a `POST` on it fails the same way. The window is the time between the handshake and the service's accept, microseconds when the process is not starved of CPU (tens of milliseconds when its CPU is saturated, as at the Postgres held peak), once per restart; the restart loops would show it as a failed refresh, which is then investigated as a new finding.

**Health endpoints (FR-16, OPS-12, OPS-13).** `GET /healthz` answers `200` while the process runs. `GET /readyz` answers `200` when the database answers a ping and `503` when it does not, and `503` from the moment `SIGTERM` arrives. On SQLite the ping goes through the read pool only, so that it does not wait in the queue of the single write connection under load; a failing write (a full disk, a read-only or locked file) shows in request errors and the logs, not in `/readyz`. On Postgres, where one pool serves reads and writes, the ping goes through one connection of its own, outside that pool (Database configuration, Pools and health). `/readyz` is not made cheaper to satisfy the image's health check, because a readiness answer that never touches the database would hide a real outage; under sustained load a late answer is tolerated until 6 checks in a row fail (Docker). `featherauth healthcheck` calls `/readyz` with a 3 second timeout.

**Reverse proxy.** FeatherAuth listens on plain HTTP on a local port and serves all its own pages, so any proxy that ends TLS works. The proxy must open a new connection to the service for every request and keep no idle upstream connection for reuse (Restart specification, Proxy connections), and it must forward `Host`, `X-Forwarded-For` and `X-Forwarded-Proto`; `public_url` decides HTTPS, and `trusted_proxies` decides which proxy addresses may supply the client IP. The client IP is found as follows: if the connection does not come from a trusted proxy, `X-Forwarded-For` is ignored and the connection's address is the client IP; if it does, the header is read from right to left, skipping addresses inside `trusted_proxies`, and the first other address is the client IP. Reading from the right matters because a proxy that appends to the header (nginx's `$proxy_add_x_forwarded_for`) keeps whatever a client sent in front of its own entry, so only the entries nearest the service can be believed. When the proxy runs on the host and the service in a container, the proxy reaches it from the container network's gateway address, not `127.0.0.1`, so list that range, and publish the container port on `127.0.0.1` only so that nothing can bypass the proxy.

- **nginx:** Let's Encrypt with Certbot or a paid certificate, a port 80 server block that answers `301` to HTTPS, and a TLS block that forwards to the service's local port with the headers above and logs with a format that records `$uri`, not `$request`, so query strings with codes and ID tokens never reach the access log (SEC-13, OPS-18). nginx's error log cannot be given a format and records the full request line and upstream URL, query included, when the upstream fails (for example during a restart), so the example sends each server block's error log to its own file at level `crit`, which leaves those lines out. nginx cannot hold requests during a restart (see the Restart specification).
- **Caddy:** Let's Encrypt is automatic, a paid certificate uses `tls <cert> <key>`, `lb_try_duration` holds requests during a restart, and `transport http { keepalive off }` makes Caddy open a connection per request, without which the hold fails for a `POST` (Restart specification). Caddy writes no access log unless a `log` directive is added; if one is, it must drop the query string the same way.
- The `listen ... ssl http2;` form of the nginx example works on nginx 1.24 and 1.28 (the separate `http2 on;` directive is unknown to 1.24).
- Step-by-step guides are in the user guide.

**Rate limit keys (SEC-24).** The rate limit counts per IPv4 address and per IPv6 `/64` prefix (an IPv4-mapped IPv6 address counts as its IPv4 address), because one IPv6 host normally controls a whole `/64`. The log still records the full client address. The limiter remembers at most 100,000 keys (a fixed number, not an option). When it is full, a request from a key it does not hold removes the idle keys (a key not used for a minute; at most once a second) and, if the table is still full, is answered `429`; one warning a minute is logged while that lasts. Accepted risk: an attacker who can send from 100,000 addresses or `/64` prefixes within a minute (a botnet, or one IPv6 `/48`) keeps the table full, and clients not yet in it get `429` for as long as the attack lasts; the cap chooses that over unbounded memory, and a firewall or the proxy is the place to stop such an attack.

**More than one instance (FR-54).** With `driver: postgres`, several service processes may run on one database, which allows a deploy with no failed request.
- What each instance keeps to itself is safe to repeat: configuration (every instance gets the same config directory; a reload is done on each, so for a moment the instances may differ), key and discovery caches, and the hourly cleanup (deletes are harmless twice).
- What must happen once is guarded: migrations at startup run under a Postgres advisory lock, so two instances that start together apply them once and the second waits; the back-channel logout worker claims rows with `FOR UPDATE SKIP LOCKED`, so a notification is sent by one instance.
- What must be shared is in the database: codes, tokens, logins in progress, handoffs, browser sessions, DPoP proofs, remembered events, and the rate limit when `rate_limit.store: database` (with `memory`, each instance counts for itself and the effective limit is the limit times the number of instances; `config check` cannot see the number of instances, so the user guide says it).
- A deploy replaces the instances one after another: each new one must answer `/readyz` before the next old one gets `SIGTERM`; the old one answers `/readyz` `503` at once and drains (Restart specification), and the proxy sends requests only to instances whose `/readyz` is `200`, on a new connection for each request (Restart specification, Proxy connections). `deploy/compose.ha.yaml` runs two instances behind Caddy with active health checks, and `deploy/ops/rolling-deploy.sh` does the replacement. `deploy/Caddyfile.ha` checks `/readyz` of each instance every 2 seconds (`health_uri /readyz`, `health_interval 2s`, `health_timeout 2s`), sends requests round robin, opens a connection per request (`transport http { keepalive off }`), and holds a request with `lb_try_duration 30s` and `lb_try_interval 250ms` alone: it sets no `lb_retries`. Caddy stops trying at whichever of `lb_try_duration` and `lb_retries` is reached first, so a count of tries would end the hold within about a second (three tries 250 ms apart) when both instances are unready at once, for example when the health checks have not yet seen the new instance as ready while the old one drains, or when both are restarted; with the duration alone a request is held, and tried on whichever instance is ready, for up to 30 seconds. The comment at the top of `Caddyfile.ha` says the same: a request that meets an instance being replaced is tried on the other one, and a request that finds no instance ready is held, for up to 30 seconds in both cases. Migrations stay backward compatible with the previous version (Restart specification), which is what lets the old and the new version run side by side.
- SQLite stays one process.

**Shared rate limit (FR-53).** The option `rate_limit.store`: `memory` (default: each instance counts in memory, with the keys of SEC-24) or `database` (`restart`; only with `driver: postgres`). With `database` the count is kept in the table `rate_limits` (`key`, `window_start`, `count`; primary key `key`, `window_start`), one row for each key and minute of the service clock, raised by one statement for each request; the key is that of SEC-24 (the IPv4 address or the IPv6 `/64`). A request is refused when the count of the current minute is above `per_ip_per_minute`. It is a fixed window, not a token bucket, so up to twice the limit can pass around a minute boundary; that is accepted. The hourly job deletes every window older than the current one. The 100,000-key cap of SEC-24 does not apply to the table: an attack from very many addresses costs one small row and one write for each new key, which is accepted for the same reason as there, and the proxy or a firewall is the place to stop it. The statement has a 1 second limit. When it fails or takes longer, the instance counts that request with its in-memory limiter instead and logs the failure once a minute: an outage of the shared count must become neither an outage of login nor no limit at all.

**TLS certificates (OPS-15).** With `tls.mode: none` (the default) the reverse proxy owns TLS: it gets or loads the certificate and ends HTTPS, and FeatherAuth listens on plain HTTP on a local port. With `tls.mode: files` the service ends TLS itself from certificate files (FR-52, SEC-41). `require_https: true` (the default) requires `public_url` to be `https`, so production never runs without TLS, from a proxy or from `tls.mode: files`; plain HTTP is for local development only. A server with no proxy at all uses `compose.caddy.yaml`, which adds Caddy in front, or `tls.mode: files`.

### Logs (SEC-13, OPS-17)

The service writes structured JSON logs to standard output: one line per request (message `request`, with `method`, `path`, `status`, `duration_ms`, `realm` and `client_ip`; the redirect listener of `tls.mode: files` writes none), and lines for every reload result: each diagnostic as `configuration error` (error level) or `configuration warning` (warning level) with `file`, `line`, `field` and `reason`; `realm serves its last good configuration` (warning, with `realm`) for each realm whose file is invalid and which keeps its previous settings; then `configuration loaded` with `realm_count` when the reload applied a configuration (also when some realms kept their previous one, since realms reload independently, FR-18), or `configuration not applied; the last good configuration keeps serving` at error level when it applied nothing (for example a reload that would leave no valid realm; an invalid `server.yaml` or `database.yaml` alone is reported and the realms still reload, so that reload writes `configuration loaded`) and every `restart required` notice (with `options`, the names of the options). Audit records are also log lines, with `audit: true` (Data model). Logs never hold a secret or personal data other than the user id and the client address, at every level including `debug`. Secrets are every token (access, ID, refresh and provider tokens), code, `code_verifier`, `state`, `nonce`, `id_token_hint`, client secret and password, and the `Authorization`, cookie and `DPoP` headers; emails are never logged, and the user id is logged instead, in audit lines too.

All logging goes through one logger, which:

1. hides a value whose key is `token`, `access_token`, `refresh_token`, `id_token`, `id_token_hint`, `code`, `code_verifier`, `state`, `nonce`, `client_secret`, `secret`, `password`, `authorization`, `cookie`, `set_cookie`, `email`, `login_hint` or `dpop` (the `DPoP` header is hidden by it too, as net/http writes it `Dpop`), or ends in `_token`, `_secret`, `_password`, `_email`, `_key`, `_code`, `_hint`, `_authorization` or `_cookie`. Keys are compared after normalizing them (letter case; dashes, dots and spaces as underscores; camelCase split; one trailing `s` ignored, so `X-Auth-Token`, `accessToken`, `user.email` and `cookies` match), at any depth: in groups, in values that expand to groups, when the key or an enclosing group's name is one of these, and in maps of any type (by key where the keys are strings, and in the values of every map whatever its key type), slices, arrays, form values, headers and raw JSON bytes such as a provider's response body (bytes that are not JSON are hidden whole);
2. logs URLs without query, fragment or user information (a username or password inside a URL); the request log records the path only;
3. rewrites the URL inside errors from outgoing HTTP calls the same way.

The logger recognises a secret only by its key, so code passes a secret to it only under such a key, never inside a message or the text of an error. Keys that must stay visible avoid the hidden suffixes: an HTTP status is logged as `status`, an OAuth error code as `error` and a provider as `provider`. The documented proxy configurations log the path without the query string (OPS-18), because codes, `state` and `id_token_hint` travel in query strings. A Prometheus `/metrics` endpoint is on the roadmap of REQUIREMENTS.md; until then the logs are the only measurement.

## Example web app (FR-61, UC-8)

The repository ships `examples/web-app/`: a small React single-page app, built with Vite, that signs a user in to FeatherAuth as a public client with the authorization code flow and PKCE through `oidc-client-ts`, verifies the ID token with `jose`, shows the user's claims, refreshes, and signs out by RP-initiated logout. It is the code a developer copies (UC-8). It is a separate Node project: its dependencies are in its own `package.json` and lockfile, the Go module gains nothing, and Node is needed only to build it and to run its browser test.

**Files.**

```text
examples/web-app/

  example-web-client.yaml   the client entry to copy into a realm file

  vite.config.js       dev server and preview on 127.0.0.1, port 5173, strictPort
```

The default `public/config.json` is `{"authority": "https://auth.example.com/example", "client_id": "example-web", "redirect_uri": "http://127.0.0.1:5173/callback", "post_logout_redirect_uri": "http://127.0.0.1:5173/"}`; the developer edits `authority` to their FeatherAuth's issuer.

**Client entry.** The entry ships with the example, not in the shipped configuration examples: `config init` writes no loopback client into a new configuration. `examples/web-app/example-web-client.yaml` holds the entry below under a `clients:` key and, as its header comment, the one edit that adds it: copy the `example-web:` block under `clients:` of the realm file the quick start uses, then reload (`docker compose kill -s HUP featherauth`, or `SIGHUP`). This is what FR-61's "ready client entry for the quick start configuration" means: a copyable entry for the quick-start realm, shipped with the example. The developer signs in with the provider the quick start configured; no stand-in identity provider ships.

```yaml
clients:
  example-web:                                       # the example web app (examples/web-app); for trying it, not for production
    name: Example web app
    type: public                                     # a browser app cannot keep a secret; PKCE protects the code
    redirect_uris: [http://127.0.0.1:5173/callback]  # loopback: plain http is allowed only on 127.0.0.1 or [::1], never localhost (FR-32)
    post_logout_redirect_uris: [http://127.0.0.1:5173/]
    web_origins: [http://127.0.0.1:5173]             # the app calls token, userinfo, JWKS and discovery from the browser
```

`http://localhost` is refused by validation (Clients), so the app runs on `127.0.0.1`. A public client's loopback redirect may vary in port, but the post-logout return URL matches exactly, so the app keeps the fixed port 5173 (`strictPort`). The app runs on loopback against the normal HTTPS FeatherAuth, so no FeatherAuth setting changes (`require_https` stays `true`); its pages over plain `http` on loopback are the developer's own machine. Scopes: `openid` only, the one scope FeatherAuth recognises; the claims come from `user_data.claims`.

**Flow.** `src/auth.js` builds one `UserManager` from `config.json` with `response_type: "code"` (PKCE `S256` is the library's default), `scope: "openid"`, `loadUserInfo: false` (the app calls userinfo itself, step 4), `automaticSilentRenew: false`, and `userStore: new WebStorageStateStore({ store: new InMemoryWebStorage() })`; the sign-in state across the redirect stays in the library's default `sessionStorage` state store, which holds no token.

1. At start the library reads discovery from `<authority>/.well-known/openid-configuration` (CORS, FR-26).
2. "Sign in" calls `signinRedirect()`: the browser goes to the authorize endpoint with a `state`, a `nonce` and a PKCE challenge, then to the provider (or the chooser) and back to `/callback`.
3. On `/callback` the app calls `signinRedirectCallback()`, which exchanges the code at the token endpoint and checks `state` and the ID token's claims (`iss`, `aud`, `nonce`, `exp`). The library does not check the ID token's signature, so `src/auth.js` then verifies it with `jose`: `jwtVerify(id_token, createRemoteJWKSet(new URL(jwks_uri)), { issuer: authority, audience: client_id, algorithms: ["RS256"], typ: "JWT", clockTolerance: 300 })`; the 300 seconds are the clock skew `oidc-client-ts` itself allows, so a token the library accepted is not refused for a few seconds of skew on the developer's machine. A failure shows the error and discards the user. Then the app replaces the URL with `/`.
4. The page shows the verified ID token's claims (`sub`, `name`, `email`, `email_verified`, `preferred_username` when present, `auth_time`, `exp`) and whether userinfo's `sub` equals the ID token's: the app calls the userinfo endpoint itself with the access token for that comparison, once after each sign-in and once after each refresh; the library makes no userinfo call of its own (`loadUserInfo: false`), so there is no second call.
5. "Refresh" calls `signinSilent()`, which uses the refresh token at the token endpoint; the page shows the new access token expiry and how many refreshes were made. The app refreshes only on this button (`automaticSilentRenew: false`) because refresh tokens rotate: two refreshes sent at once with one token, as an automatic timer and a click could do, would be a reuse, and a reuse after the grace window revokes the session (Sessions and refresh rotation).
6. "Sign out" calls `signoutRedirect()`, which sends `id_token_hint`, `client_id` and `post_logout_redirect_uri` to the logout endpoint (RP-initiated logout, request 1 of Ending a session); FeatherAuth ends the session and redirects to `/` with `state`, where the app calls `signoutRedirectCallback()` and shows "Signed out".

Tokens are kept in memory only, as Clients advises for single-page apps, so a reload of the page loses the session and the user signs in again; no token is shown on the page or written to the console.

**Page.** One page with an element `#status` ("Signed out", "Signed in", or "Error"; it and `#signin` are rendered only once the start has finished: `config.json` read and, on `/callback` or on the return from logout, the callback processed), the buttons `#signin`, `#refresh` and `#signout` (each shown only when it applies), `#verified` ("ID token signature verified"), a table `#claims` of the claims above, `#userinfo` ("userinfo sub matches"), `#expires` (access token expiry) and `#refreshes` (a count), and `#error` with the `error` and `error_description` of a failed step.

**Running it.** With Node: `cd examples/web-app && npm ci && npm run dev`, then open `http://127.0.0.1:5173/`. With Docker only: `docker compose -f examples/web-app/compose.yaml up --build`; `compose.yaml` mounts `./public/config.json` read-only at `/srv/config.json` over the copy in the image, so one build serves any FeatherAuth and the `authority` is changed by editing `public/config.json` and reloading the page, with no rebuild. Caddy serves `dist/` over plain `http` on port 5173 (`auto_https off`, `admin off`), and any path without a file, such as `/callback`, falls back to `index.html`. On every answer it sets `Content-Security-Policy: default-src 'self'; connect-src 'self' https:; frame-ancestors 'none'; base-uri 'none'; object-src 'none'` and `X-Content-Type-Options: nosniff`. The policy fits the built app: Vite emits one module script and its assets as files under `/assets/`, with no inline script or style, so `default-src 'self'` covers scripts, styles and images; `connect-src 'self' https:` lets the app read `config.json` and call the FeatherAuth endpoints (discovery, token, userinfo, JWKS) on any `https` origin, since the authority is set at run time; the sign-in and sign-out are top-level navigations, which the policy does not restrict. The Vite dev server of `npm run dev` sets no such headers. The README gives both ways to run it, points to `example-web-client.yaml`, and says that `authority` in `public/config.json` names the realm's issuer and is read at every page load.

**Tests.** `make example` runs `npm ci --ignore-scripts` (no package's install script runs) and `npm run build` in `examples/web-app` (it needs Node; `make check` does not run it). `make browser` runs `make example` first, and the browser job of CI installs Node with `actions/setup-node` pinned by commit hash, `node-version-file: examples/web-app/.node-version` (OPS-03). `TestBrowserExampleWebApp` (`internal/testutil/server`, build tag `browser`, chromedp as the other browser tests) starts the in-process test server with the mock identity provider as the realm's only provider and the client entry read from `examples/web-app/example-web-client.yaml`, with `http://127.0.0.1:5173` replaced by `https://app.example.com` (so `https://app.example.com/callback`, `https://app.example.com/` and the origin `https://app.example.com`), so that the shipped entry is the one tested; it serves `examples/web-app/dist` on `app.example.com` with a `config.json` naming that server, and fails, naming `make example`, when `dist` is missing. The server's fake clock is set to the real current time at the start and not advanced, because the browser checks `exp` and `iat` with its own clock. The test clicks `#signin`, then expects `#status` "Signed in", `#verified`, the mock user's `sub` and name in `#claims` and `#userinfo`, and exactly one userinfo call; clicks `#refresh` and expects `#refreshes` 1, exactly one more userinfo call, and the session's previous refresh token rotated in the store; clicks `#signout` and expects `#status` "Signed out" and the session revoked in the store; `#error` stays empty throughout; and after the sign-in neither `localStorage`, `sessionStorage` nor the page's text holds the access, ID or refresh token. `make check` also runs `deploy/example_web_app_test.go` (exact versions of exactly the named dependencies, a lockfile with a `sha512` integrity hash from the npm registry for every package, the `go.mod` stub, `.node-version` equal to the Dockerfile's node image, both images pinned by digest, the loopback port, and the CI step) and a test of `internal/config` that the shipped realm example holds no `example-web` client and validates with the block of `example-web-client.yaml` added. `make ops` runs `deploy/ops/check-example.sh` (`TestOpsCheckExample`), which needs host port 5173 on the loopback free: it builds and starts the compose file, and checks that it becomes healthy, is published on `127.0.0.1:5173` only, serves the page at `/` and at `/callback` with the two security headers above exactly, and serves at `/config.json` the mounted `public/config.json`, parsed as JSON and compared field by field (`client_id` `example-web` and the other three fields as in the file), not matched as text. Not tested: the README's text and a sign-in against a real FeatherAuth and provider.

### Rows not yet traced

A row moves into the table above as soon as any test for it exists; there it is listed in `tools/trace/pending.txt` until a test proves all of it, and its tests carry `Acceptance: <Area>` (with `(part)` while partial). "Test status" says what that change needs.

None today: every row of this document has a test. A new row without a test is listed here with the columns Area, Test, Pass condition, Covers and Test status, and moves into the table above in the change that adds its first test.

- **Ops (`make ops`, build tag `ops`, run by CI).** Go tests run the scripts of `deploy/ops/` against docker and fail on a non-zero exit. `check-proxy.sh` runs `caddy validate` on the Caddy example and its variants and `nginx -t` on the nginx example with nginx 1.28 and 1.24, and sends requests with a query string through a real nginx to prove that neither its access log nor its error log holds the query. `check-image.sh` checks the image and the compose files and runs a login, an import and a backup in the container started from `compose.yaml`; it then runs the same login and the CLI commands in the stack of `compose.postgres.yaml`, and checks that the database publishes no port, that `backup` is refused naming `pg_dump`, that `strict_permissions` accepts the password file at `0600` and refuses it at `0644`, and that the password is in no log or database file. `check-offsite.sh` runs `backup-offsite.sh` on a snapshot with one imported user and proves that the copies (the snapshot and the configuration tar) cannot be read as SQLite or tar, that they decrypt with the private key, and that a service restored from them serves. `check-rolling.sh` starts `compose.ha.yaml`, runs a loop of logins and refreshes through Caddy, runs `rolling-deploy.sh` during it, and passes when every request of the loop succeeded and the loop ran through the whole deploy. `TestOpsCaddyOpensAConnectionPerRequest` (`deploy/proxy_connections_ops_test.go`, row Restart) runs Caddy (the image of `compose.caddy.yaml`) in docker with each shipped Caddyfile, derived as `check-proxy.sh` derives its variants: for `Caddyfile.example` the site address becomes plain HTTP on a port published on `127.0.0.1` and the upstream becomes the test's upstream; for `Caddyfile.ha` both upstreams become two listeners of the test's upstream. That upstream is a Go HTTP server of the test on all interfaces, which the container reaches as `host.docker.internal` (`host-gateway`, as the load stack does); it answers `GET /readyz` `200` on any connection (Caddy's health checks), answers the first `POST` on a connection `200` with a fixed body, and closes a connection without answering when a `POST` arrives on a connection that already carried a request: the state of the race, made certain. It counts connections and `POST` requests. The test sends two `POST` requests for each upstream address of the Caddyfile (two for `Caddyfile.example`, four for `Caddyfile.ha`, whose round robin alternates), one after the other, and requires every one to answer `200`, each from its own upstream connection (with the Caddyfiles before this rule a `POST` that meets a reused connection answers `502`, so the test fails first); then it closes the upstream's listeners, sends a `POST` (for `Caddyfile.ha` both listeners are closed, so no instance is ready and the request is held by `lb_try_duration` alone), opens them again on the same ports 1 second later (the ops tests run on the real clock, `clock.Real`), and requires that `POST` to answer `200` after at least 1 second and under 10 seconds, and the upstream to have counted it once. The hardened Postgres check (SEC-44) starts the stack of `compose.postgres.yaml` on an empty volume and again on the volume it filled, and asserts with `docker inspect` that the `postgres` container has a read-only root, `CapDrop` `ALL`, `CapAdd` exactly the four add-backs, `no-new-privileges`, and only the data volume and the `tmpfs` at `/var/run/postgresql` writable (no `tmpfs` at `/tmp`); that it becomes healthy both times and a login and a refresh work through it; and that the same start with any one add-back removed does not become healthy, so the list holds nothing it does not need. Any of these assertions failing fails `make ops`. The image-only setup check (OPS-21, `deploy/ops/check-setup.sh`) runs the containers of "Setup with the image alone" with the candidate image, on a new docker volume (so that owners and modes are those of a Linux file system on every host) owned by uid 65532 with mode `700`: `config init`, then `keys generate` for an RSA key at the example's path `secrets/example/signing-2026-10.pem`, an EC key at `secrets/example/signing-ec-1.pem` and an encryption key at `secrets/encryption_key`. It asserts that each exits `0`; that `config check` then prints only `ok`; that `server.yaml`, `database.yaml`, `realms/example.yaml` and `locales/en.yaml.example` exist; that the three keys are owned by uid 65532 with mode `0600`, the first RSA of 2048 bits, the second EC P-256, the third 44 base64 characters of 32 bytes; that a second `keys generate` on each exits `1` and leaves it unchanged; and, so that the `ok` is not an absent check, that with the encryption key at mode `0644` `config check` exits `1` and names the mode. **Upgrades with no previous release.** `TestOpsUpgradeSQLite` and `TestOpsUpgradePostgres` need a previous release: `PREV_IMAGE`, or else the newest tag `vMAJOR.MINOR.PATCH` of the repository, built from a git worktree of that tag. The rules, in this order: a missing docker fails the test; a checkout without the full history (`git rev-parse --is-shallow-repository` prints `true`) fails it with `fetch the full history and the tags (fetch-depth: 0, fetch-tags: true)`, so a CI checkout without tags can never pass for "no release"; with `PREV_IMAGE` set, or a release tag present, the test runs, and a failure to build or pull the previous image fails it; with neither, and only then, the test calls `t.Skip("no previous release to upgrade from")`, because before the first release there is nothing to upgrade from, as item 5 of the release check records (`not applicable: there is no previous release`). This is the one exception to the rule of the repository that ops tests never skip; it covers these two tests and only this cause. `TestOpsPostgresRestore` needs no previous release: it dumps and restores with the candidate image alone (`NEW_IMAGE`, or the image built from the working tree), so it never skips. ## Open items

An item is listed here only while it is undecided. When one is decided, the decision is written into the sections of this document it affects and the item is deleted, so the document body is the only record of decisions. Each item says what is undecided, who runs into it, the recommended decision, and which sections change when it is decided; "Seen by" names the group: **Users** (the people signing in), **Web apps** (browser-based apps that use FeatherAuth), **Operator** (the person who deploys and runs it), **App developers** (people building an app or API that uses it) and **Implementers** (people building FeatherAuth itself).

- **Paid certificate with Caddy not run.** Undecided: how Caddy treats replaced `tls <cert> <key>` files. The Caddy half of the TLS examples was run on a test host (automatic Let's Encrypt certificate, redirect, persistence across a restart), but the paid-certificate variant was checked against documentation only, and Caddy's documentation does not say whether it picks up replaced files without a reload. The design's instruction to reload Caddy after replacing the files is the safe one and stays. **Seen by:** Operator. **Recommended decision:** run the variant on a test host once, with a certificate replaced under a running Caddy, and either keep the reload instruction as required or relax it to what was seen. **Sections that change when decided:** TLS certificates (Deployment and operations), the user guide.
- **Checks that were not run, or run only in part.** Undecided: whether each is closed by a test, run by hand, or accepted. They are known limits, none of which changes a behaviour: (1) the encryption-key restart is not tested in the wiring test of the emergency key rotation (SEC-10, SEC-07); (2) no real Postgres deadlock (`40P01`) is provoked in tests, the forced SQLSTATE hook stands in for it, and the verified-email race test is timing based; (3) the `pg_dump` plus `age` backup and its restore are proved by the row Postgres restore in `make ops`, on the compose stack; a restore on a separate physical host, as an operator would do it, has not been run; (4) the `X-Content-Type-Options: nosniff` of SEC-29 covers answers written by FeatherAuth's handlers and not those `net/http` writes itself (for example a malformed request line), on the router and on the plain redirect listener alike; (5) `tools/archcheck` rejects an `http.Client` literal without `CheckRedirect` only in non-test files of `internal/provider`, and its hand-written cryptography check is an import allow-list that does not catch cryptography assembled from allowed primitives in an allowed file; (6) an iOS in-app session and Android Custom Tabs were not tested for the Apple web flow, and real logins on iOS and Android were not run (not required, Acceptance criteria). **Seen by:** Implementers, Operator. **Recommended decision:** add a test for (1); accept (2), (3), (4), (5) and (6) and name them in the security notes of the user guide. **Sections that change when decided:** Acceptance criteria, Tech stack and code structure, the user guide.
